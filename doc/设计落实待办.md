## 四、7 条集成纪律（原文 §3.1）→ 落到本工程哪里

| # | 事项 | 我们的动作 |
| --- | --- | --- |
| 1 | `imu_top` 的 `SCK_HALF_DIV` **RTL 默认 3（8.33 MHz，实测初始化失败）**，README/示例写 25（1 MHz） | `rtl\top\` 例化**必须显式写 `.SCK_HALF_DIV(25)`**，不依赖默认值。失败表现是 `o_err_code=2`，极易误判成"模块坏了"（§10-14） |
| 2 | `hdmi_1024x600` 顶层不对 `reset_n` 做像素域同步释放（内部直接用 `reset_n & pll_lock`） | `rtl\common\` 自建复位同步链：DVI 单独一条、比主逻辑延后两拍，并加布局约束；否则上电偶发花屏 |
| 3 | `pixel_req` ≡ `video_active` ≡ `disp_driver.Disp_DE` | 像素源必须在 `pixel_req` 为高的**那一拍**给出 `pixel_rgb888`（同一时钟沿采样）；`pixel_x/y` 有效区外输出 0。写进 UI 合成层（现为 `ui_render`；原计划的 `ui_compositor` 已合并进去）的接口约定 |
| 4 | `m10_point_cloud_core` 的 `out_de/out_hs/out_vs` **三拍对齐** | UI 合成用它的 `out_*`，不能直接用输入的 `video_de/hs/vs`，否则雷达层整体错位三拍 |
| 5 | `m10_radar` 端口**无 `i_`/`o_` 前缀** | 顶层按端口名连接，**不要顺手改名**（改名会让端口与包 README / 示例脱节，将来排错与升级时难追溯） |
| 6 | `disp_parameter_cfg.vh` 由 `disp_driver.v` 包含 | 不要再把它当独立 Verilog 源加入工程；换分辨率要同时改显示时序与 UI 布局（我们的 `scripts\vendor_sources.tcl` 只收 `*.v`，天然不收 `.vh`，符合此要求） |
| 7 | `m10_radar/constraints/m10_radar.sdc` 是 **50 MHz 独立模板** | 与 HDMI 示例的完整约束**不能同时加载**；集成时按顶层端口/实例名合并成**一份** `constr\*.sdc` |

### ⚠ 口径更正（我上一轮的表述需要修正）

"PWM 20 kHz / 控制环 1 kHz / 编码器反馈 1 kHz / TOF 50 Hz / 手柄 100 Hz"这一组指标出自**已删除的 404 行版**；
现权威的 AI 扩写版（**678 行**）给的是 **§4.3 数据流与带宽预算**：

| 链路 | AI 扩写版（678 行）的指标 |
| --- | --- |
| IMU → yaw | 1 kHz × 14 B（SPI 1 MHz，占空 11%） |
| 编码器 → 速度环 | 4 × **100 Hz**（计数/10 ms 窗口）← 与现有 `speed_measure` 默认窗口一致 |
| 雷达 → 点云 | 460800 8N1，102 B/包，≈20 包/s（≈92 kbit/s，占用 20%） |
| ToF | I2C 400 kHz，≈30 ms/次 → **测距周期 ≥ 30 ms** |
| 遥控 | 6 路 PWM，20 ms 周期（捕获分辨率 ≈ 1 µs） |

**PWM 频率在扩写版里没有给指标**：现有 `motor_pwm` 用 `2^PWM_BITS` 拍周期（零乘除法、`duty = 2^(N-1)` 恰为 50%），
50 MHz 下若要 20 kHz 需 2500 拍（非 2 的幂）→ 存在"精度 vs 频率"的取舍，**定标前先与需求方确认频率要求**。
