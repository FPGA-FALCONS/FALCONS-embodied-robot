## 一、项目目标与范围

**平台**：高云 ACG720 开发板，器件 **GW5AT-138B**（`GW5AT-LV138PG484AC1/I0`），系统时钟 **50 MHz（Y18）**。
**载体**：四驱差速（skid-steer）小车，4 × MG513P30_12V 电机 + GMR 500PPR 编码器 + WHEELTEC D24A 双 TB6612 驱动板。
**屏幕**：板载 HDMI 输出，**1024×600 @ 约 60 Hz**（`hdmi_1024x600` 模块固定时序）。

**设计原则**：模块之间尽量独立解耦、封装程度高 —— 具体落到四条硬约束上：

1. **接口先行**：模块间只通过定死的端口表通信（沿用 `car_fpga/doc/模块划分与接口规范.md`）；
2. **单时钟域**：本模块内不产生新时钟，分频一律用时钟使能 `ce`；跨域只在专门的 CDC 模块里发生；
3. **对外用物理量整数**：角度 0.01°、角速度 0.01°/s、速度 mm/s、距离 mm，**不传裸 Q 格式**；
4. **可观测**：每个模块至少有一个上板可看的输出（LED / 串口 / 屏幕数值）。

**手册中不存在 J8**，编号为 J1~J7 + J9，属正常（J8 未引出）。全部接口的每一根信号都**同时**出现在 J1 排针上（见 2.4 的接线纪律）。

### 2.5 接线纪律（踩过坑，逐条遵守）

| # | 纪律 | 原因 |
| --- | --- | --- |
| 1 | **排线按 Pin 号核对两端，确认 Pin1** | 母头面对插孔与公针**镜像**；插反会整排错位，综合完全查不出来 |
| 2 | **J1 与 Jx.y 是同一网络，接线二选一** | 同时接 = 两路驱动同一网络，冲突 |
| 3 | 电机 13 根输出全部 `PULL_MODE=DOWN` + STBY 加 10 kΩ 下拉 + 拔掉驱动板 STBY 跳线帽 | 三层防护，保证上电不窜车 |
| 4 | 地线**单点汇合**（J5 pin2），星形接地 | 避免地环路；电机电流不进 FPGA 地 |
| 5 | GPIO0 bank 跳线**必须 3.3 V** | 所有外设都是 3.3 V 电平 |
| 6 | **雷达必须接 J3.3 = C14**（J3 为 HY2.0 6P / 2.0 mm 座，非 2.54 排针） | 手册第 5 页第 2 条明示"雷达 J3.3 为雷达 TX → 主板 RX，接 C14 / J1.24；本板仅接收雷达数据"。模块库 M10 例程用的是 **A15**（`acg720_m10_hdmi.cst:13`），而它自己的 `docs/hardware_notes.md:17` 就写明"**A15 是 FPGA 球位，排针位置按板卡丝印核对**"—— 那是**不装 IMU 时的独立飞线选脚**。本车 IMU 必装（A15 = J2.6 = IMU `CS`），且 J1 与 J2 是**同一条网络**，两个输出挂一起会**对打**。集成时把 `IO_LOC "i_radar_rx"` 由 A15 改为 **C14** 即可：端口名、RTL 都不动 |
| 7 | 雷达不要接到 USB 串口 RX（J21） | J21 已被调试串口占用（M10 例程注释也如此提醒） |

### 2.6 ★ 供电预算（本车第一个必须核实的硬约束）

手册第 5 页原文：**"全板供电设计条件：3V3 合计 100 mA、5V 合计 50 mA，并非逐接口额度"**，
并附声明 **"主板实际供电能力尚未核实；5V 与 3V3 保持为独立电源网络"**。

本车外设清单与取电口：

| 外设 | 取电 | 电压 | 备注 |
| --- | --- | --- | --- |
| IMU660RA | J2.1 = 5V | 5 V | 板载 LDO，实测可用 |
| M10 雷达 | J3.1 = 5V | 5 V | 雷达通常功耗较大（**待实测**） |
| ToF（VL53 类） | J7.1 = 3V3 | 3.3 V | 约 20 mA 量级 |
| 遥控接收机 | J9 | 5 V 或 3.3 V | 视接收机而定 |
| OV5640 摄像头 | 板载 COMS 排针 | 3.3 V | **不在 J 接口额度内**（待确认供电来源） |
| HDMI 屏 | 板载 HDMI 口 | — | 显示器自供电 |

> **风险**：5 V 额度 50 mA 是否包含雷达与 IMU？若按字面理解，则在 50 mA 内挂 IMU（约 5 mA）+ 雷达（通常 100~200 mA）**不可行**。
> **对策**：① 先实测各外设实际电流与主板 DC-DC 余量；② 雷达与电机电源同源（D24A 模块的 5 V/5 A 输出）单独供电，只共地；
> ③ 把结论写进硬件标定记录。

### 3.1 ★ 集成前必须知道的 7 条（逐条来自源码核查，不是推测）

| # | 事项 | 后果 / 做法 |
| --- | --- | --- |
| 1 | **`imu_top` 的 `SCK_HALF_DIV` 默认值有分歧**：RTL 默认 `3`（8.33 MHz，实测**初始化失败**），README 与示例写 `25`（1 MHz） | 本车例化**必须显式写 `.SCK_HALF_DIV(25)`**，不要依赖默认值 |
| 2 | **`hdmi_1024x600` 顶层不对 `reset_n` 做像素域同步释放**（内部直接用 `reset_n & pll_lock`） | 顶层需自建复位同步链（DVI 单独一条、比主逻辑延后两拍，示例还带布局约束），否则可能上电偶发花屏 |
| 3 | **`pixel_req` ≡ `video_active` ≡ `disp_driver` 的 `Disp_DE`** | 像素源必须在 `pixel_req` 为高的**那一拍**给出 `pixel_rgb888`（模块在同一时钟沿采样）；`pixel_x/y` 在有效区外输出 0 |
| 4 | **`m10_point_cloud_core` 的 `out_de/out_hs/out_vs` 是三拍对齐的** | UI 合成要用它的 `out_*`，不能直接用输入的 `video_de/hs/vs`，否则雷达层整体错位三拍 |
| 5 | **`m10_radar` 端口没有 `i_`/`o_` 前缀**（`clk`/`reset_n`/`radar_rx`/`point_*`） | 与模块库其余模块风格不同；顶层按端口名连接即可，不要"顺手改名" |
| 6 | **`disp_parameter_cfg.vh` 由 `disp_driver.v` 包含** | 不要再把它当独立 Verilog 源加入工程；换分辨率要同时改显示时序与 UI 布局 |

### 4.2 ★ 时钟域与复位策略（本方案最需要先定死的事）

| 时钟域 | 频率 | 来源 | 归属模块 | 跨域需求 |
| --- | --- | --- | --- | --- |
| `sys_clk` | 50 MHz | 板载 Y18 | IMU、控制、估计、雷达读取、串口、ToF、遥控 | — |
| `pixel_clk` | 49 MHz | `hdmi_1024x600` 内置 PLL | HDMI 时序、点云显示核心、UI 合成 | **与 sys 域大量交互** |
| `serial_clk` | 245 MHz | 同上 PLL | TMDS 串行（模块内部） | 不对外 |
| `camera_pclk` | 摄像头输出 | OV5640 | 采集 | 经**异步 FIFO 或 DDR 帧缓存** |
| `ddr_clk` 等 | 由 DDR3 IP 决定 | DDR3 控制器 | 帧缓存 | 经 DDR3 IP 的用户接口 |

**策略**：
1. **控制链路全程 sys_clk（50 MHz）**，不让任何控制/估计逻辑进入像素域 —— 这是本架构的第一原则；
2. **视频链路全程 pixel_clk（49 MHz）**，`m10_point_cloud_core` 的 `CLK_FREQ_HZ` 也按 49 MHz 配置（其默认值就是 49 MHz，与 HDMI 像素时钟天然同域）；
3. 跨域只允许三种方式：**① 参数类**（模式、缩放档、目标点）用"寄存器 + 握手脉冲"；**② 数据类**（帧缓存、位图）用**双口 RAM / DDR3**；**③ 状态位**（LED、sticky 标志）用两级同步器。
4. **复位释放与 PLL `locked` 联动**：先等 `pll_lock` 与 DDR3 校准完成，再释放各域复位（模块库示例已这样做，含 DVI 专用复位释放链的布局约束）；
5. **参数传递必须打拍**：sys→pixel 的参数（如航向角、目标点坐标）先锁存，再在像素域用两级同步器采样，避免多比特撕裂。

### 4.3 数据流与带宽预算

| 链路 | 数据量 | 带宽/占用 | 说明 |
| --- | --- | --- | --- |
| IMU → yaw | 1 kHz × 14 B | 14 kB/s | SPI 1 MHz，占空 11% |
| 编码器 → 速度环 | 4 × 100 Hz | 忽略 | 计数/10 ms 窗口 |
| 雷达 → 点云 | 460800 8N1，102 B/包，约 20 包/s | ≈ 92 kbit/s（占用 20%） | 每包 42 槽 |
| 摄像头 → DDR3 | 1024×600 RGB565 @30 fps | ≈ 37 MB/s 写 | 若 60 fps 则 74 MB/s |
| DDR3 → HDMI | 1024×600 RGB888 @60 Hz | ≈ 110 MB/s 读 | 需 DDR3 高位宽/高频 |
| HDMI 输出 | 1024×600@60 | 像素时钟 49 MHz | 固定 |
| ToF | I2C 400 kHz，约 30 ms/次 | 忽略 | 测距周期 ≥ 30 ms |
| 遥控 | 6 路 PWM，20 ms 周期 | 忽略 | 捕获分辨率 ≈ 1 µs |

> **结论**：真正吃带宽的只有**摄像头↔DDR3↔HDMI** 这条链。若 DDR3 容量/带宽不足（**待确认**），
> 退路是：① 摄像头降分辨率或降帧率；② 摄像头页与雷达页**分时复用**一块帧缓存；③ 直接把摄像头 RGB565 经异步 FIFO 缩放后送 HDMI（不做整帧缓存，会有撕裂）。

## 五、功能详细设计

### 5.1 IMU 数据读取与偏航角积分

> **原文**：1. imu数据读取与偏航角积分。已完成imu读取和积分的模块，可直接使用。

**现状**：完整链路已上板验证，可直接例化：`imu660ra` → `gyro_tilt_comp` → `yaw_integrate`，输出 `o_yaw`（0.01°，±18000）。

**连接要点**：`gyro_tilt_comp.i_sample_valid` 必须接 `imu660ra.o_acc_valid`（**不是** `o_data_valid`）——这是踩过的坑，接错表现为"补偿永远不生效且不报错"。

**需要补的两件事**（差速小车专属优势，强烈建议做）：

1. **编码器互补**（解决 yaw 长期漂移）：差速车原地可转、低速运动学可靠，用轮速推算的航向 `ω_enc = (v_r − v_l)/L` 做慢速修正：
   `err = wrap180(yaw_enc − yaw_gyro); yaw = yaw_gyro + Kp·err`（Kp ≈ 0.01~0.1）。
2. **侧滑系数 k 标定**：skid-steer 转弯必然侧滑，`ω_实际 = k·ω_理论`，k ≈ 0.7~0.95。
   做法：让车原地转 360°，记录陀螺积分角度与轮速推算角度，`k = θ_gyro / θ_enc`，写入参数寄存器。

**前提**：轮距 L、轮径、减速比需实测（**待确认**）。

### 5.2 电机闭环（四路独立 + 左右差速转向）

> **原文**：2. 电机闭环，已完成电机pwm驱动的模块，可直接使用。要求四个电机单独闭环。小车行驶中，左侧两轮同速，右侧两轮同速。左右侧差速实现转向。

**现状**：`motor_tb6612`（驱动+编码器+堵转保护）+ 工程内 `speed_pid`（增量式 PID）已就绪，仿真 3 个 tb 全 PASS、综合通过（Fmax 55.4 MHz、DSP 14/298）。
**待办**：上板整定（`car_fpga/doc/速度闭环上板调试指南.md` 已给出命令与步骤）。

**新建 `chassis_ctrl`**：把"整车指令"翻译成四路目标转速。

| 输入 | 输出 | 说明 |
| --- | --- | --- |
| `i_v_cmd`（mm/s，有符号）、`i_omega_cmd`（0.01°/s，有符号） | 四路 `i_setpoint`（计数/窗口） | 差速分配：`v_l = v − ω·L/2`、`v_r = v + ω·L/2` |

- **左侧同速、右侧同速**由本模块保证（同一侧两路给同一目标）；左右差速即转向；
- 单位换算集中在**一个**换算函数里（`mm/s → 计数/窗口`），改编码器/轮径只改一处；
- 预留：直线纠偏（用 yaw 作外环叠加到 `omega_cmd`）、滑移系数 k 参与换算。

**优先级仲裁**（同一个模块内做，避免"谁最后写占空比"的乱战）：

```
安全急停（ToF / 遥控失效 / 堵转）  >  遥控手动  >  自动任务（导航/纠偏）  >  停机
```

### 5.3 航位计算（里程计）

> **原文**：3. 航位计算。使用编码器采集的电机转速数据，用Imu解算的航向角进行矫正（差速车可能有侧向打滑），计算当前航位并显示在屏幕上。

**新建 `odom`**，输出统一用物理量整数：

| 输出 | 格式 | 说明 |
| --- | --- | --- |
| `o_x` / `o_y` | int32，**mm** | 车体坐标（上车时清零） |
| `o_yaw` | int32，0.01° | 融合后的航向 |
| `o_v` | int16，mm/s | 车体中心线速度 |
| `o_omega` | int16，0.01°/s | 车体角速度 |

**推算公式**（四驱 skid-steer）：

```
v     = (v_l + v_r) / 2
ω     = k · (v_r − v_l) / L          ← k 为侧滑系数（5.1 标定）
yaw  += ω · dt                       ← 与陀螺做互补（5.1）
x    += v · cos(yaw) · dt
y    += v · sin(yaw) · dt
```

**实现要点**：
- **三角运算**：定点 CORDIC 或 256/512 点 sin/cos 查找表（模块库 `m10_radar` 已有 `sin_lut.vh`（Q14 正弦表）可复用思路）；
- **★ 角度解缠（unwrap）**：`yaw_integrate` 输出 ±180° 回绕、**无圈数信息**，而 odom 的 `cos/sin` 需要连续角 ——
  必须自建"连续航向"：每拍比较新旧角度，跨越 ±180° 时补 ±36000（0.01° 单位），否则车一转到边界，x/y 会被算飞；
- **★ `yaw_integrate.i_enable = 0` 的语义是"冻结并强制 yaw = 0"**：停车/暂停任务时若直接拉低它，航向会被清零、恢复后航位基准就变了。
  正确做法：任务暂停时**保持 `i_enable=1`**，只在真正需要重新定航向时用 `i_clear`（或由 `odom` 自己做"冻结但保持"）；
- **时基**：统一 100 Hz 更新（与测速窗口同拍），`dt = 10 ms` 常数；
- **打滑检测**：`|ω_gyro|` 与 `|ω_enc|` 长期偏离 → 标记"打滑中"，航位可信度下降（显示页给出提示）；
- **坐标系**：上车时 `yaw` 与被测航向同源，避免"两个 yaw"（陀螺 yaw 与 odom yaw 必须来自同一融合结果）。

### 5.4 HDMI 显示与 UI

### 5.5 摄像头采集与显示（含 RK3588 预留）

> **原文**：5. 摄像头画面采集，显示到屏幕上。目前阶段无需进行画面识别，仅显示，但后期有外接RK3588进行图像处理的需求，可预留位置。

**现状**：`ov5640_capture`（默认 1024×600 RGB565、SCCB 400 kHz 初始化）+ 已验证的 DDR3 帧缓存 + HDMI 示例工程可直接复用。

**预留 RK3588 的做法**（关键是把"接口"提前留好，而不是提前写协议）：

1. **物理层**：板载 USB2.0（FX2 类从机接口，30 根信号）或以太网（RGMII 15 根）都可作为到 RK3588 的通路 —— **待确认**最终选哪条；
2. **逻辑层**：在 `ui_compositor` 与 `ov5640_capture` 之间留一个**标准像素流接口**（`valid/ready` + RGB888/565 + 行列坐标），
   RK3588 通路将来只作为该接口的**另一个消费者**，不改动采集与显示侧；
3. **控制层**：预留一组"外部命令寄存器"（走 UART 或以太网），RK3588 只写寄存器/读状态，不直接碰时序。

### 5.6 ToF 紧急刹停

> **原文**：6. tof测距，tof模块装在车前端，感应距离50cm左右，仅用作紧急刹停。当前方障碍物距离小于一定值，控制车辆紧急刹停。

**接口**：J7 = 3V3 / GND / SDA E17 / SCL F16 / INT C20 / SHUT D20（I2C 从机地址典型 0x29）。

**新建两个模块**：
- `i2c_master`（通用 I2C 主机，400 kHz）—— 模块库内**有**可复用实现（`ov5640_capture` 包里的 `i2c_control`/`i2c_bit_shift`，带读能力端口），
  但它当前封装把读路径固定关闭、且属第三方代码（许可不明）；**建议新写一份干净的实现**（读写 + 超时 + 时钟拉伸处理，约 200 行），避免许可与"只写"两个限制；
- `tof_range`（VL53 类测距驱动）：上电初始化 → 周期测距（≥30 ms）→ 输出 `o_distance_mm` + `o_valid`；带超时/丢线检测（`o_timeout` → 视为"无目标"，不能因为读不到就把车停死）。

**`safety_stop` 判据**（写进文档，避免实现时随手改阈值）：

| 条件 | 动作 |
| --- | --- |
| `distance < D_STOP`（建议 150 mm，用户说"50 cm 左右"可先取 300 mm）连续 N=3 次 | **急停**：四路 duty=0 且 `brake=1`（短路刹车），速度环复位 |
| `distance < D_SLOW`（如 400 mm） | 限速（叠加到 `v_cmd` 上限） |
| 测距超时/无效 | 不触发急停，仅置标志与 LED |
| 急停后 | 需**人工解除**（遥控/串口/按键），不自动恢复 —— 与堵转保护同一哲学 |

**优先级**：`safety_stop` 直接钳制 `chassis_ctrl` 的输出，不经过 PID（PID 的积分状态一并复位，防止解除后暴冲）。

### 5.7 雷达建图与避障

> **原文**：7. 雷达模块，建2D平面图，实现自主避障，该避障功能在后续的导航功能中体现。

**现状**：`m10_radar`（读取 + 42 槽点云 + 握手/背压 + 诊断）与 `m10_point_cloud_core`（位图 + 显示 + 缩放）已具备，
**但"避障"本身没有实现** —— 显示核心只做可视化，不产出可用的障碍物列表。

**新建 `map_build`**：把点云累积成**栅格占据地图**（与显示位图分开，或复用同一位图的双口读）：

| 参数 | 建议值 | 说明 |
| --- | --- | --- |
| 栅格尺寸 | 512×512 | 与显示位图一致，便于叠加 |
| 分辨率 | 20 mm/像素 | 覆盖 10.24 m × 10.24 m |
| 更新 | 每包（约 20 Hz） | 增量叠加 + 概率衰减（简单计数即可，不必上完整 log-odds） |
| 存储 | DDR3 或 BSRAM | 512×512×8 bit = 256 kB（BSRAM 不够，**建议放 DDR3**） |

**避障（局部）**：先用"前向扇区最近距离 + 减速/停"的简化策略（`front_points` 已由显示核心提供），
再做 DWA/向量场直方图（VFH）。**全局规划**见 5.8。

### 5.8 自主导航与路径点导航

> **原文**：8. 自主导航与路径点导航。可在雷达建图上选定目标点或路径点，小车自主规划路径经过路径点并到达目标点，其中要自主避障和绕障。已完成雷达数据接收模块以及建图模块。

**现状**：雷达接收 + 建图（显示用）已有；**路径规划、路径跟踪、绕障均需新建**。

**建议分三层落地**（每层都能独立验收，避免一次做太大）：

| 层 | 内容 | 实现要点 | 难度 |
| --- | --- | --- | --- |
| L-A 路径点跟踪 | 给定路径点序列，用纯追踪（pure pursuit）或"朝向+距离"双环控制 | 输入 `odom(x,y,yaw)` + 路径点数组；输出 `v_cmd/omega_cmd` | 中 |
| L-B 局部绕障 | 路径点被挡住时，用雷达扇区做局部避让（VFH/DWA 简化版） | 与 5.7 的栅格/扇区共用数据 | 中高 |
| L-C 全局规划 | 栅格地图上 A*（或 Jump Point Search）生成路径 | 需 open/closed 表 + 优先队列，**资源与迭代次数是难点**，建议放 DDR3 并用定点代价 | 高 |

**资源提醒**：A* 在 FPGA 上做需要"每步代价排序"，若用 BSRAM 存 512×512 的 g/h 表（各 256 kB）不可行；
**务实路线**：① 先做 L-A（路径点跟踪）；② 绕障用 L-B；③ 全局规划**优先考虑放到 RK3588**（用户已有该规划），
FPGA 侧只接收"下一段路径点"——这也符合 5.5 的预留设计。

### 5.9 遥控器控制与模式仲裁

> **原文**：10. 遥控器控制。遥控器有两个摇杆（分别控制前后、左右）以及若干按钮和开关。当模式开关选择接管车辆控制时，通过遥控器直接控制车辆行走以及转向，原先正在执行的任务暂停；当模式开关选择控制屏幕光标时，摇杆控制屏幕光标移动，按钮来确认/返回，来选择特定的自动化功能和任务或展示数据面板。已完成遥控器数据接收模块。

**硬件**：J6 六路信号（CH1 D19 / CH2 E19 / CH3 E18 / CH4 F18 / CH5 F20 / CH6 F19），电源从 J9 取。

> ⚠️ **说明**：用户提到"遥控器数据接收模块已完成"，但**在模块库与 `car_fpga` 中均未找到独立
> 遥控模块**。模块库里有的是 `rc_pwm_receiver` 包（单路捕获 `rc_pwm_capture` + 两路封装 `rc_receiver`）。

> ★ **2026-10-16 实现说明（需求方口径，实现侧已据此完成，与本节下文冲突处以本段为准）**：
> 遥控器**实际用到的输入只有 5 个** —— 两个摇杆（前后 / 左右）、两个按钮（**确认 / select**）、
> 一个拨杆开关（模式选择）；**全部都是 PWM 通道**（需求方明确"遥控器所有输入都是 pwm"，
> 不存在 GPIO 电平型的开关）。**没有独立的"返回"按钮** —— 本节引用原文里"按钮来确认/返回"
> 应理解为"确认键 + select 键"，而"**返回**"是路径点导航页**辅助菜单里的一项**
> （用 select 键切换、确认键执行，见下文路径点导航小节）。
> 实现落在 **`rtl\rc\rc_input.v`**（**不是新建 `rc_rx`**，模块名 `rc_rx` 在本工程中不存在）：
> 把库内**单路** `rc_pwm_capture` 实例化 6 份，第 3 路保留为**预留未接**（即上表 CH4/F18 位置）。

**实现 `rtl\rc\rc_input.v` 的接口**（库内单路捕获 × 6 + 参数化通道映射）：

| 项 | 实现 |
| --- | --- |
| 输入 | `rc_pwm[5:0]`（各通道 PWM 脉宽，典型 1000~2000 µs，周期 20 ms；PPM/SBUS 需另做解码） |
| 模拟量输出 | `o_steer` / `o_throttle`（signed 12 位，−1000…+1000，中位 0，带 ±25 µs 死区） |
| 开关 / 按钮 | `o_mode[1:0]`（**两档**）、`o_btn_confirm` / `o_btn_select`（单周期脉冲） |
| 菜单拨动 | `o_menu_up` / `o_menu_down`（摇杆拨到位产生一次；**必须回中后**才能再触发） |
| 通道映射 | `CH_*` 参数（换接线只改参数）：0 转向 / 1 油门 / 2 确认 / **3 预留未接** / 4 模式 / 5 select |
| 信号有效 | `o_signal_valid`：**只看参与判定的通道**（`SIG_VALID_MASK`）—— 预留未接的通道不会把整车使能拖死 |
| 安全 | 单路超时阈值 100 ms（依据 L4 的"200 ms 内停车"判据留一半余量）；无效/超时按中位处理 → 模式退回"屏幕光标"档 |

**模式仲裁**（用户 2026-10-16 明确的语义，两条要求直接落成状态）：

```
拨杆开关（一个 PWM 通道，脉宽 <1300 µs = 接管档）→ 模式（**两档**，"自动"档已删除）：
  ├ 模式 A：手动接管 —— 手柄【只】遥控车辆：摇杆 → 转向/油门；
  │          不做任何屏幕交互（不切页、不切菜单）；自动任务【暂停并保持状态】
  └ 模式 B：屏幕光标 —— 手柄【不】控制车辆（转向/油门强制为 0，底盘不受摇杆影响）：
             摇杆 → 菜单高亮（浏览态）/ 准心（导航设置态）
             确认键 → 进入所选页面 / 确认路径点
             select 键 → 导航页辅助菜单换项
             （摇杆上下切换菜单项；进入导航设置后菜单变暗、摇杆改为
               **移动准心、地图不动** —— 见"路径点导航"小节 2026-10-16 的改动）
```

- ★ **模式 A 下"确认键也不切页"**：需求方明确"接管档手柄不做遥控车辆之外的任何交互"，
  所以摇杆拨动与确认键都限定在模式 B（实现见 `falcons_top.v` 的 `cursor_mode &&` 门控）；
- **"原先正在执行的任务暂停"** 的语义要先定死：**暂停 = 保持当前路径点与已走里程，恢复后继续**（不是清除）；
- 模式切换必须**无扰**：切换瞬间 `v_cmd` 限斜率，避免阶跃造成打滑/窜车；
- 仲裁优先级与 5.2 的仲裁表一致：**安全 > 遥控 > 自动**。

## 六、屏幕 UI 与交互设计

> 本节第一~四小节为**原始需求**（保留），其后是实现补充。

**总体布局**：左侧占屏幕约 **1/5~1/6 宽度**为菜单列表，菜单项：摄像头画面 / 雷达建图展示 / 车身运行数据显示 / 路径点导航。
摇杆上下拨动切换选项。**初始化默认选中"摄像头画面"并确认**。

（按 1024 px 宽算，菜单栏 ≈ 170~205 px；建议 **200 px**，右侧内容区 824 px。）

### 摄像头画面

选中并确认时，菜单右侧全部画面实时显示摄像头采集的画面。该页面不做交互设计，不占用摇杆功能，使用摇杆仍可上下切换菜单选项。

> 实现：DDR3 帧缓存（1024×600 RGB565）→ 裁剪/缩放到 824×600 → 合成；菜单栏叠加在最左 200 px。

### 雷达建图展示

选中该项时，菜单右侧全部画面实时显示雷达的2D建图画面，以及在页面右下角显示车辆方向和航位。该页面不做交互设计，不占用摇杆功能，使用摇杆仍可上下切换菜单选项。

> 实现：复用 `m10_point_cloud_core` 的 512×512 位图（0° 向上、顺时针），居中放在内容区，右下角叠加"车辆箭头 + x/y/yaw"文字；缩放键继续沿用 S1/S2（或映射到遥控按钮）。

### 车身运行数据显示

选中该项时，菜单右侧画面中心为一辆小车俯视示意图，小车前端（即画面上方）实时显示车辆朝向，即航向角，四个轮子旁实时显示每个轮子编码器读数，以及右侧单独竖向排列显示车辆角速度、中心速度、航位等信息。该页面不做交互设计，不占用摇杆功能，使用摇杆仍可上下切换菜单选项。

> 实现：图标 + 文字层。数据来自 `odom`（x/y/yaw/v/ω）与 `motor_top`（4 路 `o_count`/`o_delta`）。
> 刷新只要"变化时重绘"，避免每帧全屏重画。建议数值字体用 8×16 ASCII，单位写清（mm、mm/s、°）。

### 路径点导航

选中该项时，菜单右侧画面实时显示雷达的2D画面建图（地图）。点击确认键进入路径点导航设置状态（但菜单栏不消失，而是变暗。画面整体布局不变，此时摇杆不可再操作菜单，需在后续辅助菜单中选择返回并确认后才返回上一级），此时地图的中央出现一个准心，地图右侧浮空显示一个辅助菜单（包含"确认路径点"、"撤销路径点"、"开始导航"、"返回"、"清除所有路径点"，初始默认选中"确认路径点"，按手柄上的select键依次切换）。通过遥控器摇杆控制**准心上下左右移动，地图不动**，以实现准心与地图相对运动，来选择路径点位置。将准心移动到目标位置后，点按遥控器的确认键确认该路径点，随后地图上该位置出现一个圆点标志，随后继续下一个路径点的设置。直至所有路径点设置完毕，点击select键选中"开始导航"，结束路径点选择状态并开始导航任务，任务执行过程中，"开始导航"选项变为"暂停任务"，选中并确认时，停止导航任务。

> ★ **2026-10-16 需求原文已更新（本节此前的复述已按新版同步）**：选点方式由原来的
> "通过遥控器摇杆控制**地图**上下左右移动、**准心仍处于地图的画面中心**"
> 改为"通过遥控器摇杆控制**准心**上下左右移动、**地图不动**"。
> 因此下表中旧的"地图平移 / 维护视口原点 `(ox, oy)`"实现思路**作废**，见修订后的两行。
> （本节引用原文的其余部分与"返回是辅助菜单项而非独立按键"这一点未变。）

> **实现补充**：
> | 项 | 设计 |
> | --- | --- |
> | 状态机 | `BROWSE`（摇杆切菜单）→ `NAV_SETUP`（菜单变暗、摇杆改为**准心输入**、辅助菜单高亮）→ `NAV_SETUP_MENU`（select 切项 + 确认执行）→ `NAV_RUN`（显示"暂停任务"）→ `BROWSE` |
> | **准心移动**（2026-10-16 改） | 维护**准心的屏幕坐标 `(cx, cy)`**；摇杆（前后/左右两路）改变它，**地图与视口都不动**。路径点存的是"地图坐标 = 准心屏幕坐标经一次固定映射换算"，因此**不需要视口原点**，比旧方案少一个状态量 |
> | 摇杆归属 | 进入 `NAV_SETUP` 后摇杆**不可再操作菜单**；而按模式仲裁，摇杆只有在**屏幕光标档**才归 UI —— 所以导航设置态在接管档下无法操作摇杆（接管档摇杆一律给底盘） |
> | 路径点存储 | 上限建议 **8~16 个**（BSRAM 存 `x,y` 各 16 位足够），带序号显示（①②③…） |
> | 圆点/准心 | 位图叠加：圆形模板（半径 4~6 px）与十字准心，直接比较 `pixel_x/y` 与目标点距离 |
> | 辅助菜单 5 项 | 高亮用反色；"开始导航"↔"暂停任务"同一项切换文字（两套字模） |
> | 确认/撤销 | 撤销 = 删除最后一个路径点；清除所有 = 清空数组（需二次确认，防误触） |
> | 菜单变暗 | 菜单栏图层整体乘以 0.5（`rgb >> 1`），实现成本极低 |

## 七、接口与编码约定（新增部分）

沿用 `car_fpga/doc/模块划分与接口规范.md`：单时钟域、`i_*`/`o_*` 命名、模式 A（寄存器直出 + 单周期 valid）、
对外物理量整数、顶层只连线。**新增模块统一遵守以下打包约定**：

```verilog
// 控制/估计/传感（sys_clk 50 MHz）
module chassis_ctrl #( parameter CLK_FREQ_HZ = 50_000_000 ) (
    input  wire        i_clock, i_reset_n,
    input  wire signed [31:0] i_v_cmd,        // mm/s
    input  wire signed [31:0] i_omega_cmd,    // 0.01°/s
    input  wire signed [31:0] i_yaw,          // 0.01°
    input  wire        i_run_enable,
    output wire signed [31:0] o_sp_a, o_sp_b, o_sp_c, o_sp_d  // 计数/窗口
);
// 显示/交互（pixel_clk 49 MHz）—— 端口名里显式标注域
module ui_compositor (
    input  wire        i_pixel_clk,           // 49 MHz，本模块唯一时钟
    input  wire        i_pixel_reset_n,
    input  wire [11:0] i_pixel_x, i_pixel_y,
    input  wire        i_pixel_req,
    output wire [23:0] o_rgb888
);
```

**跨域接口**（sys → pixel）：参数用"锁存 + 握手脉冲"，**禁止**直接跨域连线多比特总线。

| 2 | **A15 定义冲突**：手册 J2.6 = IMU `CS`，模块库雷达例程 `acg720_m10_hdmi.cst` = 雷达 RX | 同挂一条网络会**对打**（J1 与 J2 同网络），可能损坏 IO 或表现为 IMU/雷达随机失效 | 按手册改接 **C14**（J3.3）；例程只需改一行 `IO_LOC`，端口名 `i_radar_rx` 与 RTL 不变。飞线到 A15 的接法**只适用于不装 IMU** 的场合 |
| 3 | **时序余量**（IMU 工程仅 2.2%） | 集成后可能违例 | 集成即重跑时序；必要时流水化 |

| 9 | **雷达 460800 与调试 115200** 共用 M15 | 不能同时输出两种波特率 | 雷达原始字节镜像只在调试时开；正式运行关闭 |
| 10 | 排线 Pin1 镜像、J1 与 Jx 二选一 | 上板全错且综合查不出 | 接线上电前逐针核对；写进接线纪律 |

| 12 | 全局规划（A*）资源与迭代次数 | 可能做不动 | 先做路径点跟踪 + 局部绕障；全局规划优先交 RK3588 |
| 13 | **`m10_radar` 封装版未获新的实板复验**（仅原独立工程的接收+显示被确认过） | 雷达页集成时可能需现场调试 | 先单独跑通模块库示例（读取 + 点云显示），再进整屏 UI 集成 |
| 14 | **`imu_top` 的 `SCK_HALF_DIV` 默认 3（8.33 MHz）实测会导致初始化失败** | 表现为 `o_err_code=2`（配置校验失败），极易误判成"模块坏了" | 例化时显式传 `25`（1 MHz）；提速按 1→2→4 MHz 逐步试并每次确认 `o_init_done` |
| 15 | **第三方代码许可**：`disp_driver.v`/`camera_init.v`/`i2c_*`/`DVP_Capture` 为外部参考代码（无明确开源许可），`dvi_tx.v`/`display_pll.v` 为 Gowin 加密 IP | 影响可分发性与移植 | 项目内使用可接受；对外发布前核对 `THIRD_PARTY_NOTICES.md` |

## 十二、一句话总结

底盘（IMU→yaw、四路速度闭环、电机与编码器）与两块显示外设（HDMI、雷达点云）**已经是现成模块且上板验证过**；
本车后续的主要工作量集中在 **①航位推算与滑移标定、②屏幕 UI 合成与字库、③ToF 急停、④遥控接管仲裁、⑤路径点导航**这五块新建模块上，
而**最先要解决的不是代码，是供电实测、DDR3 确认和"雷达接 C14"这三个硬件前提**。
