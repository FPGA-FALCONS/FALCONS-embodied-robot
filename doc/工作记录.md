## 一、阶段一：工程骨架与依赖锁定

**做了什么**

1. `git init`（分支 `main`）+ `.gitattributes` / `.gitignore`（行尾策略随仓库走，不依赖各机器 `core.autocrlf`）。
2. **全量内嵌模块库快照**：`git archive --format=tar HEAD` 导出到 `vendor\verilog-reusable-modules\`
   —— 10 个包 / **144 文件** / 2.8 MB，无 `.git`、无 `sim\work` 这类未跟踪产物。
   （没用资源管理器拖拽：那会把 `work\`、`transcript`、`*.qdb` 一起搬进来。）
3. 生成记账：`VENDOR.lock`（源 URL + commit + tree SHA256 + 包清单）、
   `deps\vendor_manifest.sha256`（144 行逐文件哈希）、`deps\modules.list`（工程实际引用的包）。
4. 工具脚本：`tools\lib_paths.ps1`（所有路径的唯一定义处）、`sync_vendor.ps1`、`check_vendor.ps1`、
   `run_all_modules.ps1`、`build.ps1`；Tcl 侧 `scripts\vendor_sources.tcl`（从 `modules.list` 派生源文件）。

**为什么内嵌而不是 submodule**：方案文档 `class\模块库内嵌方案_反馈.md` 的结论 —— 库还在频繁更新时，
每次升级 pin 都要重新验证，日常成本高；内嵌可以将来平滑升级为 submodule（挂载点不变）。

**验证**：`check_vendor` 逐文件比对一致；`run_all_modules` 跑库自带测试
**PASS 11 / COMPILE-ONLY 1 / FAIL 0**；`build.ps1` 在缺顶层时给出人话报错而不是让综合器报天书。

**脚本自身修掉的两个缺陷**：`check_vendor` 里"144 项逐一比对"是**硬编码**（快照变 145 文件时数字对不上）；
BREAKING 提示用了 `[BAD]` 红色（让人误以为体检失败，实际只是提示）→ 改 `[WARN]`。

## 三、阶段三：参数确认与运动学换算

用户给定：轮半径 19.9 mm（轮宽 26 mm）、左右轮中心间距（轮距 L）158.6 mm、前后轮圆心间距（轴距）170 mm、
减速比 30、屏幕 1024×600 中文界面、HDMI 到显示器、RK3588 走串口、ToF 未做出先留空。

**★ 编码器线数判定（用已有实测数据反推）**：实测手转车轮一圈 ≈ 61657 计数（4 倍频后）

| 假设 | 理论计数/车轮转 | 与实测偏差 |
| --- | --- | --- |
| 500 PPR | 60000 | 2.76% |
| **512 PPR** | **61440** | **0.35%** ✅ |

→ 判定 **512 线**。连带发现：`car_fpga` 里 "rpm = delta/10" 隐含 60000 计数/转的假设，
按 512 线应为 `rpm = delta/10.24`（**2.4% 系统偏差**），本工程统一用 10.24。

**由参数算出的运动学常量**（全部写进 `chassis_ctrl` 的参数）：
轮周长 125.0354 mm、每计数 2.035 µm、1 rpm = 10.24 计数/10ms、
差速系数 0.66415 rpm/(deg/s) → 定标为 `DIFF_K_Q10 = 627`、`CENTER_K_Q10 = 3146`。

> ★ **2026-10-19 注（保留历史，不改原文）**：上面第一行的三个量是按当时假设的轮径算的
> （C = 125.0354 mm ⇒ R = 19.9 mm）；2026-10-18 实测轮径 64 mm（C = 201.0619 mm）后已不成立，
> 偏差约 38%。**现行值见 `参数总表与待定清单.md` 第二节**，订正过程见 §56.4。
> **但第二行的两个系数结论仍然成立** —— `CENTER_K_Q10` / `DIFF_K_Q10` 标定的是
> 「摇杆量 → counts/窗口」，与轮径无关，所以轮径改了也不用重算。
> 真正被轮径影响的是「counts → 毫米」这一步，那由 `odom.DS_K_Q10` 承担。

### 遥控的实现程度（本次盘点，2026-10-15）

**已实现**（`rtl\rc\rc_input.v` + `falcons_top` 接线；仿真 12 项 PASS、综合通过）：

| 能力 | 实现 |
| --- | --- |
| 6 路 PWM 捕获 | 库内**单路** `rc_pwm_capture` 实例化 ×6；合法脉宽 900–2100 µs，单路超时 100 ms |
| 两路模拟量 | 转向 / 油门 → **±1000**；中位 1500 µs、半量程 500 µs、**死区 ±25 µs** |
| 模式开关三档 | <1300 µs → 手动接管；1300–1700 → 屏幕光标；>1700 → 自动 |
| 三个按钮 | select / 确认 / 返回：位置 2 的**上升沿** → 单周期脉冲 |
| 丢信号保护 | 任一路超时 → 摇杆输出**立即归零** + 状态栏"无信号" + LED3 灭 |

**仿真验证**（`rc_input_tb` 12 项）：中位 → 0；端点 2000/1000 → +1000/−1000；死区 1520/1480 → 0；
模式 1200 → 手动(0)、1800 → 自动(2)；select 拨高 → **恰好 1 个脉冲**；停发 6 ms → 信号无效、恢复刷新 → 有效。

**未做 / 待确认（8 项）**：

1. **光标模式的界面交互完全没做** —— 功能设计文档 §5.4 要求的"摇杆移地图、准心居中、辅助菜单 5 项、主菜单变暗"依赖导航页（L5）；当前 select/确认只用于**切页**
2. **自动档无实际功能** —— 顶层把 `i_auto_valid` 恒接 0，自动档底盘不动（有意留白，等导航/避障接入）
3. **通道角色映射是"假设"的** —— 按功能设计文档 §6.10 的语义假设（转向/油门/确认/返回/模式/select），
   **必须按实际接线核对**；错了只改参数、不动逻辑
4. **接收机型号与输出形式仍待确认**（Q3）—— 若是 **PPM / SBUS**（单线串行）而不是每路独立 PWM，前端必须重写
5. **模式开关物理形态未定**（P11）—— 现按"PWM 通道脉宽三档"判定；若实际是独立拨杆开关（GPIO 电平），改 GPIO 更直接
6. **无遥控标定流程** —— 中位/端点/死区都是写死参数，没做"打杆记端点"的自动校准
7. **无摇杆曲线 / 限速** —— 没做 expo 曲线，最大速度只受 `chassis_ctrl.MAX_DELTA` 限制
8. **丢信号是"归零滑行"而非主动刹车** —— 检测阈值 100 ms，设计文档 L4 判据是"200 ms 内停车"；
   实际响应 = 100 ms 检测 + PID 收敛时间，**未实测**

**上板要验的 5 条**：① 每个通道实际是什么（看状态栏与 LED5:4）；② 中位是否正好 1500 µs；
③ 打满杆能否到 ±1000（否则改 `HALF_RANGE_US`）；④ 关接收机电源后的停车响应时间；⑤ 按住按钮是否只触发一次。

**两条关键设计决策**：

1. **提前 2 拍取模**：字符索引与点阵行各有 1 拍 ROM 延迟，扫描不等人。
   做法是"始终请求 (x+2) 所在的字组"——数据 2 拍后有效时 x 已推进到 x+2，仍落在同一字组内。
   这样**不需要行缓冲、不需要消隐期预取**，逻辑简单且无撕裂。
2. **布局强制 16 对齐**：所有文本起点 x 与 y 都是 16 的倍数 → 每个汉字恰好落在一个 16 px 字组内，
   取模退化成"字组号 + 格内位 + 行号"三件事，不需要任何除法。

## 六、阶段六：约束、首次综合与时序优化

**约束**：`constr\falcons.cst` 逐针抄自硬件手册（电机/编码器 21 根沿用 `car_fpga` 已复核的值，
板载时钟/按键/串口/LED 按手册 §2.3，遥控取 J6 整排，雷达 **C14**，ToF/RK3588 占 J7）；
`falcons.sdc` 只约束 50 MHz 外部时钟（`.cst` 与 `.sdc` 必须成对给，否则工具按默认 100 MHz 估算，
会报假违规）。

**首次综合**：ERROR 0，但时序 **SETUP 违规 25 条，最差 −7.023 ns**。逐步优化（每步都重新综合实测）：

| 步 | 措施 | 结果 |
| --- | --- | --- |
| 1 | 遥控归一化改**移位加法**（×2.125 代替通用乘法）；`chassis_ctrl` 指令乘法**插一级流水** | SETUP 最差 −7.023 → **−2.589** |
| 2 | 差速/限幅链**再插一级流水**（切断"中心速度→限幅→差速→PID 输入"） | → **−0.616**（仅 1 条） |
| 3 | 像素域复位改**域内自产**（等 PLL 锁 + 计数释放），不再把 `sys_rst_n` 引到 pixel 域复位端 | → **−1.412**（1 条，且消除了复位链那条） |
| 4 | 加 UI 实时数值（跨域字符 RAM）后 | 7 条，最差 **−0.353** |
| 5 | 接入 IMU 链路后 | 1 条，最差 **−2.003** |

**关于"为什么不用 SDC 声明异步"**（重要，避免后人重复踩）：我**先试了正解** ——
在 `.sdc` 里写 `set_false_path -to [get_clocks {pixel_clk}]`，但 `pixel_clk` 是 `hdmi_1024x600`
内部 PLL 的派生时钟，**约束解析阶段还不是时钟对象**，直接
`ERROR (TA2004): Cannot get clock with name 'pixel_clk'` 导致综合失败 → 撤回，改为用 RTL 手段消除。

**当前剩余违规的性质**：SETUP 1 条 + HOLD 9 条，路径两端分别是同一信号在两个时钟域的采样
（状态位同步器第一级、遥控异步输入采样、动态字符 RAM 的跨域读）。这是 CDC 的结构性现象，
不构成功能风险 —— 判据在 `doc\上板指南_v1.md` 第六节列了每条路径的源/目的。

**真实逻辑路径**（非 CDC）最差 slack 只有 **+0.105 ns**，落在 `speed_pid` 内部。
这与 `car_fpga` 的 `imu_demo` 工程 Fmax 只有 51.11 MHz（余量 2.2%）是同一现象 —— 属模块自身特性，
要改**只能改 vendor 里的模块**（当时的铁律是"先在源库提交再同步"；2026-10-15 起改为 vendor 直接维护，见第十三节）。

## 七、阶段七：UI 实时数值

按功能设计文档 §5.3，车身数据页应显示四轮读数与中心速度。实现分三件：

- `num_text.v`：7 个字段 × 4 字符（符号 + 3 位数字，前导写空格），100 ms 刷一轮
- `dyn_text_ram.v`：sys 域写、pixel 域读的简单双口 BSRAM
- `ui_render.v` 从"一行一项"扩展为"**最多 6 个文本段**"，静态文案与动态数值可混排；
  数值用亮绿 `7CFC98` 与白色标签区分

| 坑 | 现象与处理 |
| --- | --- |
| **数组字面量里拼换行会丢行** | `@( @('a','b'), @('c', 'x' + "`n" + 'y') )` 里第二行会丢 —— 本会话被这个坑咬了 **4 次**（生成器脚本、tb 检查项、tb 统计块）。**改用 here-string** |

### C. Verilog / RTL

| 坑 | 现象与处理 |
| --- | --- |
| **`localparam` 不能在 module 外声明** | `include` 一个只有 `localparam` 的 `.vh` 放在 module 之前 → 解析失败、后续变量全"未定义"。**include 必须在 module 体内** |

## 十三、架构变更：vendor 转为本项目直接维护（2026-10-15）

**变什么**：原先 `vendor/` 是"上游只读引用 + 本地 patch"，改为**本项目直接维护**——源码进本仓库、可自由修改，但每次改完必须跑全量仿真回归。

**为什么**：上游模块（HDMI / 摄像头 / 遥控 / IMU）都要按本项目改时序和接口，patch 方式维护成本高于收益。

**保留的纪律**：改 `vendor/**` 下任何模块后，**必须**跑 `sim\run_sim.ps1` 全量回归，并在 `vendor\ORIGIN.md` 记上游版本与改动清单。

### 21.4 措施 13：Setup "违规端点"口径的彻底查清（★ 本节最有价值的方法论）

**问题**：报告说 `Setup Violated Endpoints = 4`，但 Setup 路径表 25 条**全为正 slack**（最小 +0.032）。这 4 个端点是谁？

**结论**：这 4 个端点是 **HDMI DVI 发送端 4 个 `OSER10` 原语的异步复位脚**，由 **245 MHz `CLKOUT1` 的下降沿**捕获：

```
u_hdmi/u_dvi_tx/rgb2dvi_inst/u_OSER10_clk/RESET
u_hdmi/u_dvi_tx/rgb2dvi_inst/u_OSER10_b/RESET
u_hdmi/u_dvi_tx/rgb2dvi_inst/u_OSER10_r/RESET
u_hdmi/u_dvi_tx/rgb2dvi_inst/u_OSER10_g/RESET
```

**推理闭合（排他性）**：违规端点必有 slack < 0；若属上升沿集合，必在"全局最差 25 条"里；那 25 条最小 slack 是 +0.032 > 0 → 不在上升沿集合 → 只能在下降沿集合；而 `Falling Endpoints = 4` 恰好 4 个 → 就是这 4 个 OSER10 RESET。∎

**四条独立证据**：① 全文 `[F]` 只出现 8 次，全是 `CLKOUT1:[F]`；② Setup 表 25 条无一个 `[F]`（跨沿检查不在该表）；③ 两次独立布局布线统计**逐项相同**；④ 这 4 个同时是 RECOVERY 8 条的捕获端。

**★ 21.5 独立复布实验（本轮新增方法论）**：`tools\sta_timing_probe.tcl` 用 `set_option -output_base_name falcons_sta` 把报告落到新文件名，**一个字节都不动 `falcons.*`**。两次独立布线（20:51 / 21:18）统计逐项相同 → **Gowin 在本设计上的 PnR 是确定性的**，"重跑一次看数字变不变"没有信息量。

**★ 21.6 工具限制（别再重复踩）**：`report_timing` / `get_pins` / `report_clocks` **不是 `gw_sh` 的 tcl 命令**（`info commands` 实测只有 `report_property`）。报告里那句 `Report Command: report_timing -setup -max_paths 25` 是 **PnR 引擎内部调用**。`set_option -help` 约 130 项，**没有任何一项能扩大 PnR 路径表的 25 条上限**。
⚠ **后续更正（2026-10-21）**：`report_timing` 在 **SDC 文件里**是可用的（官方 SUG940 有），只是不能在 `gw_sh` 交互命令行敲。

**21.7 要不要紧**：**不要紧**。`pixel_pwr_cnt` 是复位释放计数器，只在**上电复位那一次**变化；OSER10 的 `RESET` 是异步复位，语义是"复位何时释放"。物理含义是"复位比理想时刻晚几个 245 MHz 周期"，功能无害。想彻底清零只能改 vendor 的 `hdmi_1024x600` / `rgb2dvi` 内部，或加时序例外——两者都不动（加 false path 等于掩盖问题）。

### 60.1 两条修法（RTL 已改）

**① `rtl\motor\speed_pid.v`：给误差与反馈有效各打一拍。**

原先 `err_lim` 由 `i_fb` 组合算出后**当拍**直接进三条乘法，
`delta_r → o_u` 是一条 20.82 ns 的单周期组合链。改法是把误差锁进寄存器，
乘法改用锁存值，代价是 `o_u` 晚一拍：

```verilog
reg signed [15:0] err_lim_r;
reg               fb_valid_d1;
always @(posedge i_clock or negedge i_reset_n) begin
    if (!i_reset_n)      begin err_lim_r <= 16'sd0; fb_valid_d1 <= 1'b0; end
    else if (!i_enable)  begin err_lim_r <= 16'sd0; fb_valid_d1 <= 1'b0; end
    else                 begin err_lim_r <= err_lim; fb_valid_d1 <= i_fb_valid; end
end
wire signed [16:0] d1 = err_lim_r - e1;
wire signed [17:0] d2 = err_lim_r - (e1 <<< 1) + e2;
wire signed [39:0] du_sum = (i_kp * d1) + (i_ki * err_lim_r) + (i_kd * d2);
```

`o_u` 的更新条件从 `end else if (i_fb_valid)` 改成 `end else if (fb_valid_d1)`，
`o_err` / `e1` 也改用 `err_lim_r`。

★ `fb_valid_d1` 是**必需的数据配对条件**，不是随手加的：
`i_fb_valid` 是 1 kHz 的单拍脉冲，而 `err_lim_r` 要下一拍才拿到本帧误差。
若仍用 `i_fb_valid` 作更新条件，就会在"新使能 + 旧误差"那一拍输出一次错值。

**② `rtl\top\falcons_top.v`：gyro 补偿值流水一级（不动 vendor 的 `gyro_tilt_comp`）。**

```verilog
reg signed [31:0] gyro_z_comp_r;
reg               imu_data_valid_d1;
always @(posedge i_clk_50m or negedge sys_rst_n) begin
    if (!sys_rst_n) begin gyro_z_comp_r <= 32'sd0; imu_data_valid_d1 <= 1'b0; end
    else begin gyro_z_comp_r <= gyro_z_comp; imu_data_valid_d1 <= imu_data_valid; end
end
// u_yaw: .i_gyro_z(gyro_z_comp_r), .i_sample_valid(imu_data_valid_d1)
```

★ **`i_gyro_z` 与 `i_sample_valid` 必须同步延后**。只延后数据不延后使能，
`u_yaw` 会在"本帧使能 + 上一帧补偿值"那一拍采样 —— 引入的偏差比时序违约更糟。
已确认 `imu_data_valid` 只被 `u_yaw` 消费；`gyro_z_comp` 另有一处给 `gyro_deg_s` 显示用，
差 20 ns 无影响。

### 60.4 上板反馈的两个 bug 与修法

#### 60.4.1 两个三档开关的上下方向都反了

现象（需求方原话）："两个三档开关的上下方向反了"。
即 CH5 下拨执行了"返回"、上拨执行了"确认"；CH8 上拨执行了"向下切"、下拨执行了"向上切"。

修法：**只改 `falcons_top.v` 里 `u_rc` 例化的两个极性参数，不动 `rc_input.v` 的译码逻辑**。

| 参数 | 改前 | 改后 |
| --- | --- | --- |
| `CONFIRM_ACTIVE_LOW` | `1` | **`0`** |
| `AUX_SWAP` | `0` | **`1`** |
| `MODE_REVERSE` | `0` | `0`（CH7 两档方向本来就对） |

这条约定要一直保留：**开关方向反了就是翻这两个参数之一，不要动 `classify()`**。
译码逻辑（±30 µs 迟滞 + 2 帧确认）是共用的，翻参数只是换"哪一档算高"。

#### 60.4.2 退出导航交互态后，无法立即再进入

现象（需求方原话）："进入导航页面再推出，然后无法立即再进入导航页面，
必须先进入其他界面才能再进入导航页面。"

**根因**：`nav_free_ctrl.v` 里 `ui_active` 只有一个置位来源 `enter`：

```verilog
wire enter = i_active & ~active_d;      // page 进入本页的上升沿
```

而退出交互态（按返回）只清 `ui_active`、**不改变 page**。于是 `active_d` 一直为 1，
`enter` 再也不会产生 → 只能靠切页制造 `i_active` 下降沿把 `active_d` 清掉，
再切回来时才有新的上升沿。这个"必须先绕一圈"就是 bug 的表现。

**修法**：允许"已在本页、已退出交互态"时按确认重新置位：

```verilog
reg ui_active;
wire reenter = i_active & ~ui_active & i_confirm;
always @(posedge clk or negedge rst_n) begin
    if (!rst_n)                  ui_active <= 1'b0;
    else if (i_clear)            ui_active <= 1'b0;
    else if (!i_active)          ui_active <= 1'b0;
    else if (enter)              ui_active <= 1'b1;
    else if (i_back && (o_nav_state != ST_RUNNING)) ui_active <= 1'b0;
    else if (reenter)            ui_active <= 1'b1;
end
```

★ `wire reenter` 必须声明在 `reg ui_active` **之后** —— 否则 `vlog` 报
`vlog-2730 Undefined variable: 'ui_active'`（第一次改就踩了）。

**配套必须改的一处（否则会引入更严重的新 bug）**：状态机里"按确认 = 执行辅助菜单项"
这一支原本只判 `i_confirm`：

```verilog
end else if (i_confirm && o_nav_ui_active) begin   // 原为 end else if (i_confirm)
```

原因：`reenter` 那一拍 `ui_active` 还是 0，若不加门控，同一次按键会**既重新进入交互态、
又被当成"开始导航"**。此刻点表非空且高亮在「间断寻点」时就直接开跑了 —— 这正是
"退出后重进"最常见的那条路径。

门控用 `o_nav_ui_active`（`ui_active` 的**旧值**）而不是 `ui_active | reenter`，
就是为了让"进入交互态的那一拍"不执行任何菜单项。用户要操作必须再拨一次确认，
符合"先进入、再操作"的直觉。

**重进后的状态**：`PAUSED` 时按返回会 `state <= ST_SETUP`（§59.4 的状态机），
所以重进一律回到 `SETUP`，状态栏不显示"导航暂停"，与"返回菜单选择 = 退出交互"的
需求语义一致。

★ **`reenter` 不重置点表与辅助菜单高亮，`enter` 才重置**（`enter` 分支会
`pt_v <= 0`、`o_aux_sel <= AUX_SET`）。这是刻意的：返回退出只是"解锁菜单"，
不是"重开页面"，所以重新进来时点表和上次选中的菜单项都还在 —— 这正是 §60.8 第 4 条
要验的那个组合（重进后高亮仍在「间断寻点」、点表非空，第一下确认不能开跑）。

### 60.5 本轮仿真

`sim\nav_free_tb.v` 新增 7 项断言（12.1 / 12.2 两组）：

- `reenter_pre_ui` / `reenter_pre_state`：退出后确实处于 `ui_active=0` / `SETUP`。
- `reenter_ui` / `reenter_state` / `reenter_not_run`：按确认后 `ui_active=1`、
  状态仍是 `SETUP`、**没有误开跑**。★ 这一组特意在"点表有 1 个点 + 高亮间断寻点"
  的条件下做 —— 这是最容易被误启动的组合。
- `reenter_then_run` / `reenter_mode_gap`：再按一次确认能正常开跑，证明没有把功能改死。

回归：**11 台 / 405 项全 PASS**（`nav_free` 60 → **67**）。

| 时点 | Setup 同域 50 MHz | 最差 slack | Setup 同域 HDMI | 最差 slack |

**三条结论：**

1. **16 条全是同一个加法器的不同位**，不是 16 个问题：
   `u_imu/rx_buf[9]_5_s0/Q → u_imu/calib_sum_{x,y,z}_*_s4/D`。

2. **条数在 1 / 10 / 16 之间跳，根因是布局，不是逻辑**：17:22 → 17:35 这批改动
   只多了 1 行 `wire reenter` + 两个参数从 `1/0` 改成 `0/1`，逻辑量几乎为零；
   而跳动的三条路径**全部落在两个一行没改的 vendor IP**（`u_imu`、`u_hdmi`）上。
   报告只列最差 25 条，别处的 slack 一变，这棵子树的位就挤进榜或挤出榜 ——
   所以"条数"在这里是**可见性**指标，不是**严重度**指标。真正的严重度看最差值：
   三次分别是 −0.992 / −1.494 / −1.258，量级一直没离开 1 ns 出头。
3. **应用层（`nav_free` / `navpt_*` / `navc_*` / `ui_render` / `odom` / `chassis` /
   `num_text`）在 17:22 之后没有一条进榜**。§59.9 点出的 `u_tilt` / `u_yaw` 两条
   已经修掉、不再出现。

**不能说"已通过时序"。** 准确说法是：应用层两条已修完，剩下的违约全部落在

- DDR3 跨域 3 条：`fclkdiv/CLKOUT` 未 `create_clock`（`TA1132`），
  属历史既有的**假违约**，`constr\falcons.sdc` 已记。
- 若换慢批次器件或长期高温（>70 ℃）运行，这棵子树仍是第一个会出问题的地方；
  表现为**开机标定零点轻微漂移**（航向不受影响，航向用陀螺、不用加速度计）。

### 61.3 暂停必须"真停车"（`nav_ctrl` 侧的坑）

`rtl\ui\nav_free_ctrl.v:345-346` 是
```verilog
assign o_nav_run    = (o_nav_state == ST_RUNNING);
assign o_nav_paused = (o_nav_state == ST_PAUSED);
```
⇒ **暂停时 `i_run` 也是 0**。若 `nav_ctrl` 用 `if (!i_run || !i_active)` 退出，
暂停会被当成"退出"→ `o_auto_valid=0` → 底盘断驱动、靠惯性滑行，不是"停住"。
正确写法是主动给零目标让速度环把轮速拉回 0：

```verilog
if (!i_active || (!i_run && !i_paused)) begin ... 清全部状态 ... end
else if (i_paused) begin
    o_auto_valid <= 1'b1;          // ★ 保持使能
    o_center     <= 32'sd0;        // ★ 目标给 0
    o_diff       <= 32'sd0;
    mst          <= M_IDLE;        // 不改 o_state，恢复后从原状态继续
```
另外 `S_TRACK` 回退 `S_ALIGN` 的那一拍**不许再给前进速度**（原来先判
`psi_abs > ALIGN_OUT_DEG` 置 `S_ALIGN`，却仍执行 `o_center <= v_cnt`，
等于"该转却在冲"，300 mm/s 下多走 3 mm）。

### 61.4 顺带修掉一个功能 bug：`i_acc` 从来没累加过

`i_acc` 全部 5 处赋值都是 `i_acc <= 32'sd0`（复位 + 四处"模式切换清积分"），
**没有任何一处回存**。于是 `i_sum = i_acc + i_inc` 恒等于 `i_inc`，
`KI_YAW` 退化成第二个比例项、积分永远不累积 ⇒ 横向稳态误差 `e_ss = 扰动/Kp` 消不掉。
`doc\导航控制方案.md` 反复强调 `ki_yaw` 是必需品，实际却是死的。

修法（`M_A4` 决策拍、写在 `case` 之前，让模式切换分支的 `i_acc <= 0` 能覆盖它）：
```verilog
if ((o_state == S_ALIGN) || (o_state == S_TRACK)) i_acc <= i_lim;
```
`i_lim` 已是限幅后的新和值，直接回存即累加，自带抗饱和。

   仿真立刻报 4 项失败（`g2_aimed_track: got 1, expect 2` —— 车头已对准却仍卡 `ALIGN`）。
   必须用**本 tick 的新航向**；最终拆拍方案里 `M_Y2` 更新 `yaw_wrap`、`M_Y3` 就用它，天然对齐。
2. **`om_raw = dyaw_win × 100`** 里 `dyaw_win` 是 `i_yaw_centi − yaw_prev` 的组合折返，
   改成 `M_IDLE` 只锁 `dyaw_lat <= dyaw_win`、`M_Y3` 再乘 100。
3. **`diff_pid → o_diff`** 是「×KP → +i_lim → −d_term → 取负 → 两级 clamp → mux」，
   在 `M_A3 && cd_valid`（CORDIC 刚给结果那拍）锁进 `diff_pid_r`，四处 clamp 改用寄存值。
   ★ 不能无条件打拍：那样 `M_A4` 会用上**上一个 tick（10 ms 前）**的 PID 值，控制延迟白白变大。
4. **`v_cnt → o_center`** 是「加 → 移位 → ×K_SLOW → 多级 mux → ×3046 → 移位 → clamp → mux」，
   拆成 `M_V1`（`ahead_mm_r` + ×`K_SLOW_Q10`）→ `M_V2`（`v_ref_r`）→ `M_V3`（×`MMPS_TO_CNT_Q10`）三拍；
   同时**删掉 `clamp32(v_cnt, MAX_CENTER)`** —— 数学上冗余：`v_cnt` 最大 892 counts（300 mm/s），
   远小于 `MAX_CENTER=3072`。

**测量序列因此从 5 拍变成 11 拍**（`M_IDLE → M_Y1 → M_Y2 → M_Y3 → M_A1 → M_A2 → M_V1 → M_V2 → M_V3 → M_A3 → M_A4`）。
代价为零：`i_tick` 是 1 kHz，一个 10 ms 周期有 **500000 拍**，11 拍只占 0.0022%。

### 62.2 极性修复（`rtl\nav\nav_ctrl.v`）

判据是 `rtl\motor\chassis_ctrl.v:148-149`：

```verilog
tgt_left_r  <= clamp_delta(center_r - diff_r);   // 左 = 中心 − 差速
tgt_right_r <= clamp_delta(center_r + diff_r);   // 右 = 中心 + 差速
```

`diff > 0` ⇒ 左轮慢、右轮快 ⇒ `ω = 2·diff/L > 0` ⇒ **左转（CCW）⇒ `yaw` 增大**。
`psi = atan2(left, ahead)`，`psi > 0` 表示目标在左、需左转 ⇒ `diff` 必须为**正**。故：

```verilog
wire signed [31:0] diff_pid = u_pid;      // 原为 -u_pid（错）
```

`d_term` 不用翻：翻转后 `u_pid = p_term + i_lim - d_term`，左转中 `ω > 0` 时 `-d_term` 抑制左转，阻尼方向对。

配套改 `sim\nav_ctrl_tb.v` 三处断言（`g2_right_diff_neg` / `g2_left_diff_pos` / `g2_back_diff_full` 的期望值取反）。

★ 这个错的根源在**方案评审阶段**：`doc\工作记录.md` 五十六节那张表的第 ⑤ 行写了
「`diff > 0` ⇒ 车右转」，与代码相反，后续实现照着错结论写。已在原处加订正指针
（保留原文 + 注明错因），权威表述在 `doc\导航控制方案.md` §八（同日晚已订正）。

### 62.3 IMU 看门狗（`rtl\top\falcons_top.v`，**不改 vendor 快照**）

vendor `imu_top.v:748-750` 的 `S_ERROR` 分支没有任何状态转移：`err_flag_r <= 1'b1;` 之后永久停住，
且 `err_flag_r` 除 `i_reset_n` 外无处清零。下游 `data_valid_r` 永 0 → `u_yaw` 不累加 → 航向角恒 0。

顶层加一个只复位 IMU 的看门狗（参数 `IMU_WD_MS = 500`、`IMU_WD_RST_US = 20`）：

```verilog
reg        imu_local_rst_n;
reg [15:0] imu_wd_ms_div, imu_wd_ms_cnt;
reg [9:0]  imu_wd_us_cnt;

always @(posedge i_clk_50m or negedge sys_rst_n) begin
    if (!sys_rst_n) begin
        imu_local_rst_n <= 1'b1; imu_wd_ms_div <= 0; imu_wd_ms_cnt <= 0; imu_wd_us_cnt <= 0;
    end else if (!imu_local_rst_n) begin                 // 复位保持 20 µs
        if (imu_wd_us_cnt >= (IMU_WD_US_DIV - 1)) begin
            imu_local_rst_n <= 1'b1; imu_wd_us_cnt <= 0; imu_wd_ms_div <= 0; imu_wd_ms_cnt <= 0;
        end else imu_wd_us_cnt <= imu_wd_us_cnt + 10'd1;
    end else if (imu_err_flag) begin                      // 失败计数 500 ms 后硬复位
        ...
        if (imu_wd_ms_cnt >= (IMU_WD_MS - 1)) begin
            imu_wd_ms_cnt <= 0; imu_local_rst_n <= 1'b0; imu_wd_us_cnt <= 0;
        end else imu_wd_ms_cnt <= imu_wd_ms_cnt + 16'd1;
    end else begin
        imu_wd_ms_div <= 0; imu_wd_ms_cnt <= 0; imu_wd_us_cnt <= 0;
    end
end
```

把 `u_imu` 的 `.i_reset_n(sys_rst_n)` 改成 `.i_reset_n(imu_local_rst_n)`。

三个设计要点（改的时候容易踩）：
1. **只复位 IMU，不复位 `u_tilt` / `u_yaw`** —— 否则重连瞬间航向突跳到 0，比故障本身更危险。
2. `else if (!imu_local_rst_n)` 必须排在 `else if (imu_err_flag)` **之前**，否则 20 µs 保持期会被
   还在置位的 `err_flag` 立刻打断。
3. 释放后 `err_flag_r` 已被异步复位清零，看门狗回监视态，**不会无限复位**；反馈链中间有寄存器，
   不是组合环。

`SCK_HALF_DIV=25`（1 MHz）说明这条 SPI 链历史上就因为太快失败过 —— BMI270 是无状态从机，
只要时序对就能读，偶发失败最可能是上电瞬间 IMU 就绪晚于 FPGA 释放复位，500 ms 后重试必然成功。

**② `psi` / `i_lim` 在 M_A3 锁存**

```verilog
reg signed [15:0] psi_r;      // M_A3：CORDIC 角度
reg signed [31:0] i_lim_r;    // M_A3：限幅后的积分新值
```

## §63 三个导航参数调整 + 仿真补参数边界断言（2026-10-20 11:5x）

### 63.1 改了什么
| 参数 | 原值 | 新值 | 位置 |
| --- | --- | --- | --- |
| `ALIGN_IN_DEG` | `3000`（30°） | **`1000`（10°）** | `rtl\nav\nav_ctrl.v:126` |
| `D_SLOW_MM` | `130` | **`100`** | `rtl\nav\nav_ctrl.v:123` + `rtl\top\falcons_top.v:1353` |
| `MAX_DIFF_CRUISE` | `180` | **`252`** | `rtl\nav\nav_ctrl.v:136` + `rtl\top\falcons_top.v:1359` |

`MAX_DIFF_CRUISE = 252` 的换算（轮距 161.5 mm、1 count/10ms = 0.336170 mm/s）：
`60 °/s = 1.047198 rad/s → diff = 1.047198×161.5/2 = 84.561 mm/s → 84.561/0.336170 = 251.54 → 取 252（60.11 °/s）`。
对照：`180` = 42.94 °/s、`250` = 59.63 °/s。

`K_SLOW_Q10 = (V_CRUISE_MMS × 1024) / D_SLOW_MM` 是 localparam，自动从 2363 变 **3072**，不需手改。
同步改了 `NP_MIN_SPACE_MM` 两处注释：原写"= 2·D_SLOW"只在 D_SLOW=130 时成立，现改为"D_SLOW=100 后仍取 260 更保守"。

**三个副作用（改参数时必须知道）**：
① `ALIGN_IN=10°` 让迟滞区间从 5° 扩到 **25°**（`ALIGN_OUT_DEG` 仍 35°）—— TRACK 里偏到 34° 仍"边偏边走"，靠几何闭环拉回；好处是起步方向更准。
② `D_SLOW=100` 让 `v_ref` 减速斜率从 692 升到 **900 mm/s²**（300/100 = 3 /s × 300 mm/s），余量从 1.44 倍降到 **1.11 倍**。底盘实际减速能力约 1900 mm/s² 仍够，但换电机/加负载后可能不足。
③ `MAX_DIFF_CRUISE=252` 使 300 mm/s 时最小转弯半径从 **400 mm** 降到 **286 mm**，代价是直线段更易摆动。若场地出现摆头，第一优先把这个值往回收。

### 63.2 为什么要补断言
改完参数先跑了原 91 项 `nav_ctrl_tb`，全过。但查断言内容发现**没有一条依赖这三个值**：
- `ALIGN_IN_DEG`：G2 只测了"偏 0° 能进 TRACK"和"偏 180° 留 ALIGN"，10°~30° 这个被改变的区间无断言
- `MAX_DIFF_CRUISE`：tb 里只有 `ALIGN` 下的 ±612 满幅断言，TRACK 下的差速幅值无断言
- `D_SLOW_MM`：减速起点在哪无断言

即"91 项全过"只证明没回归，不证明新参数生效。这是**测试盲区与参数解耦**：改参数不会让任何断言失败，等于参数无人看守。

### 63.3 G11 组：14 项参数边界断言（`sim\nav_ctrl_tb.v`，91 → 105 项）
设计原则是**每一项都能区分新旧参数值**，改回旧值必然失败。

| --- | --- | --- |

### 63.4 `g11g` 实测 437 而非理论 446 的原因
理论：ahead=50 → `v_ref = 50 × 3072 = 153600`（Q10 mm/s = 150 mm/s）→ `×3046>>20 = 446` counts。
实测 437，差 2% 来自 `rtl\odom\sin_lut_rom.v` 的 Q15 量化：**`cos(0°)` 存的是 32767 而不是 32768**（Q15 最大正数），
使 50 mm 的 `ahead` 被算成 **49 mm**（`50×32767/32768 = 49.9985 → 截断 49`），于是 `49×3072 = 150528 → 437`。

这是 LUT 量化误差，不是逻辑错误。但**不能用 `chk_int(437)` 锁死** —— LUT 一旦重生成（索引取整变化）就会误报。
所以 `g11g` 用区间 `425..455` 只守"斜率在 150 mm/s 量级"；旧 `K_SLOW_Q10=2363` 时会得 336，落在区间外。

### 63.5 另外两处仿真改进
**① `nav_ctrl_tb` 开头打印被测参数**，避免"改了参数却跑的是旧编译"造成的假通过：
```
params: ALIGN_IN_DEG=1000 ALIGN_OUT_DEG=3500 D_SLOW_MM=100 MAX_DIFF_CRUISE=252 K_SLOW_Q10=3072
```

**② `sim\run_sim.ps1` 汇总计数兜底**。原来 `cordic_atan2` / `nav_ctrl` / `nav_sys` 三台汇总显示 `pass=0 / CHECKS=0`：
它们逐项打印用 `ok` 前缀（不是 `pass`）、也不打 `CHECKS: N`，只把总数放在结论行 `PASS: <名> <N> 项全过` 里，
于是 `passCount` 恒为 0。
修法是在 `$checkTotal` 取值后加兜底：仅当"无 CHECKS 行**且** pass 行数为 0"时，从结论行取 N 并对齐。
两个坑：
- 正则**必须只用 ASCII 锚定** `'(?m)^\s*#?\s*PASS:\s*\S+\s+(\d+)\b'`。第一版写成 `(\d+)\s*项` 永远匹配不到 ——
  ModelSim 输出被 PowerShell 捕获时中文已变成乱码（日志里显示 `105 ��????����??`），字面量"项"对不上。
- 编辑 `.ps1` 后必须恢复 **UTF-8 BOM + CRLF**（`edit` 工具会剥 BOM 并转 LF，PowerShell 5.1 按 ANSI 读中文注释会语法错）。

- 依据：STA 是 worst-case corner，本板历史上 HDMI 同域长期在 −2.1~−2.4 而实测显示正常；50 MHz 同域负 slack 的三类路径里，
  vendor 两类（`imu_top` 的 SPI 接收缓冲、`disp_driver` 的像素输出）不承载控制链路，`nav_ctrl` 一条（`cut_ok_r`）承载 L2 切点判据但每 10 ms 才算一次、允许晚一拍。
- 不能记"通过"的理由：11 条 + 9 条实测超周期，最差 1.59 ns / 7.5%，没有余量证据。

**三条可选修法**（每条都要重新综合，结果不可预测）：

| 修法 | 改动 | 预期 |
| --- | --- | --- |
| ① `cut_ok_r` 再拆一级 | `nav_ctrl.v` 加 `cut_prod_r` 寄存器，把 `dot_s * TAN_CUT_Q10` 的乘积与比较分两拍 | 直接针对最差的那条；代价 1 拍（100 ns/10 ms 周期，无感） |
| ② `nav_free_ctrl` 像素乘法输入打拍 | 把 `i_x_mm/i_y_mm/o_cur_x_mm/o_cur_y_mm` 先寄存一拍再进 `×3932` | 消掉 7 条；车绿点晚 20 ns，不可见 |
| ③ 不动 RTL，重跑 PnR | 布局偶然性已被三次实测证明 | 可能好也可能更差（17:22 先例） |

**不建议**为这 20 条负 slack 动 vendor IP：`u_imu` / `u_hdmi` 的快照一致性比这点余量更值钱。

### 66.6 显示换算的两个定点乘

- 对准角 ÷100：`(v * 328) >> 15`（328/32768 = 0.0100098，即 ÷99.9；1000→10、3500→35）

### 68.2 修复一：返回时回到进入前那一页

原实现（`rtl\top\falcons_top.v` 页面状态机）：

```verilog
end else if (tune_exit) begin
    page     <= PAGE_DATA;   // 参数页 → 回运行数据显示页
    menu_sel <= PAGE_DATA;   // 高亮同步，避免确认一次就跳走
end
```

写死回 `PAGE_DATA`。改为记住**进入参数页之前停在哪一页**：

```verilog
reg [2:0] tune_prev_page;            // 声明在 tune_lock 旁，复位到 PAGE_DEFAULT
// 进入时锁存（rc_confirm 分支内）：
if (menu_sel == PAGE_TUNE) tune_prev_page <= page;
page <= menu_sel;
// 返回时恢复：
end else if (tune_exit) begin
    page     <= tune_prev_page;
    menu_sel <= tune_prev_page;
end
```

`tune_prev_page` 与 `page` 同为 3 位，`menu_sel` 同步恢复以保证「高亮与页面同源」这条既有约束（否则确认一次就跳走）。

### 68.3 修复二：数值与单位下部被截断

**根因**（不是渲染逻辑错，是两个常量按 16 px 字高算的）：

- `rtl\ui\ui_render.v` 的 `SM_CELL = 16`（`localparam integer SM_CELL = 16;`）是**横向小区宽度**，被参数页误当成纵向字形高度用了：`i_pixel_y < base + TUNE_VDY + SM_CELL` 只放行 0..15 行。
- 而 `font_num` 点阵实际是 **16 宽 × 24 高**（`font_rom.v` 是 3808×16、`font_num.v` 是 5712×16 —— 5712 = 238 字 × 24 行，行数就是字高）。
- `TUNE_VDY = 10` 同样按 `(36−16)/2` 算的，正确值是 `(36−24)/2 = 6`。

数据页之所以没这个毛病：它写死了字面量 `i_pixel_y < 12'd48`（基址 + 24），没经过 `SM_CELL`。

**改法**：

```verilog
localparam integer TUNE_VDY = 6;    // 24px 数字相对行顶偏移 (36−24)/2
localparam integer TUNE_VH  = 24;   // 数值点阵行数（font_num: 16×24）
...
if ((i_pixel_y >= (TUNE_Y0 + ti * TUNE_STEP + TUNE_VDY)) &&
    (i_pixel_y <  (TUNE_Y0 + ti * TUNE_STEP + TUNE_VDY + TUNE_VH))) begin
```

`TUNE_VDY` 与标签的 `TUNE_TDY = 6` 变成同一个值 —— 24 px 标签与 24 px 数字基线对齐，视觉上是一行。

### 68.4 修复三：摇杆极性（右推 = 增大）

`rc_steer` 的**正 = 推杆向左**，依据是 `rtl\motor\chassis_ctrl.v` 里 `man_diff` 正 = 左转（`tgt_left` 慢），与 `i_steer` 同号。（同一个事实在 `sim\nav_sys_tb.v` 里表现为 `STEER_SIGN=-1`、推右要给 `i_steer=-1000`。）

原代码把 `st > 0` 当成"右推"：

```verilog
wire dir_p = (st >  STEER_DEADZONE);   // 实际是左推
wire dir_n = (st < -STEER_DEADZONE);   // 实际是右推
wire [1:0] dir_cur = dir_p ? 2'd1 : (dir_n ? 2'd2 : 2'd0);   // 2'd1 = 加
```

于是上板表现为"向左增大、向右减小"。改为按**物理方向**命名后再映射：

```verilog
wire        st_right = (st < -STEER_DEADZONE);   // 物理右推
wire        st_left  = (st >  STEER_DEADZONE);   // 物理左推
wire        dir_nz   = st_right | st_left;
wire [1:0]  dir_cur  = st_right ? 2'd1 : (st_left ? 2'd2 : 2'd0);
```

加步长那一支的判断也从 `if (dir_p)` 改为 `if (st_right)`（`rtl\ui\tune_ctrl.v` 的 `p[i] <= p[i] + p_step(...)` 分支）。改完 `dir_p` / `dir_n` 在全文件已无代码引用，只剩注释里的历史说明。

`sim\tune_ctrl_tb.v` 同步：`push_pos` 给 `-12'sd600`（物理右）、`push_neg` 给 `+12'sd600`；G8 长按连发那处 `i_steer = 12'sd600` 改为 `-12'sd600`。**这两个 task 是 RTL 极性的镜像，以后改极性必须一起反号**，已在 tb 里写成注释。

## §69 积分限幅端口化 + 参数页改 CH2 选行（2026-10-20 下午，上板反馈驱动）

### 69.1 起因：直行摆头的真根因是"积分限幅 >> 行进差速限幅"

上板后需求方报「走直线总是左右摆头」与「原地旋转到不了目标角度」，两次实测把原因锁死：

- `rtl\nav\nav_ctrl.v` 原 `parameter integer I_LIMIT = 400`（注释写「≈ MAX_DIFF，防饱和」），但 `MAX_DIFF_CRUISE = 180`。
- 积分 `i_sum` 可单独涨到 ±400，`u_pid = p_term + i_lim_r − d_term` 再被 `clamp32(..., MAX_DIFF_CRUISE=180)` 截断 ⇒ **积分一旦超过 180，输出恒为 ±180**，PID 退化成 bang-bang，满舵左右来回 → 摆头。
- 积分涨满耗时（`i_inc = (psi × KI_YAW=4) >> 8`）：3° 约 1.0 s、5° 约 0.57 s、8° 约 0.33 s —— 与上板观察到的摆头周期同量级。
- 需求方把航向积分清零后**能走直**，说明摆头确实来自积分而非 P/D；但清零后**原地转不到目标角度**，因为没了积分就补不掉末端静摩擦/死区。

⇒ 结论：积分必须有、但上限必须显著小于行进差速限幅。故把 `I_LIMIT` 从 `parameter` 改为**运行时端口**，放进参数整定页。

### 69.2 改动一：`I_LIMIT` → 运行时端口 `i_i_limit`

`rtl\nav\nav_ctrl.v`：
- 删 `parameter integer I_LIMIT = 400`（与上一行 `OM_CLIP` 的逗号一并处理）
- 端口列表加 `input wire signed [31:0] i_i_limit,`（在 `i_kd_yaw` 之后）
- 限幅处改为
  ```verilog
  wire signed [31:0] i_lim = (i_sum >  i_i_limit) ?  i_i_limit
                           : (i_sum < -i_i_limit) ? -i_i_limit : i_sum;
  ```
- 全文件已无 `I_LIMIT` 引用（`grep` 复核）

`rtl\top\falcons_top.v:1432` 接 `.i_i_limit (tune_p[383:352])`。

### 69.3 改动二：第 12 项参数「积分限幅」

`rtl\ui\tune_ctrl.v` 由 11 项扩到 12 项：

| 项 | 默认 | 范围 | 步长 | 显示 |
| --- | --- | --- | --- | --- |
| 11 积分限幅 | **90** | 0..612（0 = 完全禁用积分） | 10 | counts/10ms 原值，不做换算 |

`o_param` / `o_disp` 由 `[351:0]` 扩到 **`[383:0]`**；`p[]` / `d[]` 数组与三处 `for` 循环、`genvar` 打包循环同步改 12。

### 69.4 默认值 90 的选取依据

不是拍的，三条约束同时满足才取 90：

1. **不饱和**：直行时 psi 典型 |ψ| ≤ 3°（300），`p_term = 300×21>>8 = 24`；`p + i = 24 + 90 = 114 < 180`，输出仍由 P/D 主导 ✓。即使偏到 8°（800），`p_term = 65`，`65 + 90 = 155 < 180` 仍不饱和 ✓（这条已写成断言 `g14_not_saturated`）。
2. **够克服静摩擦**：90 counts ≈ 21 °/s 的末段角速度，足以让原地转在接近目标时继续微动，不会停在死区外。
3. **与行进限幅成固定比例**：`90 = MAX_DIFF_CRUISE(180) / 2`。改行进限幅时积分限幅的推荐值跟着走，不会再次出现 400 vs 180 那种 2.2 倍失配。

对照：若默认取 180（= 行进限幅），8° 偏差下 `65 + 180 = 245 > 180` 恒饱和 —— 等于把摆头原样保留下来。故 180 不能当默认。

### 74.6 逐条归因

- **① `syn_keep` 负优化（有机制证据）。** 21:52 时 `hcount → Disp_*` 从 7 条涨到 19 条、最差 −1.231 → −2.339、逻辑级数 28~30。`impl\gwsynthesis\falcons.vg:117339` 确认 `DFFRE Disp_DE_s1` 确实被保留（`.Q(Disp_DE)`、`.D(.n168_10)`、`.CLK(pixel_clk)`、`.RESET(Disp_DE_12)`），但 24 个 mux LUT（`falcons.vg:116710-116852` 的 `.I1/.I2/.I3(Disp_DE)`）仍以组合方式取 DE。机制：`syn_keep` 只保证寄存器不被优化掉，**不阻止 logic replication** —— 为了让 25 个消费点就近取到 DE，综合器复制了比较器逻辑，布局膨胀、布线更长。

- **③ 三轴打拍：起点确实变了，但没有收益。** 21:52 时路径起点从 `rx_buf` 变成 `gyro_x_cs_31`，条数 1 → 3、最差 −1.297 → −2.310，说明打拍切断的 `rx_buf → 乘法` 那段不是瓶颈，真正的瓶颈在乘法输出 → `n3913` 的组合累加。

  1. `syn_keep` 不能用来「切断组合链」。它保的是寄存器不被优化掉，综合器的 logic replication 照样会把上游逻辑复制到下游消费点。要真正切断，只能在 RTL 里插一级寄存器并同步调整下游相位，没有综合属性可以替代。

**① `rtl\ui\ui_render.v`：把 `lg_slot × 24` 从 DSP 乘法改为移位相加（23:09 综合）**

原 `:491` 一行拆成两行（现 `:496-497`）：

**③ `rtl\odom\odom.v`：角度索引与窗口位移一起锁存一拍（23:36 综合）**

起因是高扇出表里 `u_odom/idx_sin_w[6]` 扇出 **513**、worst slack 只剩 **+0.299 ns**。扇出来自 8 位地址同时驱动两个 256×16 的 LUT ROM（sin 与 cos），而这条地址线原来是纯组合的：`yaw_wrap/dyaw_acc → yaw_mid → ×7457 → >>>20 → idx → LUT 地址`。

## 76. A1 / B1'：常数除法与累加器改写的两次负优化（2026-10-21）

### 76.1 缘起与结论

§75 把同域违例收到 4 条，剩下 sys 域 1 条（`u_imu/rx_buf[6]_6_s0 → n3913_s`，−0.107）和 pixel 域 3 条（最差 −0.193）。§75.7 判断 sys 域那条的真瓶颈是 `gyro_*_cs` 的 `× 25000 >>> 12` 之后的组合累加。

本轮不再走「打拍」路线（§74 已失败），而是直接改写**算术结构**：

- **A1**：`imu_top.v` 的 `calib_sum_x/y/z` 与 `seed_sum_x/y/z` 从 48 位降到 32 位。
- **B1**：`ui_render.v:490` 的 `lg_slot = x_look / LG_CELL_N`（12 位除以常数 24）改成纯移位加法的分解实现。

两者都单独验证过**数学等价**，但 PnR 实测**都是负优化**：同域真违例 1 → 15 条，两个时钟域 Fmax 各降约 4%，连**未改动的 `nav_free` / `odom` 模块都被推过线**。已全部回退，位流重建后逐项回到基线。

**这一节最值得记的不是两个方案怎么做，而是为什么判断错了** —— 见 §76.7。

### 76.2 A1：48 位累加器 → 32 位

原代码（`vendor\verilog-reusable-modules\modules\imu660ra\rtl\imu_top.v`）：

```verilog
:340  reg  signed [47:0] calib_sum_x, calib_sum_y, calib_sum_z;
:376  wire signed [47:0] seed_sum_x = calib_sum_x + gyro_x_cs;
:699  if ((!calib_seed_done) && (calib_cnt_next == CALIB_SEED_N)) begin
:700      calib_mean_x <= seed_sum_x[35:4];      // /16
:707  if (calib_accum && (calib_cnt_next >= CALIB_SAMPLES)) begin
:708      bias_x_r <= seed_sum_x[40:9];         // /512
```

位宽核算：`CALIB_SAMPLES = 512`，单样本 `|gyro_x_cs| ≤ 200000`（`±32768 × 25000 >>> 12`），故 `|sum| ≤ 512 × 200000 = 1.024e8 < 2^27`；加 `CALIB_ABS_LIMIT = 2000` 门禁后实际更小。**32 位有 21 倍余量**，48 位是纯浪费。

改动 5 处：`[47:0] → [31:0]`（声明 1 + `seed_sum` 3）、`48'sd0 → 32'sd0`（6 处）、`seed_sum_x[35:4] → $signed(seed_sum_x) >>> 4`、`seed_sum_x[40:9] → $signed(seed_sum_x) >>> 9`。

**等价性验证（Python，3000 组随机含 ±MAXS 极值）**：`peak |sum| = 102400000`（2^31 的 4.77%）、`max |sum48 − sum32| = 0`、`>>>4` 与 `>>>9` 的 mismatch 均为 0 → PASS。`imu_top_tb` 16 项全过。

### 76.3 B1 第一版：寄存器增量计数器（已废弃）

思路：`x_look` 在一条扫描行内逐拍 +1，所以 `slot` / `col` 可用「上一拍 + 1，满 24 归零」推出，彻底不除。实现是两个寄存器 `lg_slot_p` / `lg_col_p` 保存 `i_pixel_x − 1` 的值，当前值由它们**组合**推出（`lg_wrap` 判满、`i_pixel_x == 0` 强制归位）。

独立小台 `logs\b1_slot_eq_tb.v` 逐点扫 0..1023 四轮，**4096 点全对**，数学没问题。

**但全量仿真挂了 12 项**（`imu_fail_red_text`、`ph_p1_camera`、`car_absent_on_page3`、`menu_item0_boundary`、`car_shape` 等），外加 `tune_page` 的 `5_unit_row5_none`。回退后重跑 19/19 全 PASS，证明全部由 B1 引入。

**根因是相位，不是逻辑**。`sim\ui_render_tb.v` 的采样写法是 `px = xx[11:0]; ... @(posedge pixel_clk); <采样 rgb>`，`px` 在 posedge **之前**赋值、posedge 之后不前进。而 `lg_slot_p` 在同一个 posedge 已更新为 `f(px)`，组合输出变成 `f(px+1)` → tb 看到的结果**超前 1 列**，字形位选错位。

真实硬件里 `H_Addr` 是 `hcount_r` 的组合函数（`disp_driver.v:77`），posedge 后立即前进，`lg_slot_p` 滞后一拍正好抵消 → **我的设计在硬件里是对的，只是与 tb 的建模相位不兼容**。改 tb 会影响 46 项检查的坐标语义（§75 前后 ui_render 由 42 增到 46 项），代价大于收益，故放弃这一版。

### 76.4 B1'：纯组合的除法分解

`x_look = 24·slot + col_look`，而 `24 = 8 × 3`，所以先除 8（移位）再除 3：

```verilog
wire [7:0]  lg_x_div8 = x_look[10:3];                          // n = x_look / 8，n ≤ 128
wire [12:0] lg_n43    = {lg_x_div8, 5'd0} + {lg_x_div8, 3'd0}
                      + {lg_x_div8, 1'b0} + {5'd0, lg_x_div8}; // n*43 = n*32 + n*8 + n*2 + n
wire [5:0]  lg_q_raw  = lg_n43[12:7];                          // ≈ n/3，可能偏大 1
wire [7:0]  lg_q_x3   = {lg_q_raw, 1'b0} + {1'b0, lg_q_raw};   // 3q
wire [5:0]  lg_slot   = (lg_q_x3 > lg_x_div8) ? (lg_q_raw - 6'd1) : lg_q_raw;
```

数学依据：`43/128 − 1/3 = 1/384`，故 `43n/128 − n/3 = n/384 < 2` 对 n < 768 成立 ⇒ n ≤ 128 时最多偏大 1，判据 `3·q_raw > n` 减 1 即可精确。

`n mod 3`：2^i mod 3 在 i 偶/奇时交替 1/2 ⇒ 偶位系数 1、奇位系数 2，和 ≤ 12，两次减 3 归一。最后 `col_look = 8·(n mod 3) + x_look[2:0]`。

**零 DSP、零寄存器，相位与原式完全一致**，所以 tb 不用改。

小坑：第一版误写 `{lg_q_raw, 2'b0}`（即 q×4）当 3q，`x_look=24` 时 slot 算成 0，ModelSim 立刻报 `BAD slot x_look=24 got=0 exp=1`。

**验证两道**：Python 全范围 0..1025 不符点 **0**；ModelSim 独立小台 `logs\lg_div2.v` 比对 slot / col_look / col 三项，`PASS: lg_div all 1026 points match`。全量仿真 **19 台 / 2186 项全 PASS**（`ui_render` 46 项、`tune_page` 58 项）。

### 76.7 ★ 为什么判断错了（本节是这次最大的产出）

1. **从逻辑结构推断瓶颈，没有验证 PnR 里的实际映射。** 看到「48 位加法器」「÷24」就认定它们是关键路径，但没先确认综合器把它们实现成了什么。实际是：常数除法被压成很浅的 DSP/LUT 组合，而手写分解**把 1 级换成 4~5 级级联**，逻辑深度反而增加。
2. **忽略了 P&R 对布图扰动的敏感性。** 只要 RTL 变动，PnR 就整体重排；`nav_free` / `odom` 的 7 条就是这么变差的。这与 §75.6 记的归因限制同源，但这次是**反向**教训：改动可以伤害完全无关的模块。
3. **用综合报告下结论太早。** 综合 Fmax 与 PnR 实测差 19%，LL 变化也不敏感（30 → 31）。真正能定性的是 PnR 的**同域违例明细**。

1. 先看 PnR 的 `Setup Paths Table`，确认目标路径的 **from / to 节点和逻辑级数**，不要靠猜。

## §77 按方法论文档复查全部违例：SDC 改造成功 + 方案 A 负优化

**时间**：2026-10-21 01:30 ~ 02:30
**触发**：用户给出《FPGA RTL 时序优化通用经验》（166 行，8 节），要求「按这份文档重新检查所有违例并给出分析结果和优化方案」。
**结论一句话**：把跨域伪违例清掉了（唯一净收益），但真正指向 4 条真违例的两条 RTL 改写（方案 A、步 1）全部负优化并回退。

完整分析见 `doc\时序违例分析_20261021.md`，本节只记过程与归因。

### 77.1 第一次真正看清 4 条真违例

此前 `-max_paths 25` 只报最差 25 条，全被跨域伪违例占满，pixel 域那 3 条（−0.08 级）一直看不到。
改用 `impl\pnr\falcons.timing_paths`（50 块：25 setup + 25 hold，含**每级到达/离开时间**）与综合报告的
`Detail Timing Paths Information`（25 条全是同一条链）交叉取证，才拿到完整级联：

- **sys 域**：`rx_buf[6]_6 → n3913_s`，−0.107。级联显示 `gyro ×25000>>>12`（2.31 ns）→ `dev = gyro − mean`（1.66 ns）
  → **`adev` 三轴求和（5.05 ns / 14 级）** → `< CALIB_DEV_TH` → `calib_cnt+1` → `calib_done` → `n3913`。
  对应 RTL `imu_top.v:372` 的 `wire calib_accum = (!calib_seed_done) || calib_still;`——
  **累加器的使能被一条与它无关的抖动判据链阻塞**，属方法论 §1「多级条件判断后接 CE」/ §2「减少控制依赖」。
- **pixel 域**：`hcount_r → Disp_Green`（−0.080 / −0.061）与 `vcount → u_dyn_text/o_rdata`（−0.052）。
  前两条的链是 `hcount → x_look → ÷24 → ×24 → 减法 → 条件减 → 23− → 24→1 位选 → o_rgb`，
  `lg_bit_sel` 必须用当前列号，不能被两级 ROM 流水吸收。

### 77.2 B 实验：SDC 时钟分组（✅ 成功，保留）

`set_clock_groups` 一直因 `TA2004` 不可用，根因是 **PLL 输出的 generated clock 在 SDC 解析阶段不在时钟库里**。
读 Gowin 官方 `SUG940-2.0.4_Gowin设计时序约束用户指南.pdf`（93 页）确认有 `create_generated_clock`，
于是自己命名再分组：

```tcl
create_generated_clock -name clk_pixel  -source [get_ports {i_clk_50m}] -multiply_by 49 -divide_by 50 [get_pins {u_hdmi/u_display_pll/PLL_inst/CLKOUT0}]
create_generated_clock -name clk_serial -source [get_ports {i_clk_50m}] -multiply_by 49 -divide_by 10 [get_pins {u_hdmi/u_display_pll/PLL_inst/CLKOUT1}]
create_generated_clock -name clk_cam200 -source [get_ports {i_clk_50m}] -multiply_by 4 [get_pins {u_cam/u_system_pll/PLL_inst/CLKOUT0}]
create_generated_clock -name clk_cam50  -source [get_ports {i_clk_50m}] -multiply_by 1 -divide_by 1 [get_pins {u_cam/u_system_pll/PLL_inst/CLKOUT1}]
create_generated_clock -name clk_ddrf   -source [get_pins {u_cam/u_system_pll/PLL_inst/CLKOUT0}] -divide_by 4 [get_pins {u_cam/u_frame_buffer/DDR3_Memory_Interface_Top/gw3_top/u_ddr_phy_top/fclkdiv/CLKOUT}]
set_clock_groups -asynchronous -group [get_clocks {i_clk_50m}] -group [get_clocks {camera_pclk}] \
                 -group [get_clocks {clk_pixel clk_serial}] -group [get_clocks {clk_cam200 clk_cam50 clk_ddrf}]
```

**四组**：sys / 摄像头 PCLK / HDMI（像素 + 串行必须同组，5:1 同相）/ DDR（200M + 50M + PHY 内部 fclkdiv）。
倍频比按各 IP 的 defparam 折算：`display_pll` 是 `50×49/2/25 = 49 MHz` 与 `50×49/2/5 = 245 MHz`；
`gowin_pll` 是 `50×16/1/4 = 200 MHz` 与 `50×16/1/16 = 50 MHz`。

**效果**：Hold 违例 **2605 → 18**（−99.3%）、Setup **84 → 62**，`default_gen_clk` 全部消失，
**4 条真违例的数字一个没变**（−0.107 / −0.193）。Fmax 也不变——约束只影响分析，不影响布局。

**代价**：`clk_ddrf` 显式定义后，DDR3 IP 内部 8 条 `u_dll/CLKIN → dll_step_base_*`（−3.4~−3.8 ns）
开始被分析。它们在基线里因 `WARN (TA1132) ... was determined to be a clock but was not created`
**根本没被分析**，属「从看不见到看见」，且由 IP 自身保证，不加假路径掩盖。

**踩坑一次**：第一版把 `clk_cam50` 写成 `-source clk_cam200`，但 PLL 的 CLKOUT0/CLKOUT1 是并行的两个输出
而非串联，报 `TA1021`（source 找不到）。改成与 CLKOUT0 同源（`i_clk_50m`，`-divide_by 4`）即通过。

### 77.3 方案 A：`lg_col` 与 `lg_slot` 解耦（❌ 负优化，已回退）

**假设**：pixel 域那两条的最长一段是 `lg_slot → ×24 → 减 → 条件减`，而 `lg_col` 其实只依赖当前列号。
用 `24 = 8 × 3` 得到与除法器无关的算法：`x mod 24 = 8×(⌊x/8⌋ mod 3) + (x mod 8)`，
`⌊x/8⌋` 是接线移位、`x mod 8` 取低 3 位，只剩 `n mod 3`（偶位系数 1、奇位系数 2 加权和，再循环减 3）。

**结果**（`build.tcl`，631.3 秒）：

| 指标 | B 实验基线 | 方案 A |
| --- | --- | --- |
| Setup 违例端点 | 62 | **74** |
| Hold 违例端点 | 18 | 18 |
| `i_clk_50m` TNS | −0.107 / 1 | **−2.816 / 10** |
| `clk_pixel` TNS | −0.193 / 3 | **−2.374 / 6** |
| `i_clk_50m` Fmax | 49.733（LL24） | **48.489（LL25）** |
| `clk_pixel` Fmax | 48.807（LL30） | **47.613（LL26）** |

**目标路径确实消失了**：`hcount_r_3 → Disp_Green` 不在 Setup 表里了。
**但**：原本 −0.052 的 `vcount → u_dyn_text/o_rdata_3` 恶化到 **−0.594**，同族 `o_rdata_0` −0.557；
另外冒出 `u_imu/rx_buf[9]_2 → n3913_s/A[2]`（−0.623）与 `u_nav_ctrl/n1093_s → cut_ok_r_s0`（−0.588）——
**后两条所在模块一行都没改**。

### 77.4 为什么又失败：pixel 域是「多条近临界路径并存」

方法论 §4 已预警「局部路径缩短后，其他近临界路径也可能接替成为全局瓶颈」，§3「多类路径同时接近临界值时，
单点优化效果有限」。本次是第三次验证这条规律（前两次是 §76 的 A1 / B1'）。

具体机制：
1. 新增的 `lg_cx_*`（8 个 1 位加法 + 2 级 5 位加法 + 3 级条件减）本身不算深，但它**多占了 ~20 个 LUT**，
   改变了 pixel 域的摆放，把 `vcount → dyn_text` 那条推过线。
2. `lg_col` 与 `lg_slot` 解耦后，原来共享的除法器输出要驱动两条独立路径，**扇出与布线变差**。
3. `imu` / `nav_ctrl` 的新违例说明影响是**全局布图级**的，不是局部的。

### 77.7 结论与建议

1. **4 条真违例的缺口只有 0.4%~0.5%**（−0.107 / −0.193 ns，周期 20 ns / 20.408 ns）。
2. **四次改动每次都让整体更差**，共同原因是布图扰动，不是算法错误（四次都通过全部仿真）。
3. **唯一的净收益是 SDC 改造**：报告从 `84 setup + 2605 hold` 缩到 `62 setup + 18 hold`，

   或接受现状——两个域分别只差 0.53% 和 0.39%，但这属于工程判断，不是时序报告能保证的结论。
