## 一、阶段一：工程骨架与依赖锁定

**做了什么**

1. `git init`（分支 `main`）+ `.gitattributes` / `.gitignore`（行尾策略随仓库走，不依赖各机器 `core.autocrlf`）。
2. **全量内嵌模块库快照**：`git archive --format=tar HEAD` 导出到 `vendor\verilog-reusable-modules\`
   —— 10 个包 / **144 文件** / 2.8 MB，无 `.git`、无 `sim\work` 这类未跟踪产物。
   （没用资源管理器拖拽：那会把 `work\`、`transcript`、`*.qdb` 一起搬进来。）
3. 生成记账：`VENDOR.lock`（源 URL + commit + tree SHA256 + 包清单）、
   `deps\vendor_manifest.sha256`（144 行逐文件哈希）、`deps\modules.list`（工程实际引用的包）。
4. 工具脚本：`tools\lib_paths.ps1`（所有路径的唯一定义处）、`sync_vendor.ps1`、`check_vendor.ps1`、
   `run_all_modules.ps1`、`build.ps1`；Tcl 侧 `scripts\vendor_sources.tcl`（从 `modules.list` 派生源文件）。

**为什么内嵌而不是 submodule**：方案文档 `class\模块库内嵌方案_反馈.md` 的结论 —— 库还在频繁更新时，
每次升级 pin 都要重新验证，日常成本高；内嵌可以将来平滑升级为 submodule（挂载点不变）。

**验证**：`check_vendor` 逐文件比对一致；`run_all_modules` 跑库自带测试
**PASS 11 / COMPILE-ONLY 1 / FAIL 0**；`build.ps1` 在缺顶层时给出人话报错而不是让综合器报天书。

**脚本自身修掉的两个缺陷**：`check_vendor` 里"144 项逐一比对"是**硬编码**（快照变 145 文件时数字对不上）；
BREAKING 提示用了 `[BAD]` 红色（让人误以为体检失败，实际只是提示）→ 改 `[WARN]`。

## 三、阶段三：参数确认与运动学换算

用户给定：轮半径 19.9 mm（轮宽 26 mm）、左右轮中心间距（轮距 L）158.6 mm、前后轮圆心间距（轴距）170 mm、
减速比 30、屏幕 1024×600 中文界面、HDMI 到显示器、RK3588 走串口、ToF 未做出先留空。

**★ 编码器线数判定（用已有实测数据反推）**：实测手转车轮一圈 ≈ 61657 计数（4 倍频后）

| 假设 | 理论计数/车轮转 | 与实测偏差 |
| --- | --- | --- |
| 500 PPR | 60000 | 2.76% |
| **512 PPR** | **61440** | **0.35%** ✅ |

→ 判定 **512 线**。连带发现：`car_fpga` 里 "rpm = delta/10" 隐含 60000 计数/转的假设，
按 512 线应为 `rpm = delta/10.24`（**2.4% 系统偏差**），本工程统一用 10.24。

**由参数算出的运动学常量**（全部写进 `chassis_ctrl` 的参数）：
轮周长 125.0354 mm、每计数 2.035 µm、1 rpm = 10.24 计数/10ms、
差速系数 0.66415 rpm/(deg/s) → 定标为 `DIFF_K_Q10 = 627`、`CENTER_K_Q10 = 3146`。

## 四、阶段四：中文界面基础设施

FPGA 上要显示中文，必须有点阵字库。做法：写生成器 `tools\gen_font_rom.py`，
从 `tools\font_chars.txt`（73 条文案）渲染出 **16×16 点阵**，直接**内嵌进 Verilog**
（不用 `$readmemh` —— 避免综合工作目录、外部文件缺失、CR 混入等一类问题）。

产物三个：`font_rom.v`（**223 字 / 3568 行**）、`ui_text_rom.v`（字符串索引流）、
`ui_text_index.vh`（73 条 `localparam` 地址/长度）。当前占 **5 块 BSRAM**（另加动态字符 1 块，共 6）。

> 更正（2026-10-15 自查发现）：这里原写"220 字"，与同一行的"3568 行"矛盾（3568 ÷ 16 = **223**），
> 生成器输出也是 223。**"字库字符数"这个数字以前在文档里被写错过一次，以 `rtl\common\font_rom.v`
> 里的 `CHAR_COUNT` 为准。**

生成器修掉三个自身 bug：索引文件曾**覆盖** ROM 内容；`localparam` 名里混进对齐空格
（Verilog 标识符不允许空格）；长度字段位宽 12 位导致拼接后被截断（改 6 位）。

## 五、阶段五：RTL 实现

| 文件 | 作用 | 关键设计 |
| --- | --- | --- |
| `rtl\rc\rc_input.v` | 遥控 6 路输入 | **实例化 6 个库内 `rc_pwm_capture`**（单路捕获可扩展），归一化用**移位加法**（×2.125 代替通用乘法），三档模式 + 按钮上升沿 |
| `rtl\motor\chassis_ctrl.v` | 底盘控制 | 差速分解（左=中心−Δ、右=中心+Δ）+ 4×增量式 PID + `u→(dir,duty)`（`i_dir`: 0=正转） |
| `rtl\ui\ui_render.v` | 中文界面 | 逐像素叠加、无帧缓存；**提前 2 拍取模**（ROM 各 1 拍延迟）；最多 6 个文本段 |
| `rtl\ui\num_text.v` | 实时数值格式化 | 慢速状态机逐位减法（不用组合除法） |
| `rtl\ui\dyn_text_ram.v` | 跨域字符缓冲 | 简单双口 BSRAM：sys 写 / pixel 读 |
| `rtl\top\falcons_top.v` | 整车顶层 | 只做例化连线；急停 > 堵转 > 遥控 > 自动的优先级链 |
| `rtl\common\app_key.v` | 按键去抖 | 两级同步 + 计时稳定 + 边沿 |
| 从 `car_fpga` 搬入 | `speed_pid` / `reset_sync` / `uart_cmd_rx` / `speed_report` | 行数、哈希与来源逐一核对 |

### 遥控的实现程度（本次盘点，2026-10-15）

**已实现**（`rtl\rc\rc_input.v` + `falcons_top` 接线；仿真 12 项 PASS、综合通过）：

| 能力 | 实现 |
| --- | --- |
| 6 路 PWM 捕获 | 库内**单路** `rc_pwm_capture` 实例化 ×6；合法脉宽 900–2100 µs，单路超时 100 ms |
| 两路模拟量 | 转向 / 油门 → **±1000**；中位 1500 µs、半量程 500 µs、**死区 ±25 µs** |
| 模式开关三档 | <1300 µs → 手动接管；1300–1700 → 屏幕光标；>1700 → 自动 |
| 三个按钮 | select / 确认 / 返回：位置 2 的**上升沿** → 单周期脉冲 |
| 丢信号保护 | 任一路超时 → 摇杆输出**立即归零** + 状态栏"无信号" + LED3 灭 |
| 档位联锁 | 手动档才接收摇杆；**光标档把摇杆强制为 0**；任何档位都要先按 S1 才输出 |
| 通道映射参数化 | `CH_STEER` / `CH_THROTTLE` / `CH_CONFIRM` / `CH_BACK` / `CH_MODE` / `CH_SELECT` |

**仿真验证**（`rc_input_tb` 12 项）：中位 → 0；端点 2000/1000 → +1000/−1000；死区 1520/1480 → 0；
模式 1200 → 手动(0)、1800 → 自动(2)；select 拨高 → **恰好 1 个脉冲**；停发 6 ms → 信号无效、恢复刷新 → 有效。

**未做 / 待确认（8 项）**：

1. **光标模式的界面交互完全没做** —— 功能设计文档 §5.4 要求的"摇杆移地图、准心居中、辅助菜单 5 项、主菜单变暗"依赖导航页（L5）；当前 select/确认只用于**切页**
2. **自动档无实际功能** —— 顶层把 `i_auto_valid` 恒接 0，自动档底盘不动（有意留白，等导航/避障接入）
3. **通道角色映射是"假设"的** —— 按功能设计文档 §6.10 的语义假设（转向/油门/确认/返回/模式/select），
   **必须按实际接线核对**；错了只改参数、不动逻辑
4. **接收机型号与输出形式仍待确认**（Q3）—— 若是 **PPM / SBUS**（单线串行）而不是每路独立 PWM，前端必须重写
5. **模式开关物理形态未定**（P11）—— 现按"PWM 通道脉宽三档"判定；若实际是独立拨杆开关（GPIO 电平），改 GPIO 更直接
6. **无遥控标定流程** —— 中位/端点/死区都是写死参数，没做"打杆记端点"的自动校准
7. **无摇杆曲线 / 限速** —— 没做 expo 曲线，最大速度只受 `chassis_ctrl.MAX_DELTA` 限制
8. **丢信号是"归零滑行"而非主动刹车** —— 检测阈值 100 ms，设计文档 L4 判据是"200 ms 内停车"；
   实际响应 = 100 ms 检测 + PID 收敛时间，**未实测**

**上板要验的 5 条**：① 每个通道实际是什么（看状态栏与 LED5:4）；② 中位是否正好 1500 µs；
③ 打满杆能否到 ±1000（否则改 `HALF_RANGE_US`）；④ 关接收机电源后的停车响应时间；⑤ 按住按钮是否只触发一次。

**两条关键设计决策**：

1. **提前 2 拍取模**：字符索引与点阵行各有 1 拍 ROM 延迟，扫描不等人。
   做法是"始终请求 (x+2) 所在的字组"——数据 2 拍后有效时 x 已推进到 x+2，仍落在同一字组内。
   这样**不需要行缓冲、不需要消隐期预取**，逻辑简单且无撕裂。
2. **布局强制 16 对齐**：所有文本起点 x 与 y 都是 16 的倍数 → 每个汉字恰好落在一个 16 px 字组内，
   取模退化成"字组号 + 格内位 + 行号"三件事，不需要任何除法。

## 六、阶段六：约束、首次综合与时序优化

**约束**：`constr\falcons.cst` 逐针抄自硬件手册（电机/编码器 21 根沿用 `car_fpga` 已复核的值，
板载时钟/按键/串口/LED 按手册 §2.3，遥控取 J6 整排，雷达 **C14**，ToF/RK3588 占 J7）；
`falcons.sdc` 只约束 50 MHz 外部时钟（`.cst` 与 `.sdc` 必须成对给，否则工具按默认 100 MHz 估算，
会报假违规）。

**首次综合**：ERROR 0，但时序 **SETUP 违规 25 条，最差 −7.023 ns**。逐步优化（每步都重新综合实测）：

| 步 | 措施 | 结果 |
| --- | --- | --- |
| 1 | 遥控归一化改**移位加法**（×2.125 代替通用乘法）；`chassis_ctrl` 指令乘法**插一级流水** | SETUP 最差 −7.023 → **−2.589** |
| 2 | 差速/限幅链**再插一级流水**（切断"中心速度→限幅→差速→PID 输入"） | → **−0.616**（仅 1 条） |
| 3 | 像素域复位改**域内自产**（等 PLL 锁 + 计数释放），不再把 `sys_rst_n` 引到 pixel 域复位端 | → **−1.412**（1 条，且消除了复位链那条） |
| 4 | 加 UI 实时数值（跨域字符 RAM）后 | 7 条，最差 **−0.353** |
| 5 | 接入 IMU 链路后 | 1 条，最差 **−2.003** |

**关于"为什么不用 SDC 声明异步"**（重要，避免后人重复踩）：我**先试了正解** ——
在 `.sdc` 里写 `set_false_path -to [get_clocks {pixel_clk}]`，但 `pixel_clk` 是 `hdmi_1024x600`
内部 PLL 的派生时钟，**约束解析阶段还不是时钟对象**，直接
`ERROR (TA2004): Cannot get clock with name 'pixel_clk'` 导致综合失败 → 撤回，改为用 RTL 手段消除。

**当前剩余违规的性质**：SETUP 1 条 + HOLD 9 条，路径两端分别是同一信号在两个时钟域的采样
（状态位同步器第一级、遥控异步输入采样、动态字符 RAM 的跨域读）。这是 CDC 的结构性现象，
不构成功能风险 —— 判据在 `doc\上板指南_v1.md` 第六节列了每条路径的源/目的。

**真实逻辑路径**（非 CDC）最差 slack 只有 **+0.105 ns**，落在 `speed_pid` 内部。
这与 `car_fpga` 的 `imu_demo` 工程 Fmax 只有 51.11 MHz（余量 2.2%）是同一现象 —— 属模块自身特性，
要改**只能改 vendor 里的模块**（当时的铁律是"先在源库提交再同步"；2026-10-15 起改为 vendor 直接维护，见第十三节）。

## 九、阶段九：IMU 链路接入

**接入**：`imu_top` (u_imu) → `gyro_tilt_comp` (u_tilt) → `yaw_integrate` (u_yaw) → 数据页航向角。
三个包进 `deps\modules.list`；SPI 四线约束到 A14/A13/A16/A15（J2）。

**接线没自己猜** —— 直接照 `car_fpga\rtl\top\imu_demo_top.v` 里**已上板验证过**的接法，
三条契约写进顶层注释：

1. `gyro_tilt_comp.i_sample_valid` 接 **`o_acc_valid`**（不是 `o_data_valid`）：
   后者只在 RUN 态产生，标定窗口期收不到样本，会让倾斜补偿**永远不生效且不报错**。
2. `gyro_tilt_comp.i_calib_start` 接 `o_calib_busy`。
3. `yaw_integrate.i_sample_valid` 接 `o_data_valid`。

另外 `imu_top.SCK_HALF_DIV` **显式写 25**（1 MHz）：源码默认 3（8.33 MHz）实测会导致

**验证**：编译通过、仿真 4/4 PASS（新增航向角显示检查 `yaw_number_px = 172` 通过）、

### A. 工具链与沙箱

### B. PowerShell / 脚本

| 坑 | 现象与处理 |
| --- | --- |
| **数组字面量里拼换行会丢行** | `@( @('a','b'), @('c', 'x' + "`n" + 'y') )` 里第二行会丢 —— 本会话被这个坑咬了 **4 次**（生成器脚本、tb 检查项、tb 统计块）。**改用 here-string** |

| `Get-Content` 默认按 GBK 解码无 BOM 的 UTF-8 | **不报错**，只是安静地给错结果（曾把 588 行数成 434 行）→ 一律显式 `-Encoding UTF8` 或用 `ReadAllText` |
| `$t.Split($Old)` 陷阱 | 传字符串会被当 `char[]` 拆成逐字符分割 → 用 `[regex]::Matches` 数命中次数 |

### C. Verilog / RTL

| 坑 | 现象与处理 |
| --- | --- |
| **`localparam` 不能在 module 外声明** | `include` 一个只有 `localparam` 的 `.vh` 放在 module 之前 → 解析失败、后续变量全"未定义"。**include 必须在 module 体内** |
| **不能对表达式做位选择** | `(-cur)[15:0]` 非法（ModelSim `vlog-13069`）→ 先算 `absv` 再取位 |
| **位宽写小** | `wire [15:0] flat_us` 要装 6×16 位 → **ModelSim 容忍、Gowin 报 `EX3784` 越界**并把该模块降级成黑盒 |
| **声明顺序** | 变量必须在**使用它的 always 块之前**声明（顶层 `yaw_clear_r` 踩到） |
| 组合 `always` 未给默认值 | 推断出 latch（`EX2420`）→ 在块首赋默认值 |
| 优先级顺序影响视觉 | 状态栏与菜单条 x 范围重叠 → 谁先判断决定配色是否割裂 |

### D. Gowin 综合特有

| 坑 | 现象与处理 |
| --- | --- |
| 只能容忍语法、不能容忍越界 | 见上 `EX3784`；**仿真通过 ≠ 能综合**（本会话再次验证） |
| 约束里引用 PLL 派生时钟 | `set_false_path -to [get_clocks {pixel_clk}]` 报 `TA2004` 并**导致综合失败** —— 该时钟在约束解析阶段还不存在 |
| 时序报告里的 CDC | 同步器第一级、异步 RAM 读都会被当数据路径分析，报出零点几纳秒的违规；要区分"CDC 结构性"与"真实逻辑路径" |

### E. 写 testbench

| 坑 | 现象与处理 |
| --- | --- |
| **fork 多个并行进程给同一 reg 的不同位赋值** | ModelSim 下互相覆盖：所有通道脉宽恒为 0，而**单通道调试台完全正常** —— 极易误判成模块坏了。改成每路一个独立 reg 再拼接 |
| 采样时机太早 | `rc_pwm_capture` 在下降沿后还要数拍才更新输出，帧间隔只留 2 µs → 读到旧值造成**假 FAIL**（留 ≥10 拍） |
| 时间常量写错 | `#8000` 在 `timescale 1ns` 下是 8 µs 不是 8 ms（超时测试应写 `#6_000_000`） |
| 期望值写错 | 第 1 个菜单项默认**选中**，文字是亮黄 `FFE066` 而不是灰 `E5E7EB` |

### F. 时序优化

| 坑 | 现象与处理 |
| --- | --- |
| 组合乘法链过长 | 遥控归一化用 `(delta × SCALE) >> 10`，综合后 setup slack **−7.02 ns**；换移位加法 + 插流水后达标 |

## 十三、架构变更：vendor 转为本项目直接维护（2026-10-15）

### 变了什么

| 项 | 变更前 | 变更后 |
| --- | --- | --- |
| 模块库定位 | 外部源库是**真源**，`vendor\` 是只读快照 | **`vendor\` 就是本工程的代码**，直接改、直接提交 |
| 改模块的流程 | 源库改 → 提交 → 推送 → `sync_vendor` → `check_vendor` ×2 → 库测试 → 整车仿真 → 提交（**六步**） | 改 → 跑 `sim\run_sim.ps1` → 提交（**0 步同步**） |
| 记账 | `VENDOR.lock` + `deps\vendor_manifest.sha256` | `vendor\ORIGIN.md`（一篇说明：来源 commit + 改模块的纪律） |
| 漂移检测 | `tools\check_vendor.ps1`（144 项逐文件比对） | 无 —— 不存在"两份真源"，也就无所谓漂移 |
| 源库 | 需维护（fetch / 同步 / 保持最新） | **原地存档、只读**，不再维护，保留开发历史 |

**删除的 5 个文件**：`VENDOR.lock`、`deps\vendor_manifest.sha256`、`tools\sync_vendor.ps1`、
`tools\check_vendor.ps1`、`doc\模块库升级流程.md`（均可用 `git checkout <提交> -- <路径>` 从历史恢复）。

### 为什么变

1. **这批模块只有本工程一个消费者** —— 用户确认 `class\car_fpga` 是已完成使命的试验场，
   模块早已提取完毕，不再作为独立消费者维护。此时"库"的复用属性不存在，抽象层就是纯成本。
2. **同步机制的成本大于收益** —— 队友反馈"同步机制太复杂"。六步流程 + 两套记账 + 三件套体检，
   对一个四人小队、一个工程来说认知成本明显偏高（连"改一行模块"都要走一遍手册）。
3. **改模块的收益是立刻的，同步的收益是假设的** —— 只有将来真的复用，源库才有价值；
   而那时把模块从 `vendor\` 提出来也来得及。

### 保留了什么（避免"简化"变成"丢东西"）

- **源库不删**：原地存档，模块的开发历史（谁在哪次提交、为什么改）完整保留，将来可考古或复用
- **`deps\modules.list` 保留**：它是"哪些包进编译"的清单，与同步无关，`build.tcl` 仍从它派生
- **模块自带测试保留**：`tools\run_all_modules.ps1` 仍可跑 12 个入口（PASS 11 / COMPILE-ONLY 1），
  改模块后当回归用
- **`vendor\` 内容一个字节没动**：144 个文件、包结构（`rtl` + `sim` + `constraints` + 各包 README）完整保留
- **来源可追溯**：`vendor\ORIGIN.md` 里记着来源 URL 与最后同步的 commit `c9b8025`

### 新的纪律（唯一不能省的一步）

**改了 `vendor\` 里的模块，必须跑 `sim\run_sim.ps1`** —— 模块是整车的一部分
（电机驱动 / IMU 驱动 / 遥控捕获 / HDMI 显示都在里面），改了它们整车行为就变了。
改某个包时也可以顺手跑该包自带的测试：`tools\run_all_modules.ps1 -Packages <包名>`。

详见 **`vendor\ORIGIN.md`**。

`speed_report` 在顶层例化（`u_report`），串口从"只收不发"变成**收 + 发**：

### 2. 引脚逐针复验（原"遗留第 3 条" → 已完成，**并抓到一个真缺陷**）

`tools\check_pin_constraints.py` 从 `car_fpga` 迁入并**扩展**；手册 `ACG720_引脚接线手册_RevI.pdf`
一并拷进 `doc\`。脚本从 PDF 原文解析「针号 → 网络 → J1正式Pin」，再与 `constr\falcons.cst` 里
**实际生效的 IO_LOC** 逐针比对。

| 覆盖 | 根数 | 结果 |
| --- | --- | --- |
| J4/J5 电机 + 编码器 | 21 | ✅ 全部一致 |
| J2 IMU SPI | 4 | ✅ 全部一致 |
| **J7 ToF（本次扩展）** | 4 | ✅ 全部一致 |
| **J6 遥控（本次扩展）** | 6 | ✅ 全部一致 |
| 引脚唯一性 | 60 个引脚 | ✅ 无重复 |
| 注释 `J1.xx` 核对 | 12 条 | ✅ 0 条不符 |

#### ★ 复验抓到的真缺陷：顶层把 J7 的 SDA/SCL 误当成"ToF 回波 + RK3588 串口"

| J7 针 | 手册功能 | 网络 | 原来错用成 |
| --- | --- | --- | --- |
| 3 | **SDA** | E17 | `i_tof_echo`（ToF 不是 echo 型传感器，它是 I2C 器件） |
| 4 | **SCL** | F16 | `o_rk_tx`（RK3588 串口 TX） |
| 5 | INT | C20 | `i_rk_rx` |
| 6 | SHUT | D20 | 未使用 |

已修正为正确的 I2C 四线语义（`o_tof_scl` / `io_tof_sda` / `i_tof_int` / `o_tof_shut`）；
ToF 模块未做出期间置**安全空闲态**（SCL 高、SHUT 高、SDA 高阻）。

**连带结论（影响 L6 规划）**：手册里**没有 RK3588 专用接口**，而 J1 的 11 个 GPIO
已被遥控(6) + ToF(4) + 雷达(1) 占满 → **RK3588 通路没有可用 GPIO**，必须改走
USB2.0（30 根）或以太网 RGMII（15 根）。原先参数表里"RK3588 走串口"的假设作废（Q9 已更新）。

#### 复验脚本本身踩的两个解析坑（供后续扩表参考）

1. **J6 在手册里是左右两栏交错排版** —— 通用的四列正则只能吃到一半（实测只解析出 **3 针而非 6 针**）。
   改用 `finditer` 在一行里同时捞左右两栏，并优先保留带 `J1Pin` 的那条。
2. **J6 左栏没有 J1Pin 列** —— 注释核对时 `int("")` 会崩，需跳过空值。

> 教训：**"校验通过"不等于"校验充分"** —— 第一次跑就 exit 0，但 J6 只覆盖了 3/6 根。
> 后来核对"手册解析出的针数是否符合预期"（J6 应为 6）才发现。以后扩表都要先断言针数。

### 1. A1 启动门禁 + 油门中位死区（★ 用户点名）

**问题**：原来只有一行

```verilog
if (key1_press && !estop_latch) run_en <= ~run_en;
```

只要没急停，按 S1 就启动。若上电时**油门杆恰好停在半位**，一按 S1 车立刻窜出去 ——
上板第一次测试最怕的就是这个。

**改法**（`rtl\top\falcons_top.v`）：

```verilog
localparam integer ARM_THROTTLE_DEADZONE = 100;   // 归一化 ±1000 的 10%
wire throttle_centered = (rc_throttle <= ARM_THROTTLE_DEADZONE) &&
                         (rc_throttle >= -ARM_THROTTLE_DEADZONE);
wire arm_ready = throttle_centered & rc_signal_ok;
wire arm_hint  = ~run_en & rc_signal_ok & ~throttle_centered & ~estop_latch;

if (key1_press) begin
    if (run_en)         run_en <= 1'b0;       // 停止：任何时候都允许
    else if (arm_ready) run_en <= 1'b1;       // 启动：必须过门禁
end
```

**为什么用死区而不是判 `== 0`**（用户点名的原因）：归一化油门是连续量，
摇杆回弹误差 + 接收机中位漂移会让"精确等于 0"**永远不成立**，那样门禁就等于"永远不能启动"。
死区 100 与 `rc_input` 自身的 `DEADZONE_US`(25 µs) 叠加后，允许的中位误差约 ±15% 行程。

**可见反馈**：状态栏新增 `请回中位`（字表加 `ST_ARM_DENY:请回中位`，文案 73 → **74 条**）。
注意**字库字符数没变（仍 223）**：这轮加的"请/回/中/位"四个字在字库里**都已存在**
（"请"来自"请选择模式"、"回"来自"返回"、"中"来自"标定中"、"位"来自"航位"），
所以 `font_rom.v` 内容不变（git 无 diff）、只有 `ui_text_rom.v` 与 `ui_text_index.vh` 变了。
字库字符数以 `font_rom.v` 的 `CHAR_COUNT` 为准。
不做提示的话，用户只会看到"按 S1 没反应"，会误判成坏了。
状态栏优先级：**急停 > 无信号 > 请回中位 > 手动 > 自动 > 请选择模式**。

**安全取向**：**停止不受任何门禁限制** —— 任何时候按 S1 都能停 ✗ 等价于"只能更难启动，不会更难停止"。

### 2. A2 串口 CSV 8 列 → 12 列

**为什么**：调遥控时 CSV 里全是轮速链路的量（tgt/act/duty/PID），**看不到"杆位 → 归一化值"这一环**。
轮速不对时无法判断是"遥控进来的值就不对"还是"PID/底盘的问题"。

新增 4 列（前 8 列顺序不变，便于与旧数据对照）：
`tgt,act,duty,kp,ki,kd,flags,err,`**`steer,throttle,mode,sig_ok`**

**实现要点与坑**：

| 点 | 说明 |
| --- | --- |
| `field` 位宽 3 → **4** | 3 位只能表示 8 个字段（0~7），第 9~12 列**永远发不出来**，且不会报任何错 |
| `S_SEP` 末字段判断 `3'd7` → `4'd11` | 漏改的表现是"列还没发完就换行"（少列） |
| `FIFO_DEPTH_LOG2` 5 → **7** | 12 列一行最长 ≈96 字符；库默认 32 字节 FIFO 会让状态机频繁等空位（不丢数据但吞吐受限） |
| 依赖闭包 | `speed_report` → `uart_tx_queue` → { `uart_byte_tx`, `sync_fifo` }，**两层** |

### 3. A3 堵转启动宽限 30 → 50 窗口

库默认 `STALL_STARTUP_WINDOWS = 30`（= 300 ms @10 ms 窗口）是给小惯量电机调的。
本车 30:1 减速 + 整车质量，从静止到目标转速需要更久，**300 ms 内位移不足会被误判堵转并锁存** ——
上板时表现为"一按 S1 就报堵转、车不动"，很容易误判成电机或驱动坏了。改为 **50（500 ms）**。

### 7. ★ 遥控死区接口归属核对（用户提出："接收模块好像带死区接口"）

**用户记得没错，但在另一个模块里**。核对结果：

| 模块 | 路数 | 死区 | 反向 | 每路独立中位 | 本工程 |
| --- | --- | --- | --- | --- | --- |
| `rc_pwm_capture` | 1 路（纯捕获） | ✗ 无 | ✗ 无 | ✗ 无 | **在用**（6 路 ×实例化） |
| `rc_receiver` | 2 路（转向+油门） | ✓ `CHn_DEADZONE_US`(25) | ✓ `CHn_REVERSE` | ✓ `CHn_CENTER_US` | 未用 |

**为什么没用 `rc_receiver`**：本车需要 6 路 —— 除转向/油门外还有 4 个开关/按钮通道，
它们要的是**三档判定**（`<1300` / `1300~1700` / `>1700`）与**按钮上升沿**，`rc_receiver` 覆盖不了。

**语义是否一致**（重要）：`rc_receiver` 的死区是"死区外**重新拉伸**到满量程"
（`(disp-dz)*1000/(max-center-dz)`），`rc_input` 的实现**同语义**（`m = |d| - DEADZONE_US` 后 ×2.125）。
差别只在实现手段：**移位加法 ×2.125**（误差 0.95%）vs **整数除法**。
选前者是因为这条路径曾经 setup slack = −7.02 ns（`u_rc/o_steer` → chassis 乘法链），
换移位加法后才满足时序。

**决策（用户选 A：保持现状先上板实测）**：`rc_receiver` 唯一更强的是"每路独立中位"。
若实测发现某一路中位偏得多（例如油门总在 +40），再给 `rc_input` 补每路独立中位参数；
**启动门禁的死区（±100 ≈ ±10% 行程）本身已能覆盖常见中位漂移**，所以不阻塞上板。

### 8. CDC 深组合路径消除（本轮引入的时序退化，已修）

**发现过程**：本轮综合后 `Numbers of Setup Violated Endpoints` 是 103（上一轮记的是"2 条"）。
先把口径查清楚 —— 解析 `falcons_tr_content.html` 的路径表后发现：

- 上一轮口径是**路径条数**（`report_timing -max_paths 25` 里的负 slack 条数）
- 那一栏是**违规端点数**（一个 2 位总线的两位各算一个端点、RAM 每一位各算一个）

但**路径表确实是退化了**，而且最差那条正是本轮新加的：

| 排名 | 上一轮 slack | 路径 | 本轮 slack | 路径 |
| --- | --- | --- | --- | --- |
| 1 | −2.473 | `u_rc/…/timed_out_s1/Q` → **`arm_ps1_s0/D`** | **−0.993** | `arm_s_s0/Q` → `arm_ps1_s0/D` |
| 2 | −2.199 | 同上 → `sig_ps1_s0/D` | −0.796 | `sig_s_s0/Q` → `sig_ps1_s0/D` |
| 3/4 | −1.585 / −0.945 | `u_rc/o_mode_*` → `mode_ps1_*` | −0.991 / −0.897 | `mode_s_*` → `mode_ps1_*` |
| 5 | −0.404 | `estop_latch_s1/Q` → `estop_ps1_s0/D` | −0.995 | `estop_s_s0/Q` → `estop_ps1_s0/D` |

**根因**：跨域**源是组合逻辑**，组合深度被 STA 算进 slack：
- `arm_hint = ~run_en & rc_signal_ok & ~throttle_centered & ~estop_latch`（含一个 12 位比较器）
- `rc_signal_ok` = 6 路 `timed_out` 相或（在 `rc_input` 内部）

**修法**：在 **sys 域先打一拍**再跨域（顶层加 `page_s/mode_s/run_s/estop_s/sig_s/arm_s`）。
源变成 DFF 输出、组合深度归零，同步器第一级的 slack 回落到与纯 DFF→DFF 同量级
（−2.473 → **−0.998**，改善 1.48 ns）。代价是延迟 1 个 50 MHz 周期 —— 这些都是"人操作级别"的慢变量。

> 为什么不加 `set_false_path` 消掉这些违规：`pixel_clk` 是 `hdmi_1024x600` 内部 PLL 的派生时钟，
> **约束解析阶段还不是时钟对象**，用 `get_clocks {pixel_clk}` 会直接 `ERROR (TA2004)` 让综合失败
> （第六节已记录过这次失败）。打拍是**物理改善**，不依赖约束是否生效，更稳。

## 十六、写入 PID 参数 P=0 / I=64 / D=0（2026-10-16）

**指令**：用户直接给值 —— "写入PID参数，P=0，I=64，D=0"。

### 1. 动手前先核对口径（这一步不能省）

工程里的 PID 参数是**定点 Q8**，`rtl\motor\speed_pid.v` 文件头写得很明确：

> 【定点格式】全部 Q8（256 = 1.0）
> Kp/Ki/Kd 为 int16 的 Q8 值：0.05 → 13，0.1 → 26，1.0 → 256

所以"64"按 Q8 解是 **0.25**，按实数解是 **64**（差 256 倍）。
结合原值（`KP_INIT = 26` 注释就是"0.1"）与 `car_fpga` 的历史记录（26/3/0 同口径），
判定用户给的三个数就是**工程参数的 Q8 原值**，按下表写入。

### 2. 写入内容（`rtl\top\falcons_top.v` 顶部 `localparam`）

| 参数 | 写入值（Q8） | 实际值 | 原值 | 变化 |
| --- | --- | --- | --- | --- |
| `KP_INIT` | **0** | Kp = 0.0 | 26（0.1） | 比例项关掉 |
| `KI_INIT` | **64** | Ki = 0.25 | 3（0.012） | **21 倍** |
| `KD_INIT` | **0** | Kd = 0.0 | 0 | 不变（先关微分，编码器量化噪声会被放大） |

即 **纯积分控制**（PI 但 P=0）。增量式 PID 的公式里 Kp 只作用于误差差分项
（`Kp × (e(k) − e(k−1))`），P=0 时该项消失、只剩 `Ki × e(k)` —— 这是常见做法，
低速时对量化噪声不敏感，代价是响应慢、靠积分慢慢磨掉稳态误差。

### 3. 量级提醒（已同步写进代码注释）

Ki 从 3 提到 64 是 **21 倍**，每个 10 ms 窗口的增量：

```
Δu = Ki × err / 256 = 64 × err / 256 = err / 4
```

- 误差 100 rpm → 每窗口 **+25**、每秒 **+2500**
- 占空比满量程只有 **2047**（`PWM_BITS = 11`）→ **约 0.8 s 就会积分饱和**

CSV 的 `flags` 列 **bit3 就是 PID 饱和标志**，上板时可以直接用它判断。
若表现为"起步猛冲 / 到速后来回振荡"，先把 Ki 降回来（例如 8 / 16 / 32）再试。

### 4. 只改顶层，没动库默认值

`rtl\motor\speed_pid.v` 里也有一套同名默认值（`26/3/0`），但顶层是这样例化的：

```verilog
chassis_ctrl #(
    .KP_INIT (KP_INIT), .KI_INIT (KI_INIT), .KD_INIT (KD_INIT)
)
```

**显式覆盖**，所以库默认值在本工程不参与 —— 实际生效值**只以顶层这三个 `localparam` 为准**。
这也是"同一事实只在一处定义"的体现：避免"改了顶层却以为库默认值也在起作用"。

## 十七、改 PID 后的重新综合与新位流（2026-10-16 01:46:55）

**为什么必须重新综合**：PID 初值是 `localparam`，综合期就**硬化进了位流**。
不重新出位流的话，烧进去跑的仍是 26/3/0 —— 这是"改了参数但板上没变"最常见的原因。

| 项 | 上一轮（A/B 补全后，01:26:49） | 本轮（PID = 0/64/0，**01:46:55**） |
| --- | --- | --- |
| 位流 | 34.2 MB | **34.2 MB** |
| Logic | 9081 | **9082**（+1） |
| Register | 4092 | 4092 |
| BSRAM / DSP / IOLOGIC | 9 / 41 / 8 | 9 / 41 / 8 |
| **SETUP** | 0 违规（最差 +0.746 ns） | **0 违规（最差 +0.259 ns）** |
| HOLD | 12（最差 −0.998 ns） | 12（最差 −1.026 ns） |
| RECOVERY | 25（最差 −5.292 ns） | 25（最差 **−4.456 ns**） |
| REMOVAL | 0 | **0**（最差 +0.252 ns） |
| 仿真回归 | 5 tb / 87 项 PASS | 5 tb / 87 项 PASS |

**怎么读这张表**：

- **SETUP / REMOVAL 全部满足** —— 同域逻辑没有时序问题。
- HOLD 12 条与 RECOVERY 25 条仍是**跨时钟域同步器第一级**与**上电复位路径**，
  与 PID 参数无关（结构性现象，来龙去脉见第十五节 §15.10）。这两类数字每次综合会小幅浮动，
  属 PnR 启发式布局的正常波动（−0.998 → −1.026、−5.292 → −4.456）。
- **P=0 没有让资源下降**（DSP 仍是 41）：PID 参数是**运行时可变的端口**（支持串口 `P/I/D` 在线改），
  乘法器必须保留，工具不会因为"初值为 0"就把它优化掉。

### 20.7 追加：CDC / 复位修正（方案 A）与重新综合结果

**背景**：需求方问"`.sdc` 的 CDC/复位约束未做是什么意思"。解释清两件事的性质差异后
（CDC 的 13 条 HOLD 是**结构性伪违规**；RECOVERY 是**真实违规**），需求方选定 **方案 A**：
把 `u_hdmi` 的复位从 sys 域改到像素域自产，而不是用 `set_false_path` 掩盖。

**动手前的安全检查（重要，避免死锁）**：`pixel_rst_n` 依赖 `pll_lock`，若 `hdmi_1024x600`
拿 `reset_n` 去复位 **PLL 自己**就会成环（不锁→不复位释放→永不锁）。读 vendor 源码确认**不成环**：
`display_pll u_display_pll` 的端口只有 `.lock / .clkout0 / .clkout1 / .clkin`（**没有 reset 端口**），
`reset_n` 只进 `disp_driver.Rst_n` 与 `DVI_TX_Top.I_rst_n`（两者都是 `reset_n & pll_lock`，pixel/串行域）。

**改了什么**（`rtl\top\falcons_top.v`）：
- `u_hdmi` 的 `.reset_n` 由 `sys_rst_n` → **`pixel_rst_n`**（域内自产：PLL 锁定后计数到 bit3 释放；
  释放沿是 pixel 域 DFF 输出 → 对像素域是同步释放）
- 把 `pixel_pwr_cnt` / `pixel_rst_n` 的声明**移到 `u_hdmi` 例化之前**
  （否则例化处会被当成隐式 1 位 net，后面再声明就是"重复声明"）
- 顺手把 `rc_signal_ok` 注释里的"6 路"改成"参与判定通道"

**重新综合（2026-10-16 18:36:19，ERROR 0）**：

| 指标 | 改前（02:21:19） | 改后（18:36:19） |
| --- | --- | --- |
| RECOVERY 违规条数 | 25 | **8**（−68%） |
| RECOVERY 最差 slack | −4.282 ns | **−5.869 ns**（变差） |
| SETUP 最差 | +0.569 ns | **+0.092 ns**（余量变紧，仍满足） |
| HOLD | 13 条（−1.019） | 13 条（−1.026） |
| REMOVAL | 0 条 | 0 条（+0.267） |
| Logic / Register | 9136 / 4243 | **8705 / 4113** |
| 复位源头 | sys 域（与 pixel 完全异步） | pixel 域（与 245 MHz 同源、相位固定） |

**结论：方案 A 达到了"减少违规"但没达到"清零"，而且最差 slack 数字变差** —— 如实记录：

- 我原先的预期是"RECOVERY 清零"，**实际没有**。原因是我对路径的判断不完整：目标
  `u_OSER10_*/RESET` 属于 **245 MHz 串行域**（`CLKOUT1`），不是 49 MHz 像素域 ——
  而顶层**拿不到 245 MHz 时钟**（`hdmi_1024x600` 只输出 `pixel_clk`），无法在其域内做同步释放；
  另外 vendor 内部是 `reset_n & pll_lock`，`pll_lock` 本身就是异步信号。
- "条数大减、最差更差"的解释：**245 MHz = 49 MHz × 5**，同源且相位固定 → 释放沿相对串行时钟的
  位置**确定**，一部分路径恰好满足（违规消失），剩下 8 条落在确定的不良相位上。
  `−5.869 ns` 已超过一个 245 MHz 周期（4.08 ns），物理含义更接近"**复位晚一拍释放**"（功能上无害），
  而不是随机亚稳态 —— 这与 `car_fpga` 阶段同结构实测 HDMI 正常一致。
- **附带代价**：SETUP 余量从 +0.569 压到 **+0.092 ns**（0.46%），仍满足但很紧，后续加逻辑要留意。
- **附带收益**：复位源头统一为域内自产（消除了"sys 域复位直接进 pixel 域"的结构）；
  违规条数 25→8；Logic 9136→8705（含删返回按钮链路与死信号）。

**顺带取得的可复用信息**（写进了 `constr\falcons.sdc` 注释）：PLL 派生时钟的**真实对象名** ——
`u_hdmi/u_display_pll/PLL_inst/CLKOUT0.default_gen_clk`（49 MHz）、
`.../CLKOUT1.default_gen_clk`（245 MHz）。将来若要写 `set_clock_groups -asynchronous` 直接用这两个名字，
不必再猜（此前按端口名 `pixel_clk` 写会报 TA2004）。**但要清楚：它只能消掉 HOLD 的 13 条噪音，
消不掉 RECOVERY 那 8 条**（复位释放是真实功能路径）。

**裁定（2026-10-16 晚，需求方）**：**保留**本次改动（`u_hdmi.reset_n ← pixel_rst_n`）；
**不动 vendor 内部**（不为了清零 RECOVERY 去改 `hdmi_1024x600.v`）；
**不加时序例外**。判据不是 slack 数字，而是**上板实测**：HDMI 稳定点亮即按"分析模型偏严"归档；
只有出现"偶发不点亮"才回头考虑在 245 MHz 域做同步释放。

### 21.7 本次踩的新坑（都已写进 `sim\README.md`）

1. **`fork` 里的多个 task 调用是并行的**：想"连发 N 帧"必须用 `begin…end` 包住，
   否则 N 个分支同时拉高/拉低、等价于只发一帧 —— 表现是"**帧确认类断言永远不通过**"（我为此查了一轮）。
2. **编译库的工作目录要对**：`vlog -work work_sim` 是相对**当前目录**建库的；在工程根编译却在 `sim\`
   下 `vsim`，会各用一套库 → 出现"改了代码结果不变"的假象（我误判过一次）。
3. **`edit` 类工具会丢 `.ps1` 的 BOM**（本轮第二次踩到）：改完 `run_sim.ps1` 后 PowerShell 报
   `Unexpected token` + 中文乱码；按"读字节判 BOM → `UTF8Encoding($true)` 写回"修复。
4. **我算错了掩码的位序**：把 `6'b101111` 当成"排除 bit5"，其实它排除的是 **bit4**
   （`6'b101111` 的 MSB 才是 bit5）。正确的是 **`6'b011111`**。**位序类常量必须用测试锁住**（见 21.6）。
