# 时序违例分析（2026-10-21）

按《FPGA RTL 时序优化通用经验》（下称"方法论"）对基线 `048ec3f` 起的一系列时序报告做逐条复查，
给出违例分组、根因、试过的方案与实测结论。**数据全部来自 PnR 实物报告，不用综合估计代替。**

## 1. 数据来源与口径

| 来源 | 内容 |
| --- | --- |
| `impl\pnr\falcons_tr_content.html` | TNS Summary、Max Frequency Summary、Setup/Hold 表（各 25 条）、高扇出网、拥塞 |
| `impl\pnr\falcons.timing_paths` | 50 条路径（25 setup + 25 hold）的完整级联，含每级到达/离开时间 |
| `impl\gwsynthesis\falcons_syn.rpt.html` | 综合阶段 `Detail Timing Paths Information`（早期判断用，**不作结论依据**） |
| `constr\falcons.sdc` | 约束文件（第 2 节改造过） |

方法论 §8 第 4 条：综合估计只用于早期判断，**最终以 PnR 为准**。实测同一版 RTL 综合报
39.777 MHz、PnR 报 47.567 MHz，差 19%，绝对值不可信。

## 2. 约束改造：让跨时钟域能被分析（唯一保留的净收益）

**问题**：PLL 输出的 generated clock（`u_hdmi/.../CLKOUT0.default_gen_clk` 等）在 SDC 解析阶段
不在时钟库里，`set_clock_groups` 写入即报 `ERROR (TA2004): Cannot get clock with name ...`，
于是**所有跨域路径都按同步关系分析**，产生 84 条 setup + 2605 条 hold 伪违规。

**办法**：用 `create_generated_clock` 自己命名（`-source` 填上一级时钟的源端口，`-divide_by`
按 PLL 的 IDIV/ODIV 填），再用 `set_clock_groups -asynchronous` 分组。写在 `constr\falcons.sdc` 末尾。

| 时钟名 | 定义 | 频率 |
| --- | --- | --- |
| `clk_pixel` | `-source [get_ports {i_clk_50m}] -multiply_by 49 -divide_by 50`，源 `u_hdmi/u_display_pll/PLL_inst/CLKOUT0` | 49 MHz |
| `clk_serial` | 同源 `-multiply_by 49 -divide_by 10`，源 `.../PLL_inst/CLKOUT1` | 245 MHz |
| `clk_cam200` | `-source [get_ports {i_clk_50m}] -multiply_by 4`，源 `u_cam/u_system_pll/PLL_inst/CLKOUT0` | 200 MHz |
| `clk_cam50` | 同源 `-multiply_by 1 -divide_by 1`，源 `.../PLL_inst/CLKOUT1` | 50 MHz |
| `clk_ddrf` | `-source [get_pins {u_cam/u_system_pll/PLL_inst/CLKOUT0}] -divide_by 4`，源 `DDR3_Memory_Interface_Top/.../fclkdiv/CLKOUT` | 50 MHz |

分**四组**：`i_clk_50m` / `camera_pclk` / `clk_pixel clk_serial`（像素与串行必须同组，5:1 同相）/
`clk_cam200 clk_cam50 clk_ddrf`。

**效果**：Hold 违例 **2605 → 18**（−99.3%），Setup 84 → 62，`default_gen_clk` 全部消失，
真违例（4 条）**数字一个都没变**。

**代价**：`clk_ddrf` 被显式定义后，DDR3 IP 内部 8 条 `u_dll/CLKIN → dll_step_base_*` 路径
（−3.4 ~ −3.8 ns）开始被分析。它们在基线里因 `TA1132`（时钟未创建）**根本没被分析**，
属于"从看不见到看见"，且由 IP 自身保证，不加假路径掩盖。

**结论**：Fmax 不动（本来就该如此——约束只影响分析，不影响布局），但报告从
`84 setup + 2605 hold` 缩到 **22 条真实路径**，优化目标因此可见。**这是本次唯一的净收益。**

## 3. 违例全貌（B 实验后的口径）

| 类别 | 数量 | 真实性 |
| --- | --- | --- |
| Setup 违例端点 | 62 | 8 条 DDR3 DLL + 50 条下降沿（245M 串行域）+ 4 条真违例 |
| Hold 违例端点 | 18 | 跨域残余 |
| **真违例** | **4 条** | sys 1 条 −0.107 ns、pixel 3 条合计 −0.193 ns |

TNS Summary 只有两处非零，与上表自洽：

```
i_clk_50m   Setup  -0.107   1 endpoint
clk_pixel   Setup  -0.193   3 endpoints
```

两个 Fmax：`1/(20.000+0.107)=49.733`、`1/(20.408+0.193)=48.807`。

## 4. sys 域：根因是控制依赖，不是算术位宽

`falcons.timing_paths` 里这条路径的完整级联（到达 23.270 ns / 要求 23.163 ns）：

```
rx_buf[6]_6_s0      3.832 → 4.176
gyro_x_cs_31_s0     4.730 → 7.035    ×25000>>>12          2.31 ns
dev_x_1_s           7.844 → 8.380    gyro − mean          1.66 ns
adev_x_5 .. _30_s0  8.889 → 13.944   |dev| 三轴求和        5.05 ns / 14 级
n2222_s             14.995 → 15.698  < CALIB_DEV_TH       1.56 ns
calib_cnt_31_s12    16.692 → 17.203  calib_cnt + 1        2.07 ns
calib_done_r_s6     19.196 → 19.455
n6432_s41/n6434_s44 19.865 → 21.415
n3913_s             23.270           终点
```

对应 RTL（`vendor/.../imu660ra/rtl/imu_top.v:367-373`）：

```verilog
wire calib_still = calib_in_range && ((adev_x + adev_y + adev_z) < CALIB_DEV_TH);
wire calib_accum = (!calib_seed_done) || calib_still;   // ← 累加器的使能
```

**累加器的使能被一条与它无关的抖动判据链阻塞**，正是方法论 §1 表格第一行
「多级条件判断后接 CE」与 §2「减少不必要的控制依赖」的典型。

A1 实验（`calib_sum` 48→32 位）失败的原因由此清楚：**数据加法器根本不在关键路径上**，
缩位宽不改变使能链长度。方法论 §1 已明确不宜下"只要减少算术位宽就能解决"的结论。

## 5. pixel 域：位选链串在除法器后面

B 实验让这 3 条终于可见（此前被 `-max_paths 25` 截断）：

```
−0.080  u_hdmi/u_disp_driver/hcount_r_3_s0/Q → u_hdmi/u_disp_driver/Disp_Green_3_s0/D   20.437 ns
−0.061  u_hdmi/u_disp_driver/hcount_r_3_s0/Q → u_hdmi/u_disp_driver/Disp_Green_4_s0/D   20.458 ns
−0.052  u_hdmi/u_disp_driver/vcount_r_0_s0/Q → u_dyn_text/o_rdata_3_s0/D                20.385 ns
```

Data Delay 均 ≈ 一个周期，说明是**纯组合直通**。前两条的链路是：

```
hcount_r → x_look(+2) → lg_slot(÷24) → lg_slot_x24(移位加法) → lg_col_look(减法)
        → lg_col(条件减) → lg_bit_sel(23−) → 24→1 位选 mux → o_rgb → Data → Disp_Green/D
```

`ui_render.v:560` 的 `lg_bit_sel = 5'd23 - lg_col[4:0]` 必须用**当前像素**的列号，所以这条链
无法被两级 ROM 的流水吸收。`lg_col` 原先由 `lg_slot` 回算（除法 → 乘 24 → 减 → 条件减），
是整条链最长的一段。

第三条 `vcount → u_dyn_text/o_rdata` 走 `sm` 通路：`vcount → sm_sel(6 路比较) → sm_ram_rd(加法)
→ i_raddr → LUTRAM 异步读 → o_rdata/D`（`dyn_text_ram` 只有 64×8=512 bit，被综合成分布式 RAM）。

## 6. 试过的方案与实测结果

四次改动，**全部负优化，全部已回退**。每次都跑全量仿真 + `build.tcl`（run all）。

| 实验 | 改动 | 仿真 | Fmax(50M) | Fmax(pixel) | 同域违例 | 结论 |
| --- | --- | --- | --- | --- | --- | --- |
| 基线 | `048ec3f` | 19/19 PASS | 49.733 | 48.807 | 4 条 | 参照 |
| A1 | `calib_sum` 48→32 位 | PASS | 47.567 | 46.701 | 15 条 | 负优化，回退 |
| B1' | `x_look/24` 换移位加法 | PASS | 47.567 | 46.701 | 15 条 | 负优化，回退 |
| 步 1 | pixel 位宽收敛 12→6 | PASS | 47.860 | 47.385 | 11 条 | 负优化，回退 |
| 方案 A | `lg_col` 与 `lg_slot` 解耦 | PASS | **48.489** | **47.613** | 16 条 | 负优化，回退 |

> A1 与 B1' 是同一版 PnR，两个数字无法单独归因——这正是方法论 §8
> 「组合成功不能证明单项有效」的反面教训。

### 6.1 方案 A 的细节（最值得记录的一次）

代数上 `lg_col = i_pixel_x mod 24`，而 `24 = 8 × 3` 给出与除法器无关的算法：

```
x mod 24 = 8 × (⌊x/8⌋ mod 3) + (x mod 8)
```

`⌊x/8⌋` 是接线移位、`x mod 8` 取低 3 位，只剩 `n mod 3`（偶位系数 1、奇位系数 2 加权和，再循环减 3）。
**目标路径确实消失了**：改动后 Setup 表里再没有 `hcount_r → Disp_Green`；
但**原本 −0.052 的 `vcount → u_dyn_text/o_rdata` 恶化到 −0.594 / −0.557**，
同时冒出 `u_imu/rx_buf[9]_2 → n3913_s/A[2]`（−0.623）和
`u_nav_ctrl/n1093_s → cut_ok_r_s0`（−0.588）。

**这就是方法论 §4 预警的"局部路径缩短后，其他近临界路径接替成为全局瓶颈"**。
pixel 域属于 §3「多类路径同时接近临界值」——同族还有 4 条 +0.066~+0.201 的路径排在后面，
动一条就会把另一条推过线。

## 7. 结论与建议

1. **4 条真违例的缺口只有 0.4% ~ 0.5%**（−0.107 / −0.193 ns，周期 20 ns / 20.408 ns）。
2. **四次改动每次都让整体更差**，共同原因是**布图扰动**：只要 RTL 变动就整体重排，
   把本来达标的模块（`nav_free`、`odom`、`imu`、`nav_ctrl`）推过线。
3. **可做的净收益只有第 2 节的 SDC 改造**：把 2605 条 hold 伪违规清成 18 条，
   让真实瓶颈可见。它不改逻辑，所以不改 Fmax，但让报告可用。
4. 若要真正消除这 4 条，需要**成组改动**（同时处理 pixel 域同族的多条近临界路径），
   而不是单点优化；或接受现状——`i_clk_50m` 实际 49.733 MHz、pixel 实际 48.807 MHz，
   相对约束分别差 0.53% 和 0.39%，在器件温度与电压裕量内通常可正常工作，
   但**这属于工程判断，不是时序报告能保证的结论**。
