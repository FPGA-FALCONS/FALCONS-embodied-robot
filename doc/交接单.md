★ **A1 / B1' / 步1 / 方案A 四条已全部回退**（2026-10-21 02:21 重建位流，时序逐项回到基线）。教训一句话：**不要从逻辑结构推断瓶颈**——综合器能把常数除法压得很浅，手写分解换来的是一串 LUT 级联；而且 **P&R 对布图扰动极敏感，未改动的模块也会被推过线**。改动前务必先读 `工作记录.md` §76、§77。**pixel 域属于「多条近临界路径并存」，单点优化一定会被下一条接替；要动就得成组动。**

★ **做这类改动的三条纪律**（来自 §74 / §75 的实测教训）：

1. **一次只改一处，每一步都单独综合。** §74 那次三处齐改，结果互相掩盖，三处全被判为负优化、整体回退，白跑三轮。
2. **判断有效性前先确认两版输入是否逐字节相同。** §74 里我因为 ② 还在就断定「布局随机、13 条是运气好」，是无效对照；后来 22:28:15 用逐字节相同的 RTL 重综合，位流大小、六时钟 Fmax、两域 TNS、每条 slack 全部复现，才证明综合器是确定性的。
3. **改完必须能说清「哪些条消失了」，而不只是总数下降。** §75 里 ② 的收益能确定归因，是因为 `odom → nav_free/mult` 那 7 条在报告里彻底消失；而 ③ 之后 imu 与 pixel 域的条数也跟着变（11 → 4），所以那一步的收益无法与全局重布局分离，只能记「合计改善」。
