<a id="601-两条修法rtl-已改"></a>
### 60.1 两条修法（RTL 已改）

**① `rtl\motor\speed_pid.v`：给误差与反馈有效各打一拍。**

原先 `err_lim` 由 `i_fb` 组合算出后**当拍**直接进三条乘法，
`delta_r → o_u` 是一条 20.82 ns 的单周期组合链。改法是把误差锁进寄存器，
乘法改用锁存值，代价是 `o_u` 晚一拍：

```verilog
reg signed [15:0] err_lim_r;
reg               fb_valid_d1;
always @(posedge i_clock or negedge i_reset_n) begin
    if (!i_reset_n)      begin err_lim_r <= 16'sd0; fb_valid_d1 <= 1'b0; end
    else if (!i_enable)  begin err_lim_r <= 16'sd0; fb_valid_d1 <= 1'b0; end
    else                 begin err_lim_r <= err_lim; fb_valid_d1 <= i_fb_valid; end
end
wire signed [16:0] d1 = err_lim_r - e1;
wire signed [17:0] d2 = err_lim_r - (e1 <<< 1) + e2;
wire signed [39:0] du_sum = (i_kp * d1) + (i_ki * err_lim_r) + (i_kd * d2);
```

`o_u` 的更新条件从 `end else if (i_fb_valid)` 改成 `end else if (fb_valid_d1)`，
`o_err` / `e1` 也改用 `err_lim_r`。

★ `fb_valid_d1` 是**必需的数据配对条件**，不是随手加的：
`i_fb_valid` 是 1 kHz 的单拍脉冲，而 `err_lim_r` 要下一拍才拿到本帧误差。
若仍用 `i_fb_valid` 作更新条件，就会在"新使能 + 旧误差"那一拍输出一次错值。

**② `rtl\top\falcons_top.v`：gyro 补偿值流水一级（不动 vendor 的 `gyro_tilt_comp`）。**

```verilog
reg signed [31:0] gyro_z_comp_r;
reg               imu_data_valid_d1;
always @(posedge i_clk_50m or negedge sys_rst_n) begin
    if (!sys_rst_n) begin gyro_z_comp_r <= 32'sd0; imu_data_valid_d1 <= 1'b0; end
    else begin gyro_z_comp_r <= gyro_z_comp; imu_data_valid_d1 <= imu_data_valid; end
end
// u_yaw: .i_gyro_z(gyro_z_comp_r), .i_sample_valid(imu_data_valid_d1)
```

★ **`i_gyro_z` 与 `i_sample_valid` 必须同步延后**。只延后数据不延后使能，
`u_yaw` 会在"本帧使能 + 上一帧补偿值"那一拍采样 —— 引入的偏差比时序违约更糟。
已确认 `imu_data_valid` 只被 `u_yaw` 消费；`gyro_z_comp` 另有一处给 `gyro_deg_s` 显示用，
差 20 ns 无影响。

<a id="604-上板反馈的两个-bug-与修法"></a>
### 60.4 上板反馈的两个 bug 与修法

<a id="6041-两个三档开关的上下方向都反了"></a>
#### 60.4.1 两个三档开关的上下方向都反了

现象（需求方原话）："两个三档开关的上下方向反了"。
即 CH5 下拨执行了"返回"、上拨执行了"确认"；CH8 上拨执行了"向下切"、下拨执行了"向上切"。

修法：**只改 `falcons_top.v` 里 `u_rc` 例化的两个极性参数，不动 `rc_input.v` 的译码逻辑**。

| 参数 | 改前 | 改后 |
| --- | --- | --- |
| `CONFIRM_ACTIVE_LOW` | `1` | **`0`** |
| `AUX_SWAP` | `0` | **`1`** |
| `MODE_REVERSE` | `0` | `0`（CH7 两档方向本来就对） |

这条约定要一直保留：**开关方向反了就是翻这两个参数之一，不要动 `classify()`**。
译码逻辑（±30 µs 迟滞 + 2 帧确认）是共用的，翻参数只是换"哪一档算高"。

<a id="6042-退出导航交互态后无法立即再进入"></a>
#### 60.4.2 退出导航交互态后，无法立即再进入

现象（需求方原话）："进入导航页面再推出，然后无法立即再进入导航页面，
必须先进入其他界面才能再进入导航页面。"

**根因**：`nav_free_ctrl.v` 里 `ui_active` 只有一个置位来源 `enter`：

```verilog
wire enter = i_active & ~active_d;      // page 进入本页的上升沿
```

而退出交互态（按返回）只清 `ui_active`、**不改变 page**。于是 `active_d` 一直为 1，
`enter` 再也不会产生 → 只能靠切页制造 `i_active` 下降沿把 `active_d` 清掉，
再切回来时才有新的上升沿。这个"必须先绕一圈"就是 bug 的表现。

**修法**：允许"已在本页、已退出交互态"时按确认重新置位：

```verilog
reg ui_active;
wire reenter = i_active & ~ui_active & i_confirm;
always @(posedge clk or negedge rst_n) begin
    if (!rst_n)                  ui_active <= 1'b0;
    else if (i_clear)            ui_active <= 1'b0;
    else if (!i_active)          ui_active <= 1'b0;
    else if (enter)              ui_active <= 1'b1;
    else if (i_back && (o_nav_state != ST_RUNNING)) ui_active <= 1'b0;
    else if (reenter)            ui_active <= 1'b1;
end
```

★ `wire reenter` 必须声明在 `reg ui_active` **之后** —— 否则 `vlog` 报
`vlog-2730 Undefined variable: 'ui_active'`（第一次改就踩了）。

**配套必须改的一处（否则会引入更严重的新 bug）**：状态机里"按确认 = 执行辅助菜单项"
这一支原本只判 `i_confirm`：

```verilog
end else if (i_confirm && o_nav_ui_active) begin   // 原为 end else if (i_confirm)
```

原因：`reenter` 那一拍 `ui_active` 还是 0，若不加门控，同一次按键会**既重新进入交互态、
又被当成"开始导航"**。此刻点表非空且高亮在「间断寻点」时就直接开跑了 —— 这正是
"退出后重进"最常见的那条路径。

门控用 `o_nav_ui_active`（`ui_active` 的**旧值**）而不是 `ui_active | reenter`，
就是为了让"进入交互态的那一拍"不执行任何菜单项。用户要操作必须再拨一次确认，
符合"先进入、再操作"的直觉。

**重进后的状态**：`PAUSED` 时按返回会 `state <= ST_SETUP`（§59.4 的状态机），
所以重进一律回到 `SETUP`，状态栏不显示"导航暂停"，与"返回菜单选择 = 退出交互"的
需求语义一致。

★ **`reenter` 不重置点表与辅助菜单高亮，`enter` 才重置**（`enter` 分支会
`pt_v <= 0`、`o_aux_sel <= AUX_SET`）。这是刻意的：返回退出只是"解锁菜单"，
不是"重开页面"，所以重新进来时点表和上次选中的菜单项都还在 —— 这正是 §60.8 第 4 条
要验的那个组合（重进后高亮仍在「间断寻点」、点表非空，第一下确认不能开跑）。

### 60.6 三次综合对比，以及"同域条数为什么每次都不一样"

| 时点 | Setup 同域 50 MHz | 最差 slack | Setup 同域 HDMI | 最差 slack |
| --- | --- | --- | --- | --- |
| 16:50（§59.8） | 10 条 | −0.992 | 8 条 | −1.010 |
| 17:22（§60.3） | 1 条 | −1.494 | 23 条 | −2.380 |
| 17:35（本轮） | **16 条** | **−1.258** | 6 条 | −1.322 |

17:35 这次 Setup 的 25 条分布：**22 条同域（50 MHz 16 + HDMI 6）+ 3 条跨域**。
Hold / Recovery / Removal 三张表各 25 条，**同域都是 0 条**。
（`falcons_tr_content.html` 里带 `Path Slack` 列的四张表依次是
`report_timing -setup` / `-hold` / `-recovery` / `-removal`，判据是表前的 Report Command。）

**三条结论：**

1. **16 条全是同一个加法器的不同位**，不是 16 个问题：
   `u_imu/rx_buf[9]_5_s0/Q → u_imu/calib_sum_{x,y,z}_*_s4/D`。
   17:22 那次报的 `rx_buf[8] → calib_cnt_2_s2/CE` 也是这棵子树。
2. **条数在 1 / 10 / 16 之间跳，根因是布局，不是逻辑**：17:22 → 17:35 这批改动
   只多了 1 行 `wire reenter` + 两个参数从 `1/0` 改成 `0/1`，逻辑量几乎为零；
   而跳动的三条路径**全部落在两个一行没改的 vendor IP**（`u_imu`、`u_hdmi`）上。
   报告只列最差 25 条，别处的 slack 一变，这棵子树的位就挤进榜或挤出榜 ——
   所以"条数"在这里是**可见性**指标，不是**严重度**指标。真正的严重度看最差值：
   三次分别是 −0.992 / −1.494 / −1.258，量级一直没离开 1 ns 出头。
3. **应用层（`nav_free` / `navpt_*` / `navc_*` / `ui_render` / `odom` / `chassis` /
   `num_text`）在 17:22 之后没有一条进榜**。§59.9 点出的 `u_tilt` / `u_yaw` 两条
   已经修掉、不再出现。

<a id="607-当前时序结论"></a>
### 60.7 当前时序结论

**不能说"已通过时序"。** 准确说法是：应用层两条已修完，剩下的违约全部落在
未改动的 vendor IP（`u_imu` 标定累加、`u_hdmi` 像素计数）与未 `create_clock`
的 DDR3 PHY 上。

- `u_imu/calib_sum_*`（16 条，最差 −1.258）：只在开机标定期间累加，256 样本取平均，
  错一拍 = 零点差 0.39%，**可忽略**。不修（要动 vendor）。
- `u_hdmi/hcount_r_1_s0 → Disp_*`（6 条，最差 −1.322）：显示计数链，
  历史长期 −2.1 ~ −2.4 且屏幕实测正常，**在已知范围内**。
- DDR3 跨域 3 条：`fclkdiv/CLKOUT` 未 `create_clock`（`TA1132`），
  属历史既有的**假违约**，`constr\falcons.sdc` 已记。
- 若换慢批次器件或长期高温（>70 ℃）运行，这棵子树仍是第一个会出问题的地方；
  表现为**开机标定零点轻微漂移**（航向不受影响，航向用陀螺、不用加速度计）。

<a id="612-手动挡语义用户-m01153--m01187"></a>
### 61.2 手动挡语义（用户 m01153 / m01187）

用户原话：
> 「任务暂停时，车停下来，继续时车继续当前任务。当任务运行时切到手动挡，车停下来且进入手动控制。
> 当返回光标挡时，显示任务暂停，此时继续任务的话仍可从刚刚的任务继续」
> 「手动挡时确认键和 select 键都屏蔽！只有挡位切换键是有效的」

落地两处：

1. **运行中切手动挡 → 落 `ST_PAUSED`**（不是 `ST_SETUP`）：
   ```verilog
   end else if (i_manual && (o_nav_state == ST_RUNNING)) begin
       o_nav_state <= ST_PAUSED;
   ```
   底盘 `chassis_ctrl.v:117-118` 本来就是手动优先，但 UI 若还停 `RUNNING`，
   切回光标挡那一瞬间车会突然扑向旧目标。落 `PAUSED` 后 `nav_ctrl` 输出
   `center=diff=0` 且**内部状态不清**（`pt_idx` / 积分 / 完成计时都留着），
   按确认能"从刚才那一点继续"。不用 `SETUP` 是因为那会清掉点表与进度。
2. **四个按键在手动挡全屏蔽**，只留挡位切换（`i_manual` 本身不进这门控，
   状态机要看得见它）：
   ```verilog
   wire key_confirm = i_confirm & ~i_manual;
   wire key_back    = i_back    & ~i_manual;
   wire key_aux_up  = i_aux_up  & ~i_manual;
   wire key_aux_down= i_aux_down& ~i_manual;
   ```

<a id="613-暂停必须真停车nav_ctrl-侧的坑"></a>
### 61.3 暂停必须"真停车"（`nav_ctrl` 侧的坑）

`rtl\ui\nav_free_ctrl.v:345-346` 是
```verilog
assign o_nav_run    = (o_nav_state == ST_RUNNING);
assign o_nav_paused = (o_nav_state == ST_PAUSED);
```
⇒ **暂停时 `i_run` 也是 0**。若 `nav_ctrl` 用 `if (!i_run || !i_active)` 退出，
暂停会被当成"退出"→ `o_auto_valid=0` → 底盘断驱动、靠惯性滑行，不是"停住"。
正确写法是主动给零目标让速度环把轮速拉回 0：

```verilog
if (!i_active || (!i_run && !i_paused)) begin ... 清全部状态 ... end
else if (i_paused) begin
    o_auto_valid <= 1'b1;          // ★ 保持使能
    o_center     <= 32'sd0;        // ★ 目标给 0
    o_diff       <= 32'sd0;
    mst          <= M_IDLE;        // 不改 o_state，恢复后从原状态继续
```
另外 `S_TRACK` 回退 `S_ALIGN` 的那一拍**不许再给前进速度**（原来先判
`psi_abs > ALIGN_OUT_DEG` 置 `S_ALIGN`，却仍执行 `o_center <= v_cnt`，
等于"该转却在冲"，300 mm/s 下多走 3 mm）。

<a id="614-顺带修掉一个功能-bugi_acc-从来没累加过"></a>
### 61.4 顺带修掉一个功能 bug：`i_acc` 从来没累加过

`i_acc` 全部 5 处赋值都是 `i_acc <= 32'sd0`（复位 + 四处"模式切换清积分"），
**没有任何一处回存**。于是 `i_sum = i_acc + i_inc` 恒等于 `i_inc`，
`KI_YAW` 退化成第二个比例项、积分永远不累积 ⇒ 横向稳态误差 `e_ss = 扰动/Kp` 消不掉。
`doc\导航控制方案.md` 反复强调 `ki_yaw` 是必需品，实际却是死的。

修法（`M_A4` 决策拍、写在 `case` 之前，让模式切换分支的 `i_acc <= 0` 能覆盖它）：
```verilog
if ((o_state == S_ALIGN) || (o_state == S_TRACK)) i_acc <= i_lim;
```
`i_lim` 已是限幅后的新和值，直接回存即累加，自带抗饱和。

`u_nav_ctrl` 是新模块，时序要一轮轮压。**四轮数据**（判据：`impl\pnr\falcons_tr_content.html`
四张表，按表前 `Report Command` 区分 setup/hold/recovery/removal，看 `From Clock`/`To Clock` 两列）：

| 时点 | 位流 | 50 MHz 同域 | 最差 | 主要来源 |
| --- | --- | --- | --- | --- |
| 22:30 | 36.6 MB | **4 条** | −0.852 | `u_imu` 1 条 + `nav_ctrl` 3 条（`o_diff` clamp 链、yaw 索引乘） |

**四次改法**（每次只动 `rtl\nav\nav_ctrl.v`）：

1. **折返航向 → 索引 → 查表 → 投影** 这条链原是一整条组合（两级乘法 + 一次 LUT），
   拆成 `M_Y1`（加 `dyaw_lat`）→ `M_Y2`（折回 ±18000）→ `M_Y3`（×7457）→ `M_A1`（投影乘法）四拍。
   ★ 中间踩了一次坑：先把 `idx_w_r` 按 `yaw_wrap` 打拍，等于用**上一 tick 的旧航向**做投影，
   仿真立刻报 4 项失败（`g2_aimed_track: got 1, expect 2` —— 车头已对准却仍卡 `ALIGN`）。
   必须用**本 tick 的新航向**；最终拆拍方案里 `M_Y2` 更新 `yaw_wrap`、`M_Y3` 就用它，天然对齐。
2. **`om_raw = dyaw_win × 100`** 里 `dyaw_win` 是 `i_yaw_centi − yaw_prev` 的组合折返，
   改成 `M_IDLE` 只锁 `dyaw_lat <= dyaw_win`、`M_Y3` 再乘 100。
3. **`diff_pid → o_diff`** 是「×KP → +i_lim → −d_term → 取负 → 两级 clamp → mux」，
   在 `M_A3 && cd_valid`（CORDIC 刚给结果那拍）锁进 `diff_pid_r`，四处 clamp 改用寄存值。
   ★ 不能无条件打拍：那样 `M_A4` 会用上**上一个 tick（10 ms 前）**的 PID 值，控制延迟白白变大。
4. **`v_cnt → o_center`** 是「加 → 移位 → ×K_SLOW → 多级 mux → ×3046 → 移位 → clamp → mux」，
   拆成 `M_V1`（`ahead_mm_r` + ×`K_SLOW_Q10`）→ `M_V2`（`v_ref_r`）→ `M_V3`（×`MMPS_TO_CNT_Q10`）三拍；
   同时**删掉 `clamp32(v_cnt, MAX_CENTER)`** —— 数学上冗余：`v_cnt` 最大 892 counts（300 mm/s），
   远小于 `MAX_CENTER=3072`。

**测量序列因此从 5 拍变成 11 拍**（`M_IDLE → M_Y1 → M_Y2 → M_Y3 → M_A1 → M_A2 → M_V1 → M_V2 → M_V3 → M_A3 → M_A4`）。
代价为零：`i_tick` 是 1 kHz，一个 10 ms 周期有 **500000 拍**，11 拍只占 0.0022%。

<a id="622-极性修复rtlnavnav_ctrlv"></a>
### 62.2 极性修复（`rtl\nav\nav_ctrl.v`）

判据是 `rtl\motor\chassis_ctrl.v:148-149`：

```verilog
tgt_left_r  <= clamp_delta(center_r - diff_r);   // 左 = 中心 − 差速
tgt_right_r <= clamp_delta(center_r + diff_r);   // 右 = 中心 + 差速
```

`diff > 0` ⇒ 左轮慢、右轮快 ⇒ `ω = 2·diff/L > 0` ⇒ **左转（CCW）⇒ `yaw` 增大**。
`psi = atan2(left, ahead)`，`psi > 0` 表示目标在左、需左转 ⇒ `diff` 必须为**正**。故：

```verilog
wire signed [31:0] diff_pid = u_pid;      // 原为 -u_pid（错）
```

`d_term` 不用翻：翻转后 `u_pid = p_term + i_lim - d_term`，左转中 `ω > 0` 时 `-d_term` 抑制左转，阻尼方向对。

配套改 `sim\nav_ctrl_tb.v` 三处断言（`g2_right_diff_neg` / `g2_left_diff_pos` / `g2_back_diff_full` 的期望值取反）。

★ 这个错的根源在**方案评审阶段**：`doc\工作记录.md` 五十六节那张表的第 ⑤ 行写了
「`diff > 0` ⇒ 车右转」，与代码相反，后续实现照着错结论写。已在原处加订正指针
（保留原文 + 注明错因），权威表述在 `doc\导航控制方案.md` §八（同日晚已订正）。

<a id="623-imu-看门狗rtltopfalcons_topv不改-vendor-快照"></a>
### 62.3 IMU 看门狗（`rtl\top\falcons_top.v`，**不改 vendor 快照**）

vendor `imu_top.v:748-750` 的 `S_ERROR` 分支没有任何状态转移：`err_flag_r <= 1'b1;` 之后永久停住，
且 `err_flag_r` 除 `i_reset_n` 外无处清零。下游 `data_valid_r` 永 0 → `u_yaw` 不累加 → 航向角恒 0。

顶层加一个只复位 IMU 的看门狗（参数 `IMU_WD_MS = 500`、`IMU_WD_RST_US = 20`）：

```verilog
reg        imu_local_rst_n;
reg [15:0] imu_wd_ms_div, imu_wd_ms_cnt;
reg [9:0]  imu_wd_us_cnt;

always @(posedge i_clk_50m or negedge sys_rst_n) begin
    if (!sys_rst_n) begin
        imu_local_rst_n <= 1'b1; imu_wd_ms_div <= 0; imu_wd_ms_cnt <= 0; imu_wd_us_cnt <= 0;
    end else if (!imu_local_rst_n) begin                 // 复位保持 20 µs
        if (imu_wd_us_cnt >= (IMU_WD_US_DIV - 1)) begin
            imu_local_rst_n <= 1'b1; imu_wd_us_cnt <= 0; imu_wd_ms_div <= 0; imu_wd_ms_cnt <= 0;
        end else imu_wd_us_cnt <= imu_wd_us_cnt + 10'd1;
    end else if (imu_err_flag) begin                      // 失败计数 500 ms 后硬复位
        ...
        if (imu_wd_ms_cnt >= (IMU_WD_MS - 1)) begin
            imu_wd_ms_cnt <= 0; imu_local_rst_n <= 1'b0; imu_wd_us_cnt <= 0;
        end else imu_wd_ms_cnt <= imu_wd_ms_cnt + 16'd1;
    end else begin
        imu_wd_ms_div <= 0; imu_wd_ms_cnt <= 0; imu_wd_us_cnt <= 0;
    end
end
```

把 `u_imu` 的 `.i_reset_n(sys_rst_n)` 改成 `.i_reset_n(imu_local_rst_n)`。

三个设计要点（改的时候容易踩）：
1. **只复位 IMU，不复位 `u_tilt` / `u_yaw`** —— 否则重连瞬间航向突跳到 0，比故障本身更危险。
2. `else if (!imu_local_rst_n)` 必须排在 `else if (imu_err_flag)` **之前**，否则 20 µs 保持期会被
   还在置位的 `err_flag` 立刻打断。
3. 释放后 `err_flag_r` 已被异步复位清零，看门狗回监视态，**不会无限复位**；反馈链中间有寄存器，
   不是组合环。

`SCK_HALF_DIV=25`（1 MHz）说明这条 SPI 链历史上就因为太快失败过 —— BMI270 是无状态从机，
只要时序对就能读，偶发失败最可能是上电瞬间 IMU 就绪晚于 FPGA 释放复位，500 ms 后重试必然成功。

### 62.8 `nav_ctrl` 时序拆拍：12 条 → 3 条（2026-10-19 23:53 综合）

**23:42 那次综合（含极性修复+看门狗+红字，但还没拆拍）暴露出 12 条 `i_clk_50m` 同域违约**，

但根因不是"改坏了"，而是**23:03 的 0 条本身建立在功能缺陷上**：

- 23:03 版 `i_acc` 只有 5 处清零、**没有一处回存**，`i_acc → i_sum → i_lim` 这条自反馈链根本不存在；
- 本轮把回存补上（`i_acc <= i_lim`），立刻出现 `i_acc(reg) → 32 位加法 → 32 位 clamp → i_acc(D)` 的自反馈，
  一拍走不完（21 ns）。

路径明细（`impl\pnr\falcons.timing_paths` 有逐级分段）：

```
n965_s(0.614→3.913) → s_dot_11_s..s_dot_21_s(7.488→8.433)      ← cut_ok 判据的 dot_s 高位
→ mult_573_s2(9.987→11.986)                                     ← dot_s × TAN_CUT_Q10
```

配套：`if (mst == M_A4)` → `if (mst == M_A5)`、`if (mst != M_A4)` → `if (mst != M_A5)`、

## §63 三个导航参数调整 + 仿真补参数边界断言（2026-10-20 11:5x）

<a id="631-改了什么"></a>
### 63.1 改了什么
| 参数 | 原值 | 新值 | 位置 |
| --- | --- | --- | --- |
| `ALIGN_IN_DEG` | `3000`（30°） | **`1000`（10°）** | `rtl\nav\nav_ctrl.v:126` |
| `D_SLOW_MM` | `130` | **`100`** | `rtl\nav\nav_ctrl.v:123` + `rtl\top\falcons_top.v:1353` |
| `MAX_DIFF_CRUISE` | `180` | **`252`** | `rtl\nav\nav_ctrl.v:136` + `rtl\top\falcons_top.v:1359` |

`MAX_DIFF_CRUISE = 252` 的换算（轮距 161.5 mm、1 count/10ms = 0.336170 mm/s）：
`60 °/s = 1.047198 rad/s → diff = 1.047198×161.5/2 = 84.561 mm/s → 84.561/0.336170 = 251.54 → 取 252（60.11 °/s）`。
对照：`180` = 42.94 °/s、`250` = 59.63 °/s。

`K_SLOW_Q10 = (V_CRUISE_MMS × 1024) / D_SLOW_MM` 是 localparam，自动从 2363 变 **3072**，不需手改。
同步改了 `NP_MIN_SPACE_MM` 两处注释：原写"= 2·D_SLOW"只在 D_SLOW=130 时成立，现改为"D_SLOW=100 后仍取 260 更保守"。

**三个副作用（改参数时必须知道）**：
① `ALIGN_IN=10°` 让迟滞区间从 5° 扩到 **25°**（`ALIGN_OUT_DEG` 仍 35°）—— TRACK 里偏到 34° 仍"边偏边走"，靠几何闭环拉回；好处是起步方向更准。
② `D_SLOW=100` 让 `v_ref` 减速斜率从 692 升到 **900 mm/s²**（300/100 = 3 /s × 300 mm/s），余量从 1.44 倍降到 **1.11 倍**。底盘实际减速能力约 1900 mm/s² 仍够，但换电机/加负载后可能不足。
③ `MAX_DIFF_CRUISE=252` 使 300 mm/s 时最小转弯半径从 **400 mm** 降到 **286 mm**，代价是直线段更易摆动。若场地出现摆头，第一优先把这个值往回收。

<a id="632-为什么要补断言"></a>
### 63.2 为什么要补断言
改完参数先跑了原 91 项 `nav_ctrl_tb`，全过。但查断言内容发现**没有一条依赖这三个值**：
- `ALIGN_IN_DEG`：G2 只测了"偏 0° 能进 TRACK"和"偏 180° 留 ALIGN"，10°~30° 这个被改变的区间无断言
- `MAX_DIFF_CRUISE`：tb 里只有 `ALIGN` 下的 ±612 满幅断言，TRACK 下的差速幅值无断言

即"91 项全过"只证明没回归，不证明新参数生效。这是**测试盲区与参数解耦**：改参数不会让任何断言失败，等于参数无人看守。

### 63.3 G11 组：14 项参数边界断言（`sim\nav_ctrl_tb.v`，91 → 105 项）

| 断言 | 场景 | 判据 |

| `g11a_20deg_align` / `_center0` / `_diff_pos` | 车头偏 -20°、目标正前 | psi=+20° > 10° → 留 `S_ALIGN`、`center=0`、`diff>0`（旧 30° 会误进 TRACK） |
| `g11b_8deg_track` | 偏 -8° | psi=+8° ≤ 10° → 进 `S_TRACK`（证明门限确实在 10°，不是更小） |

<a id="634-g11g-实测-437-而非理论-446-的原因"></a>
### 63.4 `g11g` 实测 437 而非理论 446 的原因
理论：ahead=50 → `v_ref = 50 × 3072 = 153600`（Q10 mm/s = 150 mm/s）→ `×3046>>20 = 446` counts。
实测 437，差 2% 来自 `rtl\odom\sin_lut_rom.v` 的 Q15 量化：**`cos(0°)` 存的是 32767 而不是 32768**（Q15 最大正数），
使 50 mm 的 `ahead` 被算成 **49 mm**（`50×32767/32768 = 49.9985 → 截断 49`），于是 `49×3072 = 150528 → 437`。

这是 LUT 量化误差，不是逻辑错误。但**不能用 `chk_int(437)` 锁死** —— LUT 一旦重生成（索引取整变化）就会误报。
所以 `g11g` 用区间 `425..455` 只守"斜率在 150 mm/s 量级"；旧 `K_SLOW_Q10=2363` 时会得 336，落在区间外。

<a id="635-另外两处仿真改进"></a>
### 63.5 另外两处仿真改进
**① `nav_ctrl_tb` 开头打印被测参数**，避免"改了参数却跑的是旧编译"造成的假通过：

修法是在 `$checkTotal` 取值后加兜底：仅当"无 CHECKS 行**且** pass 行数为 0"时，从结论行取 N 并对齐。

<a id="646-结论与可选修法"></a>
### 64.6 结论与可选修法

**结论：这版可以烧，但不能记作"时序通过"。**
- 依据：STA 是 worst-case corner，本板历史上 HDMI 同域长期在 −2.1~−2.4 而实测显示正常；50 MHz 同域负 slack 的三类路径里，
  vendor 两类（`imu_top` 的 SPI 接收缓冲、`disp_driver` 的像素输出）不承载控制链路，`nav_ctrl` 一条（`cut_ok_r`）承载 L2 切点判据但每 10 ms 才算一次、允许晚一拍。
- 不能记"通过"的理由：11 条 + 9 条实测超周期，最差 1.59 ns / 7.5%，没有余量证据。

**三条可选修法**（每条都要重新综合，结果不可预测）：

| 修法 | 改动 | 预期 |
| --- | --- | --- |
| ① `cut_ok_r` 再拆一级 | `nav_ctrl.v` 加 `cut_prod_r` 寄存器，把 `dot_s * TAN_CUT_Q10` 的乘积与比较分两拍 | 直接针对最差的那条；代价 1 拍（100 ns/10 ms 周期，无感） |
| ② `nav_free_ctrl` 像素乘法输入打拍 | 把 `i_x_mm/i_y_mm/o_cur_x_mm/o_cur_y_mm` 先寄存一拍再进 `×3932` | 消掉 7 条；车绿点晚 20 ns，不可见 |
| ③ 不动 RTL，重跑 PnR | 布局偶然性已被三次实测证明 | 可能好也可能更差（17:22 先例） |

**不建议**为这 20 条负 slack 动 vendor IP：`u_imu` / `u_hdmi` 的快照一致性比这点余量更值钱。
