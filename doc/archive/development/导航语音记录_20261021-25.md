<a id="84-imu-零偏标定失败也显示imu初始化错误2026-10-21"></a>
## 84. IMU 零偏标定失败也显示「imu初始化错误」（2026-10-21）

原实现只在 `imu_err_flag`（状态机停在 `S_ERROR`）时把数据页「中心速度」字段换成诊断码 `state*100+err_code` 并显示红字。但零偏标定超时失败时状态机已回到 `S_RUN`，屏幕毫无提示 —— 运行时 `CALIB_APPLY` 分支不生效（`bias=0`），yaw 带着零偏持续漂移，现象上只能靠事后怀疑「是不是没标定成」。

改为 `imu_fail_any = imu_err_flag | imu_calib_fail` 统一上报，红字与诊断值同时生效。诊断码低位按来源分取：初始化失败仍用 `err_code`（屏幕读作 `S.01`/`S.02`），标定失败固定填 90（此时 `state=S_RUN=14`，屏幕读作 `14.90`）。`14.90` 的语义是「通信正常、零偏没标定出来」，应去查 `CALIB_DEV_TH`、上电是否静置、`PWR_CTRL` 后是否留了足够等待时间。

`calib_fail_r` 只在 `S_WR_PWR_CTRL` 完成、进 `S_CALIB` 前清零，失败后不再回 `S_CALIB`，所以红字是持久的。看门狗仍只看 `imu_err_flag`，行为未变；`nav_calibrated` 本来就要求 `imu_calib_done`，标定失败时导航保持 not ready，不会用未标定的 IMU 跑。

仿真 26 台 / 2277 项全过；综合 + 布局布线 exit 0，位流 38,792,615 字节（19:23:33），Fmax `i_clk_50m` 46.792（LL25）/ `clk_pixel` 45.940（LL29），Setup 违例端点 497、Hold 18。本次新增的 `imufail` / `center_cms_show` / `imu_diag` 等信号在 25 条最差 setup 路径中零出现；与交接单所记 18:05 版（45.800 / 45.142）相比 Fmax 略升，属布局波动，不能归因于本次改动。未上板验证。

屏幕效果用 `tools\preview_data_page.py --imu-fail 1 --center 1490` 离屏渲染确认（点阵直接读 `font_rom_lg.v`，与上板共用同一份字库），产物 `doc\img\imu_calib_fail.png`：红字「imu初始化错误」在 y 48..71（8 字 × 24 px，x 384..575），中心速度字段显示 **14.90**。与已有的 `doc\img\imu_fail_red.png`（初始化失败场景）配对看，区别只在数值：14.90 表示通信是好的、零偏没标定出来。


<a id="85-系统复位也重新标定-imu-零偏2026-10-21"></a>
## 85. 系统复位也重新标定 IMU 零偏（2026-10-21）

原实现把 `imu_top` 的复位脚接在 `imu_local_rst_n` 上，而 `imu_local_rst_n` 在 `!sys_rst_n` 时被置 **1** —— 等于**系统复位期间反而把 IMU 放开**，状态机停在 `S_RUN` 不回 `S_IDLE`。后果是按 S0 复位键后 IMU 不重新初始化、零偏标定失败无法重试，只能重新烧录或断电。

改为 `!sys_rst_n` 时置 **0**，与看门狗走同一条「拉低 → 计满 `IMU_WD_RST_US` → 释放」路径：

| 触发源 | 改前 | 改后 |
|---|---|---|
| S0 复位键（`i_key_reset_n` → `reset_sync` → `sys_rst_n`） | IMU 不复位，沿用上次标定结果 | **重新初始化 + 重新标定** |
| 看门狗（只认 `imu_err_flag`，不看 `calib_fail`） | 拉低 20 µs 再放开 | 不变 |
| 重烧 SRAM / 断电重启 | reg 初值 0 → 重新初始化 | 不变 |

`u_tilt` / `u_yaw` 的复位本来就接 `sys_rst_n`，所以系统复位时三块一起清空、行为一致；看门狗触发时这三块都不复位、航向角保持不丢——这是原设计刻意做的区分（`falcons_top.v` 注释「只复位 IMU，不复位 u_tilt / u_yaw」），本次未动。

代价：复位后要等约 **3.2 秒**（`PWR_WAIT_MS=20` + 配置写入 + 3 秒标定窗口）才有 `o_data_valid`，期间界面数值保持 0、`nav_calibrated` 保持 0。

仿真 26 台 / 2277 项全过；构建 exit 0，位流 38,792,615 字节（19:58:08），Setup 违例端点 497 / Hold 18、Fmax `i_clk_50m` 46.792（LL25）/ `clk_pixel` 45.940（LL29），与上一版逐项相同。`falcons_top` 在仿真里仍是零覆盖，本改动**只有真机能验**，未上板验证。

**上板实测（2026-10-21 20:1x）**：SRAM 下载与 Flash 固化都成功（User Code `0x0000D3BA`，Flash 结束地址 `0x049E000`，112.18 s），但屏幕「中心速度」显示 **`15.01`**，即 `state=15(S_ERROR) × 100 + err=1(CHIP_ID 校验失败)` —— **IMU 的 SPI 根本没通**：MISO 配上拉，读回 `0xFF` 而不是期望的 `0x24`。

已排除的：`constr\falcons.cst` L146-157 的引脚分配（SCK=A14 / MOSI=A13 / MISO=A16 / CS=A15）与注释一致，雷达刻意用 C14 避开 A15，约束侧无冲突；断电重启、重复 SRAM 下载均未恢复。

尚未排除的：① J2 排线接触不良或插反（`falcons.cst` L36 就警告过"灰排线插反 = 整排错位，综合查不出"）；② IMU 模块 5 V 供电；③ §85 的复位是否引入副作用 —— 理论上不会（`imu_top` 被复位 1 µs 只让状态机从 `S_PWR_WAIT` 重新计时，SPI 引脚在复位期间是 CS 高 / SCK 低 的空闲态），但把 `falcons_top.v:904` 改回 `1'b1` 重构建可以干净地排除它。

★ 另注：那 1 µs 本身也是个旧缺陷 —— `IMU_WD_RST_US = 20` 定义了却从未使用，实际复位宽度由 `IMU_WD_US_DIV = 50` 决定，即 50 个时钟 = 1 µs，而注释写的是"保持 `IMU_WD_RST_US` 微秒"。

**★ 根因（2026-10-21 20:2x，用户反馈）**：是 **IMU 模块硬件损坏** —— 换一个模块后 `15.01` 消失、SPI 通信恢复。与引脚约束、`§85` 的复位改造都无关；"断电重启与重烧都无效、换模块即好"正是芯片本身坏掉的特征。这条记录留着，是因为排查时最容易先怀疑新改的 RTL，而这次 §85 恰好是刚改的，差点被当成嫌疑。

**★ 根因（2026-10-21 20:2x，用户反馈）**：是 **IMU 模块硬件损坏** —— 换一个模块后 `15.01` 消失、SPI 通信恢复，**零偏也恢复了正常**，§84 的红字逻辑同机复测也正常。

这条把前面 §82 那一长串零偏归因（`S_WR_PWR_CTRL` 后零等待、`CALIB_DEV_TH` 自锁、`o_bias_*` 空连接、死区放大）全部降级为**“代码里确实存在、但本次现象不是它们造成的”**：一个 CHIP_ID 都读不回来的模块，谈零偏标定没有意义。那些缺陷仍然值得修（尤其 `PWR_CTRL` 后应补一段延时、`IMU_WD_RST_US` 定义了没用），但优先级要重新排。

留下的教训：**排查时最容易先怀疑刚改过的 RTL**。这次 §85 刚改完就出 `15.01`，顺序上又"对得上"，差点被当成嫌疑人；实际上“断电重启与重烧都无效、换模块即好”早就指向硬件了。

**后续：`15.02` 也出现了，换排线解决（2026-10-21 22:0x）**：换过 IMU 模块后正常了一阵，又冒出 `15.02`（`err=2` = INTERNAL_STATUS 校验失败）。**换一条排线后恢复**。

值得记的是这组对照：**同一个接触不良，可以表现为两种错误码** ——
- 完全不通时读 CHIP_ID 拿不到 `0x24` → `15.01`
- 通得上但边沿劣化时，CHIP_ID 能读对、配置却写不进去 → `15.02`

`15.02` 的判据是 `S_CHK_STATUS` 读 0x2D 的 `init_ok`（bit0）不为 1（`imu_top.v:581`）。以前看到「配置问题」会先怀疑 `SCK_HALF_DIV` 太快或配置数组，这次证明**先查线**更快。

**决策与教训**：

- 提示音**不进 `announcements`**：那条路径是任务播报（`ALSAPlayer` + 校验过的语音资产 + 与录音互斥），录音提示音是操作提示、要短、不需要资产校验，硬塞进去会把两套语义耦在一起。新建 `RecordingCue` 只依赖一个 ALSA 设备名。
- `POST /text` 命中 preset_control 时**同步**返回；`/capture`、`/audio` 走 job 队列，必须轮询 `/jobs/<id>`——把二者当成同一种接口会白等。
- PowerShell 的 `>` 重定向写 UTF-16，`git show ... > file` 算出的 sha256 与板端 manifest 必然不符；字节级比对要用 `cmd /c "git cat-file blob HEAD:path > file"`。板端 release 与 `HEAD` 逐字节一致这一结论就是这么做出来的。
- 板端 base64 传脚本 + `ssh "echo b64 | base64 -d > /tmp/x.sh && bash /tmp/x.sh"` 比在 ssh 命令行里拼引号稳；单文件上传用 `scp` 配 `SSH_ASKPASS` 即可，不必走交互密码。
