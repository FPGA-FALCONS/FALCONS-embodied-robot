### 74.5 ★ 决定性证据：综合器对本设计是确定性的

**22:28:15 那次综合的输入 RTL 与 20:55:49 那次逐字节相同**（三个改动文件全部 `git checkout` 回 HEAD，`git status` 里 `rtl/` 与 `vendor/*.v` 无任何 `M`）。两次综合的输出：

- 位流字节数 **37,922,301**，完全相同；
- Logic 23840 / Register 12534 / BSRAM 60 / DSP 132.5，完全相同；
- 六个时钟的 Fmax **全部逐位相同**（46.955 / 209.224 / 46.213 / 2240.145 / 133.873 / 244.200）；
- 两个域的 TNS **全部逐位相同**（−3.211 / 9、−17.096 / 26）；
- 13 条同域违例的**每一条 slack 都相同**（−1.297 / −1.231 / −1.195 / −1.164 / −1.149 / −1.064 / −0.987 / −0.939 / −0.910 / −0.897 / −0.859 / −0.737 / −0.725）。

**结论：在本工程的固定约束与固定工具版本下，同一份 RTL 综合出同一份结果。** 因此 21:52 与 22:16 的恶化**不是布局随机性，是改动造成的**。

⚠ **本条推翻了本章早期的判断。** 22:16 那次（只回退 ①③、保留 ②）我一度把它归因为「综合不可复现」，理由是 `disp_driver.v` / `imu_top.v` 与 20:55 逐字节相同但 `hcount → Disp_*` 从 7 条变 15 条。那个推理漏了一件事：22:16 时 ② 仍在，两次综合的输入并不相同。22:28 把 ② 也回退后才拿到真正的对照组。**教训：判断"改动是否有效"必须先确认两版输入逐字节相同，只对比"某一处改动相同"是无效对照。**

<a id="746-逐条归因"></a>
### 74.6 逐条归因

- **① `syn_keep` 负优化（有机制证据）。** 21:52 时 `hcount → Disp_*` 从 7 条涨到 19 条、最差 −1.231 → −2.339、逻辑级数 28~30。`impl\gwsynthesis\falcons.vg:117339` 确认 `DFFRE Disp_DE_s1` 确实被保留（`.Q(Disp_DE)`、`.D(.n168_10)`、`.CLK(pixel_clk)`、`.RESET(Disp_DE_12)`），但 24 个 mux LUT（`falcons.vg:116710-116852` 的 `.I1/.I2/.I3(Disp_DE)`）仍以组合方式取 DE。机制：`syn_keep` 只保证寄存器不被优化掉，**不阻止 logic replication** —— 为了让 25 个消费点就近取到 DE，综合器复制了比较器逻辑，布局膨胀、布线更长。
- **② `block_ram` 是唯一主因，且是重伤。** 只要 ② 在，同域违例就是 23 条：`hcount → Disp_*` 7 → 15 条、`rx_buf → n3913` 1 → 4 条、`vcount → o_rdata` 的 5 条变成 `vcount_r_6 → u_dyn_text/mem_mem_0_0_s` 的 4 条。**连完全不相关的 `camera_pclk`（209.2 → 206.1）、`u_cam/CLKOUT1`（133.9 → 118.3）、DDR3 `fclkdiv`（244.2 → 202.1）的 Fmax 都被拖下去了** —— 说明它逼着 BSRAM 分配从 60 变 61，触发整次 PnR 重布局，代价远超"把 5 条换 4 条"这点局部收益。`dyn_text_ram` 只有 512 bit，做成 LUT RAM 用 64 个 LUT 完全划算，**不该强制进 BSRAM**。
- **③ 三轴打拍：起点确实变了，但没有收益。** 21:52 时路径起点从 `rx_buf` 变成 `gyro_x_cs_31`，条数 1 → 3、最差 −1.297 → −2.310，说明打拍切断的 `rx_buf → 乘法` 那段不是瓶颈，真正的瓶颈在乘法输出 → `n3913` 的组合累加。

<a id="747-本轮留下的东西"></a>
### 74.7 本轮留下的东西

- **三个模块级 tb**（共 1417 项），其中 `disp_driver_tb` 的 1331 项把 vendor 显示驱动的行为锁死了（行场扫描、DE 窗口 282~1306 / 19~619、逐拍像素透传、`H_Addr`/`V_Addr`），以后动它不会静默改坏画面。
- **`sim\run_sim.ps1` 的双 `+incdir` 与 vendor 源文件清单**：`disp_driver.v` 依赖同目录的 `disp_parameter_cfg.vh`，`imu_top.v` 的闭包是两层（`spi_master_mode0` / `bmi270_cfg_rom`），这些依赖关系现在写进脚本了。
- **两条教训**：
  1. `syn_keep` 不能用来「切断组合链」。它保的是寄存器不被优化掉，综合器的 logic replication 照样会把上游逻辑复制到下游消费点。要真正切断，只能在 RTL 里插一级寄存器并同步调整下游相位，没有综合属性可以替代。
  2. 小模块的「存储风格」属性会改变全局布局。`dyn_text_ram` 只有 512 bit，改成 BSRAM 看起来只是多占 1 块 RAM、读延迟不变，实际把整次 PnR 推向了另一条路，六个时钟的 Fmax 全部下降。**在资源不紧张时，动这类属性没有收益，只有风险。**

<a id="752-全工程审计结论"></a>
### 75.2 全工程审计结论

审计口径：所有 `rtl\` 下的 `.v`（排除 `ip\`），逐行去掉 `//` 注释后用正则 `\w\s*[\*\/\%]\s*[\w\(]` 抓算术，再对命中行逐个追消费者、位宽、时钟域。

**结论：全工程真正的"本可两个 LUT 搞定却被综合成 DSP"只有 `rtl\ui\ui_render.v` 那一处。**

- **不在位流里的模块**（`falcons_top.v` 里 0 次实例化）：`point_cloud_video`（`/12` 与 `%12` 两个除法器）、`polar_to_xy`（三个 `/10`）、`m10_point_cloud_core`、`m10_radar`。它们写得再离谱也不占资源。
- **设计得好的例子**（不动）：`ui_render.v:932-970` 判圆用**比较式**而不是 `dx²+dy²`，`:947` 的注释写明「pixel 域只有 1 拍，乘法会把这条路径拉长」；`nav_ctrl.v:331-334` 的坐标旋转结果立刻被 `:584-587` 的 `p_dcs/p_dss/p_dsc/p_dcc` 寄存；`nav_ctrl.v:344-350` 的 `cut_ok`/`space_ok` 已提前一拍寄存（`:351-356` 记录了 2026-10-19 修过 26.4 ns）。
- **必需或无害的**：`nav_ctrl.v:412-414` 的 PID 是变量×变量；`odom.v` 6 处、`falcons_top.v:959/978/1240/1276/1200-1201` 全是常数乘。

<a id="753-三处改动按落地顺序"></a>
### 75.3 三处改动（按落地顺序）

**① `rtl\ui\ui_render.v`：把 `lg_slot × 24` 从 DSP 乘法改为移位相加（23:09 综合）**

原 `:491` 一行拆成两行（现 `:496-497`）：

```verilog
wire [11:0] lg_slot_x24 = {2'd0, lg_slot, 4'd0} + {3'd0, lg_slot, 3'd0};   // ×16 + ×8 = ×24
wire [11:0] lg_col_look = x_look - lg_slot_x24;
```

两个操作数都显式补到 12 位，避开 `:487` 记的「6 位相乘截成 6 位，24×8=192 溢出」旧坑；`lg_slot` 最大 42，42×24 = 1008 < 4096。

效果：DSP **132.5 → 132**（那半片就是它）；`hcount_r → Disp_*` 7 条**全部消失**；HDMI TNS −17.096 → −4.855。但布局重排引入 7 条 `u_odom/dyaw_acc_3_s1 → u_nav_free/mult_5763_s1`（LL 只有 14，纯布线），`i_clk_50m` TNS 反而 −3.211 → −23.575。

**② `rtl\ui\nav_free_ctrl.v`：车辆位置输入先打一拍（23:27 综合）**

在 `:448` 之前插入 `reg signed [31:0] ix_d1, iy_d1;` 及其 always 块（`clk`/`rst_n`），两个 32 位乘法器改用 `ix_d1`/`iy_d1`。

机理：`odom.o_x_mm` 那个寄存器的边界被综合器吸收进了消费者，于是 `odom` 内部积分树 → 本模块 32 位乘法器连成一条长链，而两个模块被摆得很远。多插一级寄存器后跨两级不会被吸收。代价 1 拍（20 ns），车辆位置 10 ms 更新一次，无感。

效果：`odom → nav_free/mult` **7 条 → 0 条**；`i_clk_50m` TNS −23.575/54 → −6.029/16；Fmax 47.273 → 48.132。

**③ `rtl\odom\odom.v`：角度索引与窗口位移一起锁存一拍（23:36 综合）**

起因是高扇出表里 `u_odom/idx_sin_w[6]` 扇出 **513**、worst slack 只剩 **+0.299 ns**。扇出来自 8 位地址同时驱动两个 256×16 的 LUT ROM（sin 与 cos），而这条地址线原来是纯组合的：`yaw_wrap/dyaw_acc → yaw_mid → ×7457 → >>>20 → idx → LUT 地址`。

做法（`odom.v` 第 5 节末新增约 30 行）：在 `i_delta_valid` 拍把 `idx_sin`/`idx_cos`/`ds_q10` 一起打进寄存器，`sin_lut_rom` 地址改接 `idx_sin_r`/`idx_cos_r`，`dx_q10`/`dy_q10` 改用 `ds_q10_r`，位置累加（`x_q10`/`y_q10`/`o_x_mm`/`o_y_mm`）改由 `delta_vld_d1` 使能，速度输出仍用 `i_delta_valid`。

**★ 必须整条链一起延：** `ds_q10` 与 `cos_v` 必须在**同一拍**相乘，只给 idx 打拍会让位移和角度差一拍，积分结果系统性错位。`idx_sin_r` 取的是 `delta_valid` 拍的值，那正是"本窗口中点"的索引（见 `:208-214` 的中点积分说明），语义不变。代价 1 拍（20 ns），`delta_valid` 周期 10 ms。

验证：`odom_tb` 的 16 项位置断言（`fwd_x`=335±3、`back_x`=−335±3、`left90_y`=335±8、`right90_y`=−335±8、`fl45_x/y`=237±6、`arc_mid_x`=10±8、`arc_mid_y`=286±8）全部通过，证明语义没变。

效果：`i_clk_50m` Fmax **49.733**（差约束 0.267）、HDMI **48.807**（差 0.193）；TNS −0.107/1 与 −0.193/3。

<a id="754-p0set_clock_groups失败"></a>
### 75.4 P0（`set_clock_groups`）失败

按 `constr\falcons.sdc:55-59` 记的时钟名写了 `set_clock_groups -asynchronous`，PnR 读约束时直接终止：

```
ERROR (TA2004) : "constr\falcons.sdc":92 | Cannot get clock with name
  'u_hdmi/u_display_pll/PLL_inst/CLKOUT0.default_gen_clk'
ERROR (TA2004) : ... | Cannot get clock with name '...CLKOUT1.default_gen_clk'
BUILD FAILED (run all):   [exit code: 1]
```

原因：那两个名字是从**布线后**报告的 Clock Summary 里抄的，那里 PLL 的 generated clock 已建立；而 SDC 在 `read_netlist` 之后、PnR 之前解析，此刻 generated clock 还不在时钟库里。与 `:62-64` 记的 `pixel_clk` 是同一类问题的不同表现。

失败原因与两种待查做法已写进 `constr\falcons.sdc` 的注释，命令本体没有保留。P0 的收益（清掉 86 条跨域假违例）只是**报告可读性**，不影响硬件。

## 76. A1 / B1'：常数除法与累加器改写的两次负优化（2026-10-21）

<a id="761-缘起与结论"></a>
### 76.1 缘起与结论

§75 把同域违例收到 4 条，剩下 sys 域 1 条（`u_imu/rx_buf[6]_6_s0 → n3913_s`，−0.107）和 pixel 域 3 条（最差 −0.193）。§75.7 判断 sys 域那条的真瓶颈是 `gyro_*_cs` 的 `× 25000 >>> 12` 之后的组合累加。

本轮不再走「打拍」路线（§74 已失败），而是直接改写**算术结构**：

- **A1**：`imu_top.v` 的 `calib_sum_x/y/z` 与 `seed_sum_x/y/z` 从 48 位降到 32 位。
- **B1**：`ui_render.v:490` 的 `lg_slot = x_look / LG_CELL_N`（12 位除以常数 24）改成纯移位加法的分解实现。

两者都单独验证过**数学等价**，但 PnR 实测**都是负优化**：同域真违例 1 → 15 条，两个时钟域 Fmax 各降约 4%，连**未改动的 `nav_free` / `odom` 模块都被推过线**。已全部回退，位流重建后逐项回到基线。

**这一节最值得记的不是两个方案怎么做，而是为什么判断错了** —— 见 §76.7。

<a id="762-a148-位累加器--32-位"></a>
### 76.2 A1：48 位累加器 → 32 位

原代码（`vendor\verilog-reusable-modules\modules\imu660ra\rtl\imu_top.v`）：

```verilog
:340  reg  signed [47:0] calib_sum_x, calib_sum_y, calib_sum_z;
:376  wire signed [47:0] seed_sum_x = calib_sum_x + gyro_x_cs;
:699  if ((!calib_seed_done) && (calib_cnt_next == CALIB_SEED_N)) begin
:700      calib_mean_x <= seed_sum_x[35:4];      // /16
:707  if (calib_accum && (calib_cnt_next >= CALIB_SAMPLES)) begin
:708      bias_x_r <= seed_sum_x[40:9];         // /512
```

位宽核算：`CALIB_SAMPLES = 512`，单样本 `|gyro_x_cs| ≤ 200000`（`±32768 × 25000 >>> 12`），故 `|sum| ≤ 512 × 200000 = 1.024e8 < 2^27`；加 `CALIB_ABS_LIMIT = 2000` 门禁后实际更小。**32 位有 21 倍余量**，48 位是纯浪费。

改动 5 处：`[47:0] → [31:0]`（声明 1 + `seed_sum` 3）、`48'sd0 → 32'sd0`（6 处）、`seed_sum_x[35:4] → $signed(seed_sum_x) >>> 4`、`seed_sum_x[40:9] → $signed(seed_sum_x) >>> 9`。

**等价性验证（Python，3000 组随机含 ±MAXS 极值）**：`peak |sum| = 102400000`（2^31 的 4.77%）、`max |sum48 − sum32| = 0`、`>>>4` 与 `>>>9` 的 mismatch 均为 0 → PASS。`imu_top_tb` 16 项全过。

<a id="763-b1-第一版寄存器增量计数器已废弃"></a>
### 76.3 B1 第一版：寄存器增量计数器（已废弃）

思路：`x_look` 在一条扫描行内逐拍 +1，所以 `slot` / `col` 可用「上一拍 + 1，满 24 归零」推出，彻底不除。实现是两个寄存器 `lg_slot_p` / `lg_col_p` 保存 `i_pixel_x − 1` 的值，当前值由它们**组合**推出（`lg_wrap` 判满、`i_pixel_x == 0` 强制归位）。

独立小台 `logs\b1_slot_eq_tb.v` 逐点扫 0..1023 四轮，**4096 点全对**，数学没问题。

**但全量仿真挂了 12 项**（`imu_fail_red_text`、`ph_p1_camera`、`car_absent_on_page3`、`menu_item0_boundary`、`car_shape` 等），外加 `tune_page` 的 `5_unit_row5_none`。回退后重跑 19/19 全 PASS，证明全部由 B1 引入。

**根因是相位，不是逻辑**。`sim\ui_render_tb.v` 的采样写法是 `px = xx[11:0]; ... @(posedge pixel_clk); <采样 rgb>`，`px` 在 posedge **之前**赋值、posedge 之后不前进。而 `lg_slot_p` 在同一个 posedge 已更新为 `f(px)`，组合输出变成 `f(px+1)` → tb 看到的结果**超前 1 列**，字形位选错位。

真实硬件里 `H_Addr` 是 `hcount_r` 的组合函数（`disp_driver.v:77`），posedge 后立即前进，`lg_slot_p` 滞后一拍正好抵消 → **我的设计在硬件里是对的，只是与 tb 的建模相位不兼容**。改 tb 会影响 46 项检查的坐标语义（§75 前后 ui_render 由 42 增到 46 项），代价大于收益，故放弃这一版。

<a id="764-b1纯组合的除法分解"></a>
### 76.4 B1'：纯组合的除法分解

`x_look = 24·slot + col_look`，而 `24 = 8 × 3`，所以先除 8（移位）再除 3：

```verilog
wire [7:0]  lg_x_div8 = x_look[10:3];                          // n = x_look / 8，n ≤ 128
wire [12:0] lg_n43    = {lg_x_div8, 5'd0} + {lg_x_div8, 3'd0}
                      + {lg_x_div8, 1'b0} + {5'd0, lg_x_div8}; // n*43 = n*32 + n*8 + n*2 + n
wire [5:0]  lg_q_raw  = lg_n43[12:7];                          // ≈ n/3，可能偏大 1
wire [7:0]  lg_q_x3   = {lg_q_raw, 1'b0} + {1'b0, lg_q_raw};   // 3q
wire [5:0]  lg_slot   = (lg_q_x3 > lg_x_div8) ? (lg_q_raw - 6'd1) : lg_q_raw;
```

数学依据：`43/128 − 1/3 = 1/384`，故 `43n/128 − n/3 = n/384 < 2` 对 n < 768 成立 ⇒ n ≤ 128 时最多偏大 1，判据 `3·q_raw > n` 减 1 即可精确。

`n mod 3`：2^i mod 3 在 i 偶/奇时交替 1/2 ⇒ 偶位系数 1、奇位系数 2，和 ≤ 12，两次减 3 归一。最后 `col_look = 8·(n mod 3) + x_look[2:0]`。

**零 DSP、零寄存器，相位与原式完全一致**，所以 tb 不用改。

小坑：第一版误写 `{lg_q_raw, 2'b0}`（即 q×4）当 3q，`x_look=24` 时 slot 算成 0，ModelSim 立刻报 `BAD slot x_look=24 got=0 exp=1`。

**验证两道**：Python 全范围 0..1025 不符点 **0**；ModelSim 独立小台 `logs\lg_div2.v` 比对 slot / col_look / col 三项，`PASS: lg_div all 1026 points match`。全量仿真 **19 台 / 2186 项全 PASS**（`ui_render` 46 项、`tune_page` 58 项）。

1. **从逻辑结构推断瓶颈，没有验证 PnR 里的实际映射。** 看到「48 位加法器」「÷24」就认定它们是关键路径，但没先确认综合器把它们实现成了什么。实际是：常数除法被压成很浅的 DSP/LUT 组合，而手写分解**把 1 级换成 4~5 级级联**，逻辑深度反而增加。
2. **忽略了 P&R 对布图扰动的敏感性。** 只要 RTL 变动，PnR 就整体重排；`nav_free` / `odom` 的 7 条就是这么变差的。这与 §75.6 记的归因限制同源，但这次是**反向**教训：改动可以伤害完全无关的模块。
3. **用综合报告下结论太早。** 综合 Fmax 与 PnR 实测差 19%，LL 变化也不敏感（30 → 31）。真正能定性的是 PnR 的**同域违例明细**。

**下次做时序改动的正确顺序**：

1. 先看 PnR 的 `Setup Paths Table`，确认目标路径的 **from / to 节点和逻辑级数**，不要靠猜。
2. **一次只改一处**，且改动要**减少**逻辑深度（加流水、砍冗余判断），而不是**替换**算式 —— 更换算式几乎总是让综合器重新映射出一串新逻辑。
3. 判断有效性只看 PnR 的**同域违例条数与 slack**，不看综合 Fmax。

```tcl
create_generated_clock -name clk_serial -source [get_ports {i_clk_50m}] -multiply_by 49 -divide_by 10 [get_pins {u_hdmi/u_display_pll/PLL_inst/CLKOUT1}]
create_generated_clock -name clk_cam200 -source [get_ports {i_clk_50m}] -multiply_by 4 [get_pins {u_cam/u_system_pll/PLL_inst/CLKOUT0}]
create_generated_clock -name clk_cam50  -source [get_ports {i_clk_50m}] -multiply_by 1 -divide_by 1 [get_pins {u_cam/u_system_pll/PLL_inst/CLKOUT1}]
create_generated_clock -name clk_ddrf   -source [get_pins {u_cam/u_system_pll/PLL_inst/CLKOUT0}] -divide_by 4 [get_pins {u_cam/u_frame_buffer/DDR3_Memory_Interface_Top/gw3_top/u_ddr_phy_top/fclkdiv/CLKOUT}]

                 -group [get_clocks {clk_pixel clk_serial}] -group [get_clocks {clk_cam200 clk_cam50 clk_ddrf}]
```

**四组**：sys / 摄像头 PCLK / HDMI（像素 + 串行必须同组，5:1 同相）/ DDR（200M + 50M + PHY 内部 fclkdiv）。
倍频比按各 IP 的 defparam 折算：`display_pll` 是 `50×49/2/25 = 49 MHz` 与 `50×49/2/5 = 245 MHz`；
`gowin_pll` 是 `50×16/1/4 = 200 MHz` 与 `50×16/1/16 = 50 MHz`。

**效果**：Hold 违例 **2605 → 18**（−99.3%）、Setup **84 → 62**，`default_gen_clk` 全部消失，
**4 条真违例的数字一个没变**（−0.107 / −0.193）。Fmax 也不变——约束只影响分析，不影响布局。

**代价**：`clk_ddrf` 显式定义后，DDR3 IP 内部 8 条 `u_dll/CLKIN → dll_step_base_*`（−3.4~−3.8 ns）
开始被分析。它们在基线里因 `WARN (TA1132) ... was determined to be a clock but was not created`
**根本没被分析**，属「从看不见到看见」，且由 IP 自身保证，不加假路径掩盖。

**踩坑一次**：第一版把 `clk_cam50` 写成 `-source clk_cam200`，但 PLL 的 CLKOUT0/CLKOUT1 是并行的两个输出
而非串联，报 `TA1021`（source 找不到）。改成与 CLKOUT0 同源（`i_clk_50m`，`-divide_by 4`）即通过。

<a id="773-方案-alg_col-与-lg_slot-解耦-负优化已回退"></a>
### 77.3 方案 A：`lg_col` 与 `lg_slot` 解耦（❌ 负优化，已回退）

**假设**：pixel 域那两条的最长一段是 `lg_slot → ×24 → 减 → 条件减`，而 `lg_col` 其实只依赖当前列号。
用 `24 = 8 × 3` 得到与除法器无关的算法：`x mod 24 = 8×(⌊x/8⌋ mod 3) + (x mod 8)`，
`⌊x/8⌋` 是接线移位、`x mod 8` 取低 3 位，只剩 `n mod 3`（偶位系数 1、奇位系数 2 加权和，再循环减 3）。

**结果**（`build.tcl`，631.3 秒）：

| 指标 | B 实验基线 | 方案 A |
| --- | --- | --- |
| Setup 违例端点 | 62 | **74** |
| Hold 违例端点 | 18 | 18 |
| `i_clk_50m` TNS | −0.107 / 1 | **−2.816 / 10** |
| `clk_pixel` TNS | −0.193 / 3 | **−2.374 / 6** |
| `i_clk_50m` Fmax | 49.733（LL24） | **48.489（LL25）** |
| `clk_pixel` Fmax | 48.807（LL30） | **47.613（LL26）** |

**目标路径确实消失了**：`hcount_r_3 → Disp_Green` 不在 Setup 表里了。
**但**：原本 −0.052 的 `vcount → u_dyn_text/o_rdata_3` 恶化到 **−0.594**，同族 `o_rdata_0` −0.557；
另外冒出 `u_imu/rx_buf[9]_2 → n3913_s/A[2]`（−0.623）与 `u_nav_ctrl/n1093_s → cut_ok_r_s0`（−0.588）——
**后两条所在模块一行都没改**。

<a id="774-为什么又失败pixel-域是多条近临界路径并存"></a>
### 77.4 为什么又失败：pixel 域是「多条近临界路径并存」

方法论 §4 已预警「局部路径缩短后，其他近临界路径也可能接替成为全局瓶颈」，§3「多类路径同时接近临界值时，
单点优化效果有限」。本次是第三次验证这条规律（前两次是 §76 的 A1 / B1'）。

具体机制：
1. 新增的 `lg_cx_*`（8 个 1 位加法 + 2 级 5 位加法 + 3 级条件减）本身不算深，但它**多占了 ~20 个 LUT**，
   改变了 pixel 域的摆放，把 `vcount → dyn_text` 那条推过线。
2. `lg_col` 与 `lg_slot` 解耦后，原来共享的除法器输出要驱动两条独立路径，**扇出与布线变差**。
3. `imu` / `nav_ctrl` 的新违例说明影响是**全局布图级**的，不是局部的。

<a id="777-结论与建议"></a>
### 77.7 结论与建议

1. **4 条真违例的缺口只有 0.4%~0.5%**（−0.107 / −0.193 ns，周期 20 ns / 20.408 ns）。
2. **四次改动每次都让整体更差**，共同原因是布图扰动，不是算法错误（四次都通过全部仿真）。
3. **唯一的净收益是 SDC 改造**：报告从 `84 setup + 2605 hold` 缩到 `62 setup + 18 hold`，
   让真实瓶颈可见。它不改逻辑，所以不改 Fmax。
4. 若要真正消除这 4 条，需要**成组改动**（同时处理同族的多条近临界路径），而不是单点优化；
   或接受现状——两个域分别只差 0.53% 和 0.39%，但这属于工程判断，不是时序报告能保证的结论。
