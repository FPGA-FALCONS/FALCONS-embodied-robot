## ACG720 摄像头物理接口核验（2026-10-24）

<a id="report-01--当前结论"></a>
### 当前结论

用户提供芯片丝印 `GW5AT-LV138PG484AC1/10 2518CA0N`，可识别为 GW5AT 138K 系列，但不足以确定 PCB 型号、版本或接口是否焊接。用户反馈实板没有 DVP 插座；尚未收到实板正反面及 PCB 版本照片，因此不能把本地资料中的连接器视为用户手中实物已经确认存在。

在本地《ACG720-138&60K通用原理图》第 11 页，摄像头连接器为 **P4、Header2x10（20 针）**，引出 CMOS 并行摄像头信号。DVP 是传输接口名称，实板丝印可能写 P4／CMOS／CAMERA，不能只找“DVP”字样。

此前“板上使用 2×9、18 针连接”的说明混淆了 BY_OV5640_V1.1 模块插头与开发板连接器，应以本次原理图核验和实物比对为准。2×9 模块是否可接 2×10 插座取决于具体针序、方向、供电和空针位置，不能按针数直接购买／插接。

## 摄像头 → FPGA → RK3588：实现与验收

2026-10-24。目标是保留现有OV5640采集、DDR/HDMI显示与车辆控制，增加独立的图像上传支路。摄像头不接RK3588。

<a id="report-02--代码与硬件路径"></a>
### 代码与硬件路径

```text
现有OV5640模组和现有针序
  → ov5640_capture
      ├→ 原DDR3/HDMI/现有UI（保留）
      └→ camera_fx2_stream（完整帧RAM、CRC32、跨时钟所有权）
          → 板载CY7C68013A Slave FIFO
          → J5高速USB Type-C → USB-A Host/RK3588
          → libusb → FIMG解析 → RGB565图像 → 现有YOLO入口
```

J2的CH340E串口用于调试，不能作为本次图像USB链路。J5/J2是USB连接器编号，不能和扩展排针编号混淆。已知加长相机排线的干扰仍需队友处理，传输模块不会修复采集前已经损坏的画面。

- 发送RTL：`vendor/verilog-reusable-modules/modules/camera_fx2_stream/rtl/camera_fx2_stream.v`。
- 自检仿真：同包 `sim/run_sim.py`，输出在电脑证据目录。
- 隔离整合：同包 `tools/build_integration_candidate.py`，固定来源 `ec759b161f378fcf545a836fe8bed63295efe1a2`，保留现有相机针序和 `rfifo_rden=pixel_req`。不覆盖旧工作区顶层，不包含其他人的未提交修改。
- 板端接收：`host/fx2_camera/receive.py`；协调器复用 `host/ai_coordinator/usb_camera.py` 与 `frames.py`。
- 实际端点选择：`host/fx2_camera/probe.py`、`selection.py`；配置模板 `usb.example.json`，未知值保持null。

默认从1024×600采集流抽取为512×300，单帧307200字节。完整缓存持有至发送结束；USB暂停时丢新整帧，不向相机施加背压。额外/不足像素的帧不提交。当前为隔点抽取，尚非抗混叠缩小；带宽计算和仿真通过不能替代小目标识别验收。

<a id="report-02--发送协议与固件合同"></a>
### 发送协议与固件合同

FIMG v1为24字节头，全部多字节字段小端：

| 偏移 | 字段 |
| --- | --- |
| 0..3 | ASCII `FIMG` |
| 4 / 5 | version=1 / format=1（RGB565小端） |
| 6..7 | 头长24 |
| 8..9 / 10..11 | 输出图像宽 / 高 |
| 12..15 | uint32传输序号 |
| 16..19 | payload字节数，必须等于宽×高×2 |
| 20..23 | CRC32，覆盖头前20字节及全部payload，采用zlib同一算法 |
| 24起 | 逐行紧密排列的RGB565像素 |

RTL先完整采集，再在IFCLK域遍历冻结RAM计算CRC，然后发送。故头中的CRC无需预测，也不会混合两个相机帧。序号属于完整上传帧序列，尚不是显示DDR的采集帧身份，不能直接用来保证屏幕同帧叠框。

FX2必须与RTL一致：16bit同步Slave FIFO、FX2提供48MHz IFCLK、EP6 IN/FIFO地址2、FLAGC高表示可写、512字节AUTO-IN、SLWR/SLOE/SLRD/PKTEND低有效。短帧尾部由PKTEND提交；整512字节包不额外提交空包。实际VID/PID/接口/端点必须读取描述符；不会从厂例名称猜测为已配置。

FIMG v1没有采集时间或开机会话ID。USB积压帧到达时可能已旧，接收器明确标记 `timestamp_origin=host_receipt_only`、`source_timestamp_verified=false`。当前接收适合传图和shadow识别；在完成源时钟对齐/会话扩展前，不解除真实运动准入限制。FPGA复位之后明确重启接收会话，不让CRC正确但倒退的序号自动重新成为新观测。

## 高分辨率相机直传：从 512×300 到 640×375（FIMG v2）

日期：2026-10-24
范围：OV5640 → FPGA → FX2 CY7C68013A → RK3588 USB；不包含 FPGA 烧录和整车上板。
结论先行：**1024×600 1:1 直传在现有 DVP + FX2 链路做不到；已实现并验证 5/8 直接抽取的 640×375@30fps 无整帧缓存方案。**

---

<a id="report-03--1-为什么不能直接-11-传-1024600"></a>
### 1. 为什么不能直接 1:1 传 1024×600

OV5640 默认配置（`0x3035=0x21`）PCLK 约 42 MHz，1024×600 RGB565。注意 `DVP_Capture` 是 8-bit 输入、**每 2 个 PCLK 才形成一个 RGB565 像素**（`Hcount[0]` 为 1 时 `DataValid`）：

- 帧内瞬时像素率：42 MHz ÷ 2 = **21 Mpx/s = 42 MB/s**（此前报告写成 42 Mpx/s / 84 MB/s，是漏算 2 PCLK/像素，已修正）
- 30 fps 平均：1024×600×30 = 18.4 Mpx/s = **36.9 MB/s**
- DVP 摄像头**不能反压**；`pixel_valid` 来了就必须接住，否则只能丢像素/丢整帧
- FX2 高速 Bulk-IN 实际吞吐通常只有 **约 12–24 Mword/s**（24–48 MB/s 量级，取决于固件、主机和 FLAGC）
- 现有 512×300 方案用一整帧 BSRAM 冻结后慢慢发；要缓存 1024×600 需要 1.23 MB（9.8 Mbit）弹性缓存
- 应用工程当前 BSRAM 预算：原来 283/340；去掉 160 块旧流式缓存后为 **127/340**
- 因此 1:1 30 fps 的困难不在“瞬时 84 MB/s”，而在**平均 36.9 MB/s + 帧内 42 MB/s 突发**与 FX2 实际持续吞吐的差距；5/8 方案的帧内速率只有 21×25/64 ≈ **8.2 Mpx/s（16.4 MB/s）**，留有明确余量。

因此“缓存不够就直接转发、FPGA 不处理”在 1:1 全分辨率下会**每一帧都在帧内溢出**，与帧率高低无关：即使 15 fps，HREF 内的像素仍是 42 Mpx/s。降低帧率只增加消隐时间，不能降低有效行内的瞬时速率。

可选路线：

| 方案 | 分辨率 | 帧内速率 | 需要缓存 | 结论 |
|---|---|---|---|---|
| 旧 `camera_fx2_stream` | 512×300 | 10.5 Mpx/s（抽取后） | 2.46 Mbit BSRAM | 已有，画面偏小 |
| 直接 5/8 抽取（本方案） | **640×375** | **8.2 Mpx/s（16.4 MB/s）** | 131072×16 FIFO（128 BSRAM） | **已实现，源 30 fps** |
| 直接 3/4 抽取 | 768×450 | 11.8 Mpx/s | 小 FIFO 很紧 | 仅在 USB 稳定 >47 MB/s 时考虑 |
| 直接 1:1 | 1024×600 | 21 Mpx/s（平均 18.4） | >1.2 MB | 30fps 需 FX2 持续 >36.9 MB/s；否则 DDR3/降 PCLK |
| DDR3 第二读口 | 1024×600 | USB 限速 | DDR3 | 下一步，改动大、需显示仲裁验收 |

5/8 抽取保持 1024:600 的宽高比（640:375 = 1.7067），输出 240,000 像素/帧，是 512×300 的 **1.56 倍像素**，但行内速率只有 **8.2 Mpx/s（16.4 MB/s）**，给 FX2 留出余量。

> 候选默认 `FRAME_DECIMATION=2`（源 30 fps → 实际 15 fps），先把 USB 余量留足；实测 FX2 能稳定 ≥15 MB/s 后，把该参数改为 1 即可冲 30 fps。即使 30 fps 时发生堵塞，溢出帧会被标坏并触发 `BACKOFF_FRAMES`，不会污染后续帧。

<a id="report-03--2-实现结构"></a>
### 2. 实现结构

```
OV5640 → ov5640_capture ─┬→ 现有 DDR3 → HDMI/UI（完全不动）
                         └→ x/y 5-of-8 相位抽取（无整帧缓存）
                              → 131072×16 异步 FIFO（gray 指针，128 BSRAM，256 KB 弹性缓冲）
                              → IFCLK 8 字预取 FIFO
                              → FX2 EP6，FIMG v2
```

关键点：

1. **抽取在写入 FIFO 前完成**：每 8 列取 5 列、每 8 行取 5 行；`x_phase` 每像素推进，`y_phase` 只在行尾推进，保证 640×375 的规则栅格。
2. **不缓存整帧**：FIFO 只吸收行/突发抖动；USB 堵塞导致溢出时，该帧标记为坏帧。
3. **坏帧仍保持字节定界**：FIMG v2 的 payload 长度固定，缺失部分补零，尾部 CRC 故意不匹配；主机丢弃该帧并继续解析下一帧。
4. **预取 FIFO**：异步 FIFO 读延迟 1 拍；8 字同频预取后，FX2 写侧约 **2 个 IFCLK/字**（48 MHz 下约 24 Mword/s），而不是原来的 4 拍/字。
5. **帧级自适应**：`FRAME_DECIMATION=2` 先隔帧；溢出后 `BACKOFF_FRAMES=3` 再跳帧；等发送器空闲且 FIFO 有余量才启动下一帧头。
6. **FIMG v2**：24 字节头 + RGB565 payload + 4 字节尾 CRC；头字段 20 是头 20 字节的 CRC，尾部是头 20 字节 + payload 的 CRC。主机同时兼容旧 v1。

板级参数：

```verilog
camera_fx2_direct #(
    .SOURCE_WIDTH(1024), .SOURCE_HEIGHT(600),
    .FRAME_DECIMATION(2), .BACKOFF_FRAMES(3),
    .START_WAIT_CYCLES(4096), .FIFO_DEPTH(4096),
    .DECIM_NUM(5), .DECIM_DEN(8)
) u_camera_fx2_direct ( ... );
```
