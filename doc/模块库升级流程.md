# 模块库升级流程（源库更新后，如何把项目库一并更新）

> 适用场景：队友往 `verilog-reusable-modules` 推了新提交，本工程要跟着升级内嵌快照。
> 本文每一步都在 2026-10-15 用**一份源库副本造出 4 个模拟提交**实测跑通过（见第九节）。

---

## 零、先认清三件事

| 事实 | 含义 |
| --- | --- |
| 源库与本工程是两个独立仓库 | 升级 = 用 `git archive` 把源库某个 commit 的内容**整体重放**到 `vendor\`，不是"拉取增量" |
| `vendor\` 是**只读快照** | 任何就地修改都会在下次 `sync_vendor.ps1` 时被静默覆盖 → 铁律：改动先在源库提交 |
| 升级是**有记账**的 | `VENDOR.lock`（commit + tree SHA256）+ `deps\vendor_manifest.sha256`（逐文件哈希）。所以"升没升、升到哪、动过没"随时可查 |

**角色分工**：让源库拿到新提交（`git fetch` / `git pull`）属于**写源库**，按铁律必须由你明确授权
或你自己做。本工程的脚本只做**只读**读取（`git archive` / `git log` / `git status`）。

## 一、六步操作（照抄即可）

```powershell
cd "D:\Programs\FPGA Projects\FALCONS-embodied-robot"
```

### 第 0 步（可选但推荐）：确认项目侧没欠账

```powershell
git status --short          # 上一次升级是否已提交？工作区是否有半截改动？
```

若上一次升级还没提交，先提交或先 `git checkout -- vendor VENDOR.lock deps/vendor_manifest.sha256` 回退，
**不要带着未提交的 vendor 变更去升级**（否则新旧混在一起，出事时说不清）。

### 第 1 步：让源库拿到新提交（★ 写源库，需你授权）

```powershell
git -C "D:\Programs\FPGA Projects\verilog-reusable-modules" fetch origin
git -C "D:\Programs\FPGA Projects\verilog-reusable-modules" log --oneline -5 origin/main
```

### 第 2 步：升级前体检 —— 先看清"源库到底动了什么"

```powershell
powershell -File tools\check_vendor.ps1
```

要看的四件事（实测输出）：

```text
[OK]   144 项逐一比对：全部与 VENDOR.lock 记录一致（未被本地改动）   ← ① vendor 干净
[WARN] 落后源库 4 个提交（本地 c9b8025 → 源库 68de95d）：            ← ② 落后多少
         68de95d fix(m10_radar): tweak doc
         8ab286a docs(gyro_tilt_comp): add porting note
         7bdaedd BREAKING feat(yaw_integrate): rename o_yaw to o_yaw_deg
         a4a80fa docs(motor_tb6612): clarify polarity calibration order
[WARN] 源库有 1 个标了 ⚠ BREAKING 的提交 —— 升级后应用层必须跟着改      ← ③ 有没有破坏性改动
[OK]   工程引用的包（6 个）在内嵌目录里与锁定快照完全一致              ← ④ 引用包有没有被本地改
```

**此时先判断要不要升**：若清单里全是文档类改动，升级零风险；若出现 `BREAKING`，
先读该包 README 顶部"应用层需要跟着改什么"，评估工作量再决定升不升。

### 第 3 步：同步快照

```powershell
powershell -File tools\sync_vendor.ps1
```

实测输出（关键是最后那段**差异报告**）：

```text
==> 检查源库（只读，不会写入）
    分支 main / ref HEAD / commit 68de95d (2026-10-15)
==> git archive 导出快照
==> 替换 vendor 快照（145 个文件）
==> 重算 SHA256 清单
    deps/vendor_manifest.sha256（145 个文件）
    tree_sha256 = a12091792c44ca397120ac792099846c41de4c7547f11a97fc80f15d75ec753a
==> 与上一份快照对比（c9b8025 → 68de95d）          ← 升级最该看的就是这一段
    内容变化 3 个文件   ← 其中 2 个属【工程引用包】★
          modules/m10_radar/README.md
        ★ modules/motor_tb6612/README.md
        ★ modules/yaw_integrate/README.md
    新增     1 个文件   ← 其中 1 个属【工程引用包】★
        ★ modules/gyro_tilt_comp/docs/porting.md
    ★ 工程引用的包有 3 个文件发生变化 —— 应用层（rtl\）可能需要跟着改；
==> 重写 VENDOR.lock
    VENDOR.lock：commit 68de95d / tree a12091792c44…
```

**读法**：`★` = 本工程 `deps\modules.list` 里引用的包。
没有 `★` 的改动（如上面的 `m10_radar`）本工程没用到，**可以直接忽略**；
有 `★` 的要逐个判断：只改文档 → 无需动应用层；改了端口名/参数名/默认值/行为 → 必须改 `rtl\`。

其他有用参数：

```powershell
powershell -File tools\sync_vendor.ps1 -Ref v1.2.0          # 升到某个 tag / commit，而不是 HEAD
powershell -File tools\sync_vendor.ps1 -LibRoot D:\other\lib # 从别处的源库同步（换机器 / 队友的库）
powershell -File tools\sync_vendor.ps1 -Force                # vendor 有本地改动时强行覆盖（慎用）
```

### 第 4 步：同步后再体检（确认新快照自洽）

```powershell
powershell -File tools\check_vendor.ps1
```

期望：**"已是最新：锁定 commit = 源库 HEAD"** + 逐文件比对一致。
若这里报 `[BAD]`，说明刚同步出来的快照与记账不符（脚本 bug 或磁盘问题），**别继续构建**。

### 第 5 步：跑库自带测试（把"库的问题"和"我的问题"分开）

```powershell
powershell -File tools\run_all_modules.ps1 -ReferencedOnly
```

实测：`PASS 7 / COMPILE-ONLY 0 / FAIL 0`。

- 全新克隆的机器第一次跑，或换了 ModelSim 版本时，去掉 `-ReferencedOnly` 跑全部 12 个入口；
- 这一步 FAIL 说明**新快照本身有问题** → 把日志（`logs\`）反馈给源库作者，
  或者先退回旧快照（见第八节）继续干活，不要在自己的应用层里找原因。

### 第 6 步：适配应用层并提交

```powershell
# 若差异报告里有 ★ 且涉及接口变化：改 rtl\ 下用到的实例化 / 参数
powershell -File tools\build.ps1        # 先体检再综合，顺便抓出 EX3152 之类的语法问题
```

确认无误后，把**快照与记账一起提交**（这是同一次动作，不要拆开）：

```powershell
git add vendor deps/vendor_manifest.sha256 deps/modules.list VENDOR.lock rtl
git commit -m "chore(vendor): bump module library c9b8025 -> 68de95d

- 内容变化 3 个文件（motor_tb6612 / yaw_integrate / m10_radar 的 README）
- 新增 gyro_tilt_comp/docs/porting.md
- 应用层：yaw_integrate 端口 o_yaw -> o_yaw_deg，已同步修改 rtl/imu/"
```

> `git add vendor` 会带上 `vendor\` 里的仿真产物吗？**不会** —— `.gitignore` 已忽略
> `work/`、`transcript`、`build/`、`*.qdb` 等（实测跑完测试后 `git status` 仍只有源文件）。

## 二、升级判据速查表

| 差异报告里出现 | 要做什么 |
| --- | --- |
| 只有未引用包（无 `★`） | 升级即可，应用层不用动 |
| `★` 但只有 `README.md` / 文档 | 升级即可；顺手读一下新文档（常有标定/接线新结论） |
| `★` 的 `rtl\*.v` 内容变化 | **必须**读该包 README 与 `git -C <源库> log -p` 的对应改动，核对端口/参数/行为 |
| `★` 新增 / 删除文件 | 包结构变了（如新增子模块、拆包）。新增要加进 `deps\modules.list`（若要用）；删除会让构建立刻失败，需改应用层 |
| 提交信息带 `⚠ BREAKING` | 按包 README 顶部说明逐条改 `rtl\`，改完**必须**跑 `tools\build.ps1` |
| 包清单新增 / 移除包 | `sync` 会打印"新增包 / 移除包"。新增的可按需加进 `deps\modules.list`；移除的若正在用，构建会失败 |

## 三、四种异常情况

### 1. 体检报 `[BAD]`：vendor 被本地改过

```text
[BAD] 3 个文件内容与锁定快照不一致（疑似在 vendor 里直接改了模块）：
```

- 改动有价值 → 按铁律**先在源库提交**，再回来 `sync_vendor.ps1`；
- 改动是临时的 → 直接 `sync_vendor.ps1` 覆盖掉（或 `git checkout -- vendor` 回退到上次提交）。

### 2. `源库里找不到锁定的 commit`

```text
[WARN] 源库里找不到锁定的 commit c9b8025（可能被 rebase / 强推过）。
```

说明源库被 `rebase`/强推过，历史重写了。做法：
`check_vendor -LibRoot <源库>` 看新历史，然后 `sync_vendor.ps1 -Ref <新的等价提交>` 重新钉住，
并在提交信息里写明"源库 rebase，重新锁定"。

### 3. 同步后 `run_all_modules` 某些包 FAIL

先在**旧快照**上确认同一测试是否通过（`sync_vendor.ps1 -Ref <旧commit>` 切回即测），
以此判断是"新提交引入的回归"还是"本机环境问题"（如没装 iverilog、ModelSim 版本差异）。

### 4. 同步后综合失败：包被改名/删除

`vendor\modules\<包>` 不存在时，`build.tcl` 会直接报
`ERROR: deps/modules.list references '<包>' but ... does not exist`。
改 `deps\modules.list` 与 `rtl\` 里的实例化即可。

## 四、回退（升级后悔了怎么办）

两条路，都不需要重新 clone：

```powershell
# 路 1：还在 git 里 —— 直接回退到上一次提交的状态（最干净）
git checkout -- vendor VENDOR.lock deps/vendor_manifest.sha256

# 路 2：未提交，或想回到任意历史快照 —— 用 VENDOR.lock 里记的 commit 反向同步
powershell -File tools\sync_vendor.ps1 -Ref c9b8025
```

> 因为"升级"就是换一份快照 + 换一份记账，回退同样是换回去，**不存在半升级状态**。

## 五、铁律回顾（升级时最容易违反的两条）

1. **模块的修改必须先在源库提交，再同步进本工程。** 在 `vendor\` 里改 = 造第二份真源，
   下次同步静默覆盖，而且没人会发现。
2. **未经你明确命令，不动源库。** 本工程脚本只读源库；`git fetch/pull/commit/push` 由你决定。

## 六、自动化建议（可选）

- 把 `check_vendor.ps1` 挂在 `build.ps1` 之前 —— **已经做了**，`tools\build.ps1` 第一次动作就是体检；
- 想让"落后源库"也变成构建失败（CI 场景）：`check_vendor.ps1 -FailOnOutdated`；
- 将来若改为 git submodule，本文流程可整体替换为 `git submodule update --remote`
  并在项目侧提交 gitlink —— 挂载点 `vendor\verilog-reusable-modules` 不变，应用层与脚本几乎不用改。

## 七、本次实测记录（2026-10-15）

用一份源库副本（`%TEMP%\falcons_lib_upgrade_demo`）造出 4 个模拟提交：
普通文档改动 ×2、`⚠ BREAKING` ×1、新增文件 ×1、未引用包改动 ×1。逐步跑完上述六步：

| 步骤 | 结果 |
| --- | --- |
| 升级前体检 | 正确报出落后 4 个提交、1 个 BREAKING、引用包本地无改动 |
| 同步 | 差异报告准确列出「内容变化 3 / 新增 1」，`★` 标出 3 个属引用包的文件 |
| 同步后体检 | `145 项逐一比对一致` + `已是最新（68de95d）` |
| 库自带测试 | `PASS 7 / FAIL 0`（引用包 6 个 → 7 个入口） |
| 恢复 | `sync -LibRoot <真实源库>` 后 tree 回到 `9f40e862…`（与升级前**逐字节一致**） |

演练还顺带暴露并修掉了两个脚本缺陷：逐文件比对条数被硬编码成 `144`（应随快照变化）、
BREAKING 提示用了 `[BAD]` 配色（让人误以为体检失败）。
